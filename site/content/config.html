Configuration reference

Every setting of /etc/kbf/kbf.toml, by table. A key is the long name of a flag (--storage-listen is storage-listen), and a flag on the command line overrides the key. A secret is never a value: the key holds the path of the file that has it. The file must not be writable by group or other. The modes are frontend and storage.

The source of truth is the templates in crates/kbf-cli/tests/golden, which a test holds equal to the flag definitions in kbf-cli. Where this page and a template differ, the template is right.

Tables: daemon history identity listener log memory outputs scheduler storage-client storage-node stores tls

[daemon]

KeyTypeDefaultModesDescription
async-threadstext NnoneallWorker threads of the async runtime, which run every task between its waits. Default: every CPU the process may use on the server; max(2, reserve/4), at most the physical cores, on the daemon
blocking-threadstext NnoneallThe most threads the runtime's blocking pool runs at once, for calls that wait on a disk or a process (a thread is made when a call needs one and ends when idle). Default: 512 (tokio's) for the server, 64 for the daemon
cpu-threadstext NnoneallThreads for CPU-bound work, such as hashing, which never waits and so is held to the CPUs. Default: every CPU the process may use on the server; max(2, reserve/2), at most the physical cores, on the daemon

history-index-roottext ROOTnonefrontendWhere history's index rows live in the state store: ui/, or <prefix>ui/ for a prefix that ends in /, so that one state store can hold several farms' history apart. Left out, it is ui/. Needs --history-objects
history-objectstext URInonefrontendWhere build history is kept: an object store, s3://bucket/prefix?endpoint=http://host:port (the key pair is the AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY of the environment) or file:///absolute/path (a directory this process owns, not the cold store's). invocation-memorynumber268435456frontendThe memory, in bytes, the invocation records may take together (docs/design/invocations.md, section 3.5). [memory]

KeyTypeDefaultModesDescription
memory-ladder-giblist[4, 16, 32]frontendThe memory rungs of an action, in GiB, ascending and each at least 1. The first is what an action that names no size (kbf-book-mem-gib) books. An action that passes its own memory limit runs again on the next rung above what it booked, and after the last on a whole host: the memory of the largest node that could run it, so that no other lease fits there. A rung not below that node's memory is skipped for the whole host. An action that does finish keeps its rung: later runs of it start there

[outputs]

KeyTypeDefaultModesDescription
segment-upload-idle-secsnumber60storageHow long, in seconds, a segment upload may go without a call before it is dropped and its memory returned. An upload is also dropped when the connection that began it closes; one that is committing is kept until its commit ends
segment-upload-max-bytesnumber34603008storageThe most bytes, records and footers together, one segment upload on the worker listener may hold in memory (docs/design/write-path.md, section 4.2): the segments it declares that are not written to the hot store as they arrive (all of them, without one). Not a limit on a blob's size: a segment held in memory holds no record over 16 MiB (kbf_front::MAX_UNSTAGED_BLOB_BYTES), and an upload with a larger one and no room on the hot store is answered FAILED_PRECONDITION, so the daemon sends its records by ByteStream, which streams a large blob to the cold store. Those ranges are held until the upload commits, admitted under --write-bytes-in-flight with every other upload: a Begin waits while that is spent. At least 33 MiB (kbf_front::MIN_SEGMENT_UPLOAD_BYTES), a daemon's upload of small files with room to spare, and at most --write-bytes-in-flight, so any legal Begin can be admitted; the server refuses to start otherwise. At most kbf_front::MAX_ADMISSION_BYTES, the most one admission counts, so a Begin never holds more than it is counted for under the bound

Placement is exactly what "off" does. "on" gives the scheduler the prediction as the cost of the operation's lease, at submit (on the legacy core also again for an operation read back from the state store at a start), which charges the learned memory as well as the cores: a lease is admitted to a node only while the memory charged to the node's leases stays within the node's memory. An operation the estimator has no usable row for, or is not asked about (not an action, one that asks for a GPU, no OS pinned, no subject), gets none and is charged as it is with "off". "shadow" and "on" need --learned-sizes shadow or "on"; "on" needs --placement-load on; a prediction only changes what the lease is charged: the memory limit and the cores it is booked and run with stay the request's and the ladder's. A server given a combination that breaks one of these refuses to start
