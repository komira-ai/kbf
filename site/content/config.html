Configuration reference

Every setting of /etc/kbf/kbf.toml, by table. A key is the long name of a flag (--storage-listen is storage-listen), and a flag on the command line overrides the key. A secret is never a value: the key holds the path of the file that has it. The file must not be writable by group or other. The modes are frontend and storage.

The source of truth is the templates in crates/kbf-cli/tests/golden, which a test holds equal to the flag definitions in kbf-cli. Where this page and a template differ, the template is right.

Tables: daemon enroll-service executor handover history identity job-read listener log memory outputs packs scheduler storage-client storage-node stores task-runs tls worker-session

[daemon]

The table of the three runtime thread-count flags. Its name is a legacy one, kept because files already carry it; a key of an earlier release in it is refused.

KeyTypeDefaultModesDescription
async-threadstext NnoneallWorker threads of the async runtime, which run every task between its waits. Default: every CPU the process may use
blocking-threadstext NnoneallThe most threads the runtime's blocking pool runs at once, for calls that wait on a disk or a process (a thread is made when a call needs one and ends when idle). Default: 512 (tokio's)
cpu-threadstext NnoneallThreads for CPU-bound work, such as hashing, which never waits and so is held to the CPUs. Default: every CPU the process may use

api-token-filetext API_TOKEN_FILEnonefrontendA file holding the token operator API writes (cordon, drain, uncordon) must present as Authorization: Bearer <token>. It must be owned by the server's user with mode 0600 or 0400, or the server refuses to start; run the server as a user other than the worker's, whose builds could read it. proxy-auth-filetext PATHnonefrontendA file holding the per-boot secret of the TLS-terminating proxy in front of this server (docs/design/frontend-proxy.md, section 3): exactly 32 bytes, owned by the server's user with mode 0600 or 0400, read at start. The proxy presents them as 64 lower-case hex digits in x-kbf-proxy-auth. With it, the REAPI, worker and operator listeners take calls from loopback only, and believe x-kbf-node-id and x-kbf-role only from a call that presents the secret; every other x-kbf-* header is dropped. The worker listener then takes the proxy's identity in place of a client certificate (it needs no TLS flags), and the operator API's writes must come through the proxy as well as carry the token (a local curl write is refused). The storage listener is not covered: it keeps its own mutual TLS. Without it, behavior is as before
reapi-auth-policytext REAPI_AUTH_POLICYnonefrontendA JSON file with the REAPI listener's authentication policy and authorizers (docs/reapi-auth.md), read once at start; a file that is not a valid policy stops the server. The worker listener does not read it; on the operator API only the build pages and the blob route do, and they are off unless it names their authorizers
