Design

Why kbf is built the way it is. This page is the reasoning and the rules the code keeps; the architecture page is what runs where, and the story is how we got here. works today is in the code; specified is designed and not built.

Three roles, not one server

A build farm has to answer three different questions: who should run this, where are the bytes, and what does this machine do. kbf gives each its own role, so each can fail, scale and be updated on its own.

  • The frontend decides. One process sees the queue and every worker's free room, so placement is a single decision made in one place, and the scheduler is a pure state machine: it reads no clock and draws no random number, so the same inputs always give the same choices and a simulation replays a failing seed exactly. Its state is in a store it writes before it acknowledges anything, so queued work survives a restart. The frontend holds no blobs, which is what lets it be swapped while builds are running.
  • Storage places by digest. A blob's two owners are computed from its digest and the member list by rendezvous hashing, so there is no leader to elect and no ring to coordinate, and removing a member moves only what that member held. Two copies mean a storage node can restart without losing a blob, and a writer sends each byte once, to the first owner, which forwards it.
  • The daemon only dials out. A worker needs outbound connectivity to the frontend and nothing inbound, so a Mac on a desk or a node behind a firewall joins the same way a rack server does. Work arrives on the stream the daemon opened; bytes never do, so a slow blob transfer cannot starve the control stream.
  • Who you are is in the certificate. Authority comes from a role in a certificate, not from a network location: the same listener refuses a storage certificate that tries to open a worker session, and a daemon certificate speaks for exactly one node.
  • Combined modes are colocation, not another design. storage-and-daemon and all-in-one run the same roles in one process. On a node that does both, the daemon's input cache and the node's local storage are one cache on one disk, never two copies of a blob.

The deliberate absences: no leader election among servers, no per-action resource reservations a user must tune, and no client-side kbf component. Buck2 and Bazel speak REAPI to one address.

Admission: how work is admitted, queued and refused

An action passes four gates before it runs. Each gate has one outcome for an action it cannot pass, and says why in words a person can act on.

  • Why wait before refusing. A worker that can run the work is often a moment away: daemons reconnect within seconds of a server restart, and a Mac that reboots is gone for minutes. The wait restarts whenever the operation becomes servable again, and counts from the first unservable round, through changes of reason.
  • Queue order. By urgency, then by submission. The levels are interactive (300), ci (200) and batch (100). Today the front submits every action at ci; reading the level from a request header and preempting batch work are specified. Urgency is never a platform property, because platform properties are part of the action digest and urgency must not split the cache.
  • Twins join. A new request for a hermetic action already in flight, under the same instance name, joins it as another waiter instead of queueing a second run.
  • Admission counts CPUs, not memory. Room on a worker means free whole cores and GPUs and a memory request the node could ever give; what other leases hold of its memory never keeps an action out. An action's memory is the limit its cgroup first runs under, not a booking. The node's memory-pressure backstop pauses new starts, and the memory ladder (below) handles an action that outgrows its limit. This is why there is nothing to tune per action.
  • Shutdown. A frontend that is stopping refuses new Execute calls with UNAVAILABLE, which Buck2 retries at open, and keeps the streams it has.

Failure classes and retry budgets

When an action fails, the person reading the build log needs one answer first: is this mine to fix, or the farm's? The design names four classes:

ClassMeaningExample
FarmThe farm could not run the action, or ran it on a node unfit for it, or booked too little memory. The operator's or the farm's to fix.Lost contact, a driver that failed around the action, a kill below the action's own limit.
RequestThe action cannot run as written, on any node. The client's to fix.A command with no arguments, an image named by tag, a blob never uploaded.
ActionIt ran on a fit node and exited non-zero, passed its own timeout, or needs more memory than any node has.A compile error, a failed assertion, a timeout.
AmbiguousIt ran and failed in a way the farm cannot attribute yet; one rerun on another node decides.A SIGKILL kbf did not send. specified

The rule behind them is that a farm-side problem never reaches the client as the action's exit code: an answer of OK means a fit node ran the action to the end. A request error is never INTERNAL, because the client would wait for an operator who has nothing to fix. A test failure and a test error are both the action's, and the farm passes them through untouched. The class names are the design; what the code carries today is the set of outcomes and budgets below.

  • The budgets do not mix. A rung of the ladder is not a farm rerun and a farm rerun is not a rung, so a long ladder never takes a fault's reruns and faults never stop the ladder short of the cap. With the default ladder an operation runs at most 1 + 3 + 2 times for these causes.
  • What is not charged. A lease given up for reconnection or a session switch never ran, so it spends no budget.
  • Nothing a lost run produced reaches the action cache. A killed run sends no result, a lost result never completes an operation, and a late result from a lease that was given up is refused once the operation holds a new lease. Only a successful, cacheable result is written, and before the callers are answered.
  • Execution is at-least-once, with fenced results. A partitioned daemon can run past its lease, and its result is rejected. Content-addressed outputs make a stale upload junk, never corruption. works today

Ambiguous reruns, flake tracking per action digest, known failure signatures after a run, and alerts for a node that needs a person are in the failure-classes design and are specified. So is retrying a failure the daemon cannot classify beyond the farm-fault budget above.

Placement

A placement round walks the queue in order and gives each operation to one worker. At most 256 grants are made per round, so one log flush covers a round, and a round runs after every input and once a second when nothing changes.

  1. Feasible, then room works today

    A worker is a candidate if it was heard from within the 60-second lease grace, is not cordoned and not paused by its phase, reports a driver that serves the lease kind (container, native or fake for action; native-whole-machine for whole_machine), and its report satisfies the action's platform (OSFamily, ISA, xcode, gpu and the rest). A Mac is never the least loaded worker for Linux work, because the platform is decided first and the load only ranks the workers that pass.

  2. Spread by dominant booked share works today

    Among the candidates with room, the worker with the least booked as a share of its capacity gets the lease. The share is the larger of its CPU share and its memory share, compared exactly in integers so a replay chooses the same worker. Ties go to the worker with the fewest leases, then to the first by name. A share is not capped at 1: a worker booked past its memory is still more loaded than one booked less.

    The reason is that a node out of cores runs its actions slowly and a node out of memory kills them, so both count. Spreading keeps work off a node that is about to be the one that hurts. The price, which the scheduler design states, is that a large action is likelier to wait than under first-fit: with eight one-core leases on two eight-core workers, first-fit leaves one worker empty and a six-core action runs at once, while spreading leaves four on each and it waits.

  3. A size, not a reservation works today

    Every action books one core and 4 GiB, the first rung of the memory ladder, unless it names a size with kbf-book-cpus and kbf-book-mem-gib (whole numbers in plain digits, because +4 and 04 would book the same as 4 under a different action digest and miss its cache entries). A worker's capacity is read from its own report: cpus times 1000 millicores, memory in GiB, GPUs.

  4. Whole-machine leases works today

    Some work needs the whole machine: UI tests that need a logged-in session, anything that must not share a Mac. A lease with kbf-lease=whole_machine goes only to a worker that holds no lease and is at least as large as the request, and books all of it. If it fits nowhere, it holds one feasible worker: the one it held last round while that one still could, else the one with the fewest leases. No operation after it in queue order, less urgent or younger, is placed there, so the worker empties as its leases end. Operations before it still are placed. No lease is ever stopped for it.

    An ordinary action at a worker's whole memory, the last rung of the ladder, also needs a worker with no lease, but it holds no worker. Under sustained spread load that wait can be long, and nothing reserves a worker for it; callers wait. A reservation for large actions is specified.

  5. Reruns avoid the node that failed works today

    A rerun of a farm fault is placed on a live, serving node that none of its failed runs ended on, and waits for one while any could run it after its bookings end. On a farm of one node it takes the same node.

Other placement controls: --reserve-cpus leaves CPUs for the farm's own processes, with no pinning of leases; --lease-placement=numa-node puts each lease on one NUMA node's CPUs and memory. specified are scoring beyond the spread (alignment of the request with free room, inputs already on the worker, best fit to keep large holes free), learned action sizes with a margin that shrinks as samples grow, memory that is booked but unused lent to batch work, and protected floors a node keeps for other services.

Zero-downtime updates

The constraints came first. A restart of the frontend fails every build in flight, because in our reading Buck2 does not recover an Execute stream that breaks after it started. And a busy farm is never idle, so waiting for a quiet moment does not work. So an update has to move one piece at a time while the rest keeps serving. The updates page has the sequence and what is built; these are the decisions behind it.

  • Frontend first, and every pair of releases is within one step. A new frontend serves old nodes, so nodes can never be ahead of it on an upgrade, and the order of nodes does not matter for correctness. Going back across a protocol change reverses the order; if no order works, the change is a flag day.
  • One writer decides at a time. During a frontend swap two processes overlap, so scheduling is fenced by a generation held in the state store: each write checks it in its own transaction, and after takeover the old process can finish its open streams from rows the new one writes but cannot schedule. That is why the overlap needs Postgres, since a SQLite state file is held by one process, and why the proxy that routes streams never sends GOAWAY: a stream stays with the process it started on.
  • Streams are never cut by choice. A stopping frontend refuses new calls and keeps its open ones, with no deadline by default; the old process is signalled only when it holds nothing, and never killed.
  • A planned restart is not a failure. A storage node is marked planned_down before it restarts, so writes skip it at once instead of failing for the 15 seconds until its membership row lapses, and reads fail over. It is not draining, which would start moving the node's whole shard for a one-minute restart.
  • One storage node at a time. With two copies of every blob, two nodes down lose data. A node updates only when every other member is active and fresh, no copy is owed, and the node has no open writes. Daemon-only hosts have no such coupling and go up to a set number at a time.
  • Capacity beats the update. An operator can set a floor, min_serving, so that a host is cordoned only while that many others of its platform stay; it is 0 by default, which is no floor. The wait for a host's leases ends at a limit, after which it is uncordoned and tried later.
  • Every unknown fails closed. A missing metric is never zero. A failure after the activate order holds the run for a person instead of retrying or skipping the host.
  • Trial, then keep. A new release runs on trial. It is kept only if it reports healthy and a confirm lands inside the window; a crash loop reverts it within a few starts. The previous release is only ever one that was confirmed.
  • Root does the little it must. kbf never installs, downloads or restarts anything. A separate root tool downloads through an unprivileged user, verifies the release against its attestation and the order's commit, and runs the new binary's self-report before it moves a link. The source of releases is read from the installer's own file, never from an order, so a compromised kbf can drop or delay an update and cannot make the host run an unattested one.
  • Rollback is the same mechanism with the old release as the target. It is not available across a one-way change, which the page names before you start: a metadata-log raise, a schema contract and a protocol floor.

What is built and what is not is on the updates page, including that the installer's downloader is not wired in yet.

Rules the code keeps

  • Commit before Start. Placing an operation only proposes the grant. The daemon gets Start after the grant is written, never for a grant that stopped being current. A lease the store does not know can never run.
  • One accepted result per operation, from the lease the operation currently holds, and only if every output it names is already stored.
  • Two clocks keep copies apart. The scheduler gives up every lease on a worker it has not heard from for 60 seconds; a worker stops self-fenced work 40 seconds after the newest heartbeat the scheduler acknowledged was sent. A margin covers a change of process, and the constants are checked at compile time so a change cannot break the order.
  • Present means durable. A blob is acknowledged and reported present only once its bytes are stored and its place is committed; every byte is checked against its digest on upload and on read; a hit never points at missing files.
  • Settings are flags or keys of one file. A secret is never a value: the key holds the path of a file. The object store's key pair is the one exception, taken from the standard AWS_ variables.
  • Nothing asserts a speed. Tests do not depend on timing, and every test has been seen failing on a planted defect.
