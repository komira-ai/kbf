Updates

A farm is updated one host at a time, frontend first, and a new release is kept only if it comes up and says so. This page is the order of events on a host, how nodes and the frontend are rolled, and the rules that decide whether you can go back. Each part is tagged works today or specified. The design page has the reasoning.

Read this first. The pieces of an update are built and tested one by one, but they do not yet run end to end. kbf-installer has no release downloader wired in at this commit, so kbf-installer run refuses every activation order with "this installer has no release fetcher wired in", and kbf-installer update --frontend cannot stage a release. A Mac cannot activate at all yet, because the installer has no way to read that Mac's leases. What you can do today on a host is place a verified release yourself and use the swap, confirm, revert and rollback verbs below. The table at the end lists every piece and its state.

Releases on a host

kbf-installer is the only writer of release files. It installs each kbf release into its own directory and never changes one afterwards; an update moves two links.

PathWhat
/var/lib/kbf-installer/releases/<commit>/kbfOne release. A VERIFIED marker is written into the directory before it is renamed into place; a release without it is not trusted.
releases/current, releases/previousRelative links to a <commit> directory. Every unit runs releases/current/kbf --mode=<mode>. previous is only ever a release that was confirmed.
state.json, state.json.bakThe truth about current, previous and a swap on trial. A missing or corrupt file is never treated as empty: the installer uses the backup, or writes nothing and stops for an operator.
status.jsonWhat kbf reads: the installed and staged commits, the state (idle, fetching, staged, activated_unconfirmed, confirmed, reverted, refused) and the last refusal. It is world-readable. The status verb is not built; read this file.
orders/The one directory kbf can write. kbf writes one record per order; the installer reads each once and removes it.

kbf-installer gc removes releases nothing needs. It keeps current, previous, a staged one, a swap on trial, any release a running process executes from, and the newest one more (--keep, default 1).

Swapping a release, and the confirm window

An order names a release by its 40-digit commit. Orders come from kbf, which can only drop, delay or burn an order id; it cannot make the installer run something unverified. The order is a locator and a set of claims. Every claim is checked again by root.

  1. Refuse early, change nothing works today

    Before any fetch the installer refuses: a replay or an older (epoch, generation) than it has acted on, a commit not in 40 lowercase hex, a size over the limit, a trial already pending, a generation below the floor in installer.toml, and a live lease. It reads leases itself, from the cgroup of the unit it restarts; the order's claim is never used. On a frontend unit an activate is refused as denied, since a frontend holds no leases and moves by its own path (below). At least 60 seconds must pass between activations.

  2. Fetch and verify not wired

    An unprivileged kbf-fetch user pulls the tarball from the one configured source, over a pipe, so it can create no file. Root then checks, in order: the byte count, the SHA-256 against the order and against the attestation bundle's subject, the attestation offline with the pinned gh (repository, workflow, branch, and the order's commit as --source-digest), the archive shape (exactly one regular file, no links), and finally the binary names itself: kbf --version --json, run as kbf-fetch, must report the ordered commit and the same protocol and schema facts the order expected. The code and its tests exist; the installer binary does not build a fetcher yet, so this step refuses today.

  3. Flip, state first works today

    The installer writes the whole new target to state.json with a pending-confirm record, then moves previous and then current by atomic renames, then restarts the unit. A crash at any point is repaired at the next start: the state file is the truth and the links are made to match.

  4. The window works today

    Before each start of the unit, kbf-installer boot-check counts the start. The window to confirm opens at the first start after the flip, 900 seconds by default (120 to 1800 with run --window-secs), and a release that has started 3 times without a confirm (--starts) is reverted before it starts a fourth time, so a crash loop ends in seconds.

  5. Confirm or revert works today

    The new kbf reports activated_unconfirmed and the frontend sends a confirm. A confirm is accepted only if it names the pending activation, the unit is active and the running process is the new release. With no confirm by the deadline, the installer reverts: state first, then the links, then a restart, and reports reverted. A new release that is itself compromised can confirm itself; the only defences are the attestation and the branch the package trusts.

The verbs an operator uses. Each is a dry run until --apply, and each names the service to restart by its own flag, never from an order:

# keep the swap on trial; the id is the activation, "<epoch>-<order id>"
$ sudo kbf-installer --apply confirm --id 1-7 --unit kbf-daemon.service
# undo it now
$ sudo kbf-installer --apply revert --id 1-7 --unit kbf-daemon.service
# point current at previous, with no window; refused while a swap is pending
$ sudo kbf-installer --apply rollback --unit kbf-daemon.service
# adopt a release you placed by hand as the first one
$ sudo kbf-installer --apply record-release --commit <commit>

A rollback makes the previous confirmed release current again and restarts the unit. There is no window to confirm it.

Rolling the nodes

Storage and daemon hosts are updated by the frontend, one at a time. You offer a release; the frontend's controller does the rest.

Offering a release works today

  • A frontend started with --releases-dir (it needs --api-listen and a state store) keeps a release store: the tarballs and their attestation bundles, uploaded with PUT /v1/releases/{commit}/{platform}/{name} and listed by GET /v1/releases. A platform counts as complete only when every tarball it needs is stored with its bundle.
  • POST /v1/update/desired with {"commit": "<40 hex>"} offers a release. It answers 409 unless the store holds some platform of it complete. The generation moves only when the commit differs, so a repeated click is not a new run. A rollback is the older commit offered the same way, under a higher generation. GET /v1/update shows the desired release and the policy; POST /v1/update/pause and resume stop and start new hosts.
  • The controller runs where the frontend starts. By default it starts hosts for the desired release as soon as one is offered; an operator turns that off with auto_nodes: false in the update/policy row, or pauses it.

What happens to one node works today

The controller writes each step to the state store before it acts, so a restart resumes from the rows. At most one storage node is out at a time, because every blob has two copies. Daemon-only hosts and Macs have no storage coupling and go up to max_hosts_out at a time, 1 by default, beside it.

#StepWhat it doesIf it fails
1ClaimTakes the one place in update/slot for this host.Nothing changed.
2CordonPlacement stops offering the node new leases (POST /v1/nodes/{node}:cordon). A node with no leases is cordoned in the step it is picked.Give the host back.
3Wait for leasesThe node's running leases end by themselves. Limit: 15 minutes on Linux, 60 on a Mac.Uncordon and try later: capacity beats the update.
4Planned downStorage hosts only. The member is marked planned_down, so writes skip it and reads fail over, and the controller waits until it reports no open writes (60 seconds).Undo the mark, uncordon.
5GateStorage hosts only. With this node out, every other member must be active and fresh, no copy may be owed anywhere, and none may be catching up or planned down.Undo and give the host back.
6ActivateThe order to the host: flip and restart, as in above. Wait up to 5 minutes for activated_unconfirmed.The host reverts itself.
7Rejoin storageStorage hosts only. The new process registers: active at once if its index is whole, catching_up while it rebuilds. An intact node that is not active in 120 seconds is reverted; a rebuilding one is waited for.Revert, or wait.
8RepairedStorage hosts only. The copies owed during the downtime are settled, up to 5 minutes.Hold the run; the binary is healthy, so no revert.
9ConfirmThe order to keep the release.The installer's own timer reverts.
10Rejoin workUncordon. Done when the node gets a lease, or one heartbeat with nothing waiting for it.The node stays cordoned and an alert is sent.

So a node is cordoned (draining new work, finishing what it has) from step 2 to step 10, and a storage node is also planned down from step 4 until it re-registers. Planned down is not draining: draining starts moving the node's blobs to other owners, which a one-minute restart must not. The mark lasts at most the dwell, 300 seconds, and the controller alerts before it runs out. Daemon-only hosts skip steps 4, 5, 7 and 8.

  • Any failure up to the gate gives the host back. From the activate order on, nothing uncordons the host until step 10, and a failure holds the run for a person. It is not retried and the host is not skipped.
  • With no idle node after 2 minutes, the controller cordons the node with the fewest leases, so a farm that is never idle still drains one node at a time. A Mac that is busy is deferred and picked again when it goes idle.
  • An unknown count never reads as zero: a missing metric fails the gate.
  • A rollback is another release offered under a higher generation; hosts past the activate order finish their step, finished hosts are walked back by the same code.

A frontend that is stopped, as in a restart, drains too: on SIGTERM it refuses new Execute calls with UNAVAILABLE, which Buck2 retries, and keeps every open stream until its action is done, with no deadline by default. The packaged units set TimeoutStopSec=infinity for the frontend, storage and all-in-one modes, because a stop that ends the drain fails every build in flight. A daemon drains for up to 600 seconds (--drain-deadline-secs) and its unit allows 660.

The frontend

A frontend cannot be restarted in place without failing builds: in our reading of Buck2, it does not recover an Execute stream that breaks after it started. The frontend host therefore runs kbf-installer proxy on its one public port, and the frontend is swapped behind it.

How the swap works built

  • The proxy terminates TLS and forwards each HTTP/2 stream to the active kbf --mode=frontend process on loopback. A stream stays with the process that was active when its headers arrived, until it closes. The proxy never sends GOAWAY to a client.
  • The new release starts in the idle slot as a candidate (--await-takeover): it opens the state store and checks the schema, and takes no generation, bumps no epoch and schedules nothing. Two processes side by side need Postgres.
  • Hold, quiesce, takeover. The proxy holds new streams for at most 15 seconds, the old process stops scheduling and flushes (3 seconds), the candidate takes the store's generation (10 seconds) and keeps the epoch, and the proxy releases the held streams to it. Every write is fenced by the generation, so the old process cannot write scheduler rows after the takeover. If takeover fails the proxy kills the candidate and resumes the old process from the store.
  • Daemons and storage nodes redial: the old process ends their streams with UNAVAILABLE and the redial is routed to the new one. A result a daemon has not seen acknowledged is sent again.
  • The old process keeps answering the Execute and WaitExecution streams it holds, from the results the new one writes, with no timeout. It is sent SIGTERM only when it holds no stream and no worker session, and never SIGKILL.
  • Bake and confirm. The proxy watches the new process for 5 minutes by default, then sends a confirm order for the staged release. There is no automatic rollback while the proxy runs: you roll back with the API. A restart of the proxy that finds a failed switch before the confirm rolls back by itself.
# from the frontend host, no root: swap the frontend, then have it update the nodes
$ kbf-installer update --commit <commit> --frontend --api LOOPBACK_ADDRESS:PORT --nodes

update is a client of the proxy's update API; --api is the loopback address and port of the proxy's public socket. It needs the operator token (--token-file, default /etc/kbf/api-token), is refused under sudo, writes no order itself and waits up to --handover-timeout-s (3600) for the update to end. The API is POST /v1/update/frontend with {commit, request_id, nodes, rollback}, GET /v1/update/frontend for the phase, and abort, rollback and force-retire under it. It answers 409 while another update is open or an old process still drains. The phases are accepted, fetching, verifying, staged, preflight, starting, ready, holding, quiescing, switching, switched, baking, nodes, draining and done, plus failed and rolled_back. With nodes, the new frontend sets the desired release itself once it has baked.

Gaps specified

  • The proxy's readiness check for a candidate asks for /readyz, a health-service call and a GetCapabilities; the last two probes are not built, so a swap on a real process stops at ready. The proxy's own cold start waits on /readyz alone.
  • The compatibility gate that reads the new release's protocol, min_protocol and state_schema and refuses a swap before anything starts is not built. Run kbf --version --json on both releases yourself; see version skew.
  • Staging a release for the swap needs the installer's downloader, which is not wired.
  • An all-in-one host cannot run two processes. Its swap is stop then start, with the proxy holding new streams, 300 seconds at most.
  • The proxy itself is updated with its package, not by this path: GET /v1/update/frontend shows restart_pending while the running proxy is not the installed binary. A restart of the proxy cuts every stream through it.
  • The older --handover-socket and Envoy path still exist in kbf --mode=frontend for a frontend on SQLite. A Postgres frontend refuses it and is updated through the proxy.

Version skew

During an update the farm runs two releases at once, for seconds on the frontend and for hours across the nodes. Every release says what it speaks in kbf --version --json:

FieldWhat it governs
protocol, min_protocolThe kbf.worker.v1 versions the binary speaks. A frontend accepts daemons from min_protocol through protocol; a daemon speaks exactly its protocol. Both are 1 in this build. A storage node's registration is refused below the map's floor, and the floor never falls.
state_schemaThe newest Postgres schema version the binary has a migration for. kbf-installer migrates the database to it before the release starts, and refuses with installer_too_old if the installer embeds fewer migrations than the release needs.
meta_logThe highest metadata-log machine version the binary runs. See one-way changes.
admin_protocolThe calls between the proxy and the frontend processes it starts.
profile, commit, versionprofile must be release; the installer checks the commit against the order.
  • Order. Upgrade the frontend first: it accepts old nodes as long as its min_protocol is at or below the oldest protocol a node runs, and a new protocol is fine. To downgrade across a protocol difference, do the nodes first, so no node dials a frontend that no longer accepts it. If no order satisfies both, the change is a flag day: stop the nodes, move the frontend, start them. A release that introduces new behaviour does not raise min_protocol in the same release. specified The check that applies these rules and prints the numbers is not built; GET /v1/nodes and GET /v1/members report oldest_protocol to read by hand.
  • Pairs of releases. A pair of storage nodes spans an update, so the storage calls (ByteStream, the copy leg of a write, the action store) are meant to work between a release and the one before it, in both directions. No cross-version test exists yet.
  • Schema. An update runs only expand migrations: additive steps that an older binary ignores. A contract step (a drop or a rename) is refused by an update and nothing applies one yet; it would ship a release after the one that stopped using what it removes. A release that was reverted after its successor migrated still starts, because kbf accepts a schema newer than its own while every row above its range is an expand.
  • The installer. The installer is not part of a release and does not update itself. Operator floors, min_generation and min_protocol in installer.toml, only go up, and only rollback may go below them.

One-way changes: what rollback needs

A rollback is safe as long as the release you go back to can read what the newer one wrote. Three things can say it cannot.

  • The metadata log. A storage node raises its log's machine version at start, once, and a lower binary cannot open a raised log: it refuses at start. Going from release N to N-1 is reversible only if meta_log(N) <= meta_log(N-1); a build that prints no meta_log is unknown, and unknown is not reversible. If you have to go back past a raise, the log has to be restored: stop the node and put back a copy of its --meta-dir taken before the update. Without a copy, a node can rebuild its index from the footers of the segments in the object store and registers as catching_up while it does; the action cache is not rebuilt, so the actions whose entries only that node's log held run again. Treat that as recovery, not rollback.
  • A contract schema step. Once one exists and has run, the older release cannot read the database. Back up before an update that carries one.
  • The protocol floor. A frontend rolled back to a build with a lower oldest protocol keeps the stored floor. Rolling back across a protocol bump after the nodes updated is a flag day.

The state database is backed up daily on frontend and all-in-one hosts by kbf-backup.timer; start kbf-backup.service by hand before an update you may want to undo. kbf-installer restore --file FILE restores a dump into an empty database.
