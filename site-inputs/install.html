Install

What you install, on which machine, how to check the files before you run them, and what kbf-installer sets up. Each part is tagged: works today is in the code, specified is designed and not built.

Where installing stands. CI builds, signs and attests every file below, and the kbf-installer package installs. Two steps of the one-command path are not built: kbf-installer setup cannot download the first kbf release yet, and the hosted install.sh has no release payload to fetch. Until they land, you place a verified kbf yourself. The shortest path says how.

What you install

kbf is Rust. A release has one runtime binary, kbf, and the tools around it. Nothing is built on your machines: the files come from CI.

ProgramWhat it isPlatforms
kbfThe runtime, with five modes chosen by --mode. It runs a role; it never installs, downloads or restarts anything.Linux x86_64, Linux arm64, macOS arm64
kbf-installerThe one root tool of a host: it sets the host up, verifies a kbf release, swaps releases and reverts a bad one. It never updates itself; the package manager replaces it.Linux x86_64, Linux arm64, macOS arm64
kbf-server, kbf-daemonThe earlier separate programs. kbf-daemon is the worker that kbf --mode=daemon runs; kbf-server is the older single server that holds the cache and the scheduler in one process. A new host uses kbf.Linux x86_64, Linux arm64
kbf-deployThe manual path: renders and checks the systemd units of a mode (render-units, check-units, install-units) and checks a node certificate (verify-cert).Linux x86_64, Linux arm64, macOS arm64

Which machine runs what

A host's role is the flag --mode=, or mode = "..." in /etc/kbf/kbf.toml; a flag overrides the file. It is never a subcommand. The architecture page says what each role does.

ModeRunsPut it on
frontendThe REAPI listener your build tool dials, the scheduler, the listener daemons and storage nodes connect to, and the operator API. It keeps no blobs. Its scheduler state is in a state store: setup configures a Postgres database you provide, and kbf also accepts a SQLite file for one process.One Linux host. Clients, daemons and storage nodes know only its name.
storageThe content-addressable store and action cache: a fast local tier, a metadata log, and a cold store (a directory or an S3-compatible bucket).Linux hosts with an SSD. Two or more for replication.
daemonThe worker. It dials the frontend, fetches inputs, runs each action in isolation and uploads outputs. It listens on no port.Linux (rootless containers through crun) or a Mac (plain processes, --driver native).
storage-and-daemonA storage node and a daemon in one process, sharing one cache on the node's disk.Linux build hosts that also hold data.
all-in-oneFrontend, storage and daemon in one process.A single Linux machine, or a first try. The container driver only; kbf documents it for a trusted machine, because actions run beside the farm's state.

What a host needs

Linux, x86_64 or arm64

  • The binaries link glibc and need the glibc of Ubuntu 24.04 or newer.
  • A node that runs actions needs cgroup v2 with the memory controller, crun at /usr/bin/crun, newuidmap and newgidmap (the uidmap package), and a subordinate uid and gid range of at least 65,536 for the kbf user. The daemon checks the id range, crun, the two id tools and directory permissions at start and names the one that is wrong. The build-host guide lists the rest, including the kernel it was tested on.
  • Actions name their image by digest (docker://repo@sha256:...); the node fetches it from the registry, so it needs egress to the registries your actions use.
  • A frontend or all-in-one host needs a running Postgres server on the host (socket authentication, no password in any flag). kbf-installer setup creates the schema and, with --create-local-database, the role and database.

macOS, arm64

  • The Mac is a daemon host: kbf --mode=daemon, native driver, run by a LaunchDaemon. The binary targets macOS 14.0 and later.
  • The binaries are signed ad hoc (codesign with no certificate and the runtime option) and are not notarized. The .pkg is not signed, so Gatekeeper does not open it by double click; install it with installer from a shell after you verify it.
  • all-in-one is Linux only. The installer sets a Mac up as a daemon only.
  • kbf-installer on a Mac cannot yet activate a new release: it has no way to read that Mac's leases, so it refuses the order. Updates has the detail.

The release files

A release is the set of files one push run of the artifacts workflow on main built and attested for one commit, attached unchanged to a GitHub release. Nothing is rebuilt. <commit> below is the full 40-character commit; <platform> is linux-x86_64, linux-arm64 or darwin-arm64.

FileWhat it is
kbf-<commit>-<platform>.tar.gzThe kbf binary and nothing else. The same pattern holds for kbf-installer, kbf-deploy, and on Linux kbf-server and kbf-daemon. The tarball is reproducible: one binary always packs to the same bytes.
<tarball>.cdx.jsonThe CycloneDX SBOM of that binary, made from Cargo.lock.
<tarball>.sigstore.jsonThe Sigstore bundle of the tarball's build provenance. It lets a host verify the tarball with no network.
kbf-installer-<commit>-linux-x86_64.deb, ...-linux-arm64.debThe Debian package of kbf-installer: the binary, the systemd units (installed disabled), the pinned gh, a Sigstore trusted root and the trust settings. Each has its own .sigstore.json.
kbf-installer-<commit>-darwin-arm64.pkgThe macOS package of kbf-installer: the binary, its LaunchDaemon property list (not loaded), the pinned gh and the trust directory. It has its own .sigstore.json.
SHA256SUMSThe SHA-256 of every tarball, SBOM and package of the commit, sorted by name. It is a check for a damaged download; the attestation is the proof.

The trust settings inside a package name the branch the package was attested on: a package built on main trusts releases of main and no other branch. A tag push cuts a release, and only a commit on main with a green verdict and a successful artifacts run can be released.

Verify before you run

Every file is attested by the artifacts workflow with GitHub's build provenance. You need gh and the file. Name the repository, the workflow and the branch, or an attestation from any workflow of any branch would pass.

  1. Check the download works today

    $ sha256sum --check --strict --ignore-missing SHA256SUMS

    On a Mac, use shasum -a 256 --check --strict --ignore-missing SHA256SUMS.

  2. Verify the attestation works today

    $ gh attestation verify kbf-<commit>-linux-x86_64.tar.gz \
    --repo komira-ai/kbf \
    --signer-workflow komira-ai/kbf/.github/workflows/artifacts.yml \
    --source-ref refs/heads/main \
    --deny-self-hosted-runners

    For a file built from the development branch, feature/arch-v2, the ref is refs/heads/feature/arch-v2; a file attested there does not verify as main.

  3. Or verify offline, with the bundle works today

    This is what kbf-installer does. Fetch the trusted root once on a machine with a network, then verify with no network at all. --source-digest pins the commit, so a bundle for another commit of the same branch fails.

    $ gh attestation trusted-root > trusted_root.jsonl
$ gh attestation verify kbf-<commit>-linux-x86_64.tar.gz \
    --bundle kbf-<commit>-linux-x86_64.tar.gz.sigstore.json \
    --custom-trusted-root trusted_root.jsonl \
    --repo komira-ai/kbf \
    --signer-workflow komira-ai/kbf/.github/workflows/artifacts.yml \
    --cert-oidc-issuer https://token.actions.githubusercontent.com \
    --source-ref refs/heads/main \
    --source-digest <commit> \
    --predicate-type https://slsa.dev/provenance/v1 \
    --deny-self-hosted-runners

  4. Ask the binary what it is works today

    Unpack the tarball and read the build identity. The commit is the first 12 digits of the one in the file name.

    $ tar -xzf kbf-<commit>-linux-x86_64.tar.gz
$ ./kbf --version --json
# one line: admin_protocol, commit, meta_log, min_protocol, profile, protocol, state_schema, version

    The same line is what an update compares across two releases; see version skew.

kbf-installer

Install the package works today

Installing places files and starts nothing. Verify the package first (the same flags as above, with the package and its bundle), then:

# Debian and Ubuntu
$ sudo dpkg -i kbf-installer-<commit>-linux-x86_64.deb
# macOS
$ sudo installer -pkg kbf-installer-<commit>-darwin-arm64.pkg -target /

A package manager checks no Sigstore attestation of its own, so the verification above is your step. The packages are not signed with a key and there is no apt repository yet.

Other channels, specified. A hosted curl ... | sh script, a signed apt repository, rpm and apk packages, a Homebrew cask and a frontend container image are designed in the distribution design. The script is in the repository (packaging/install.sh) and is tested, but CI does not yet publish the payload it downloads, so none of these installs anything today.

What it does

Every verb that changes a host is a dry run until you add --apply (before the verb: kbf-installer --apply setup ...). --json prints one JSON object. Exit codes: 0 ok, 1 failed, 2 usage or a missing prerequisite, 3 refused by verification or policy, 4 busy, 5 needs an operator.

VerbWhat it doesState
setupFirst configuration of a host for a mode: accounts, directories, installer.toml, kbf.toml, the enrollment token, the database schema, and the units. Safe to run again.works today except --commit, which stops with exit 1 because no downloader is wired in
record-release --commit SHAMakes a release you placed by hand the first one: checks releases/<sha>, writes the VERIFIED marker and makes it current. You vouch for it; nothing is fetched or attested.works today
runThe service loop: acts on the order records kbf writes, reverts a swap that was not confirmed, writes status.json.works today; it refuses an activation of a release that is not installed
confirm, revert, rollback, gc, boot-check, quiesceSwap, keep, undo and clean up releases. Updates explains each.works today
update --commit SHA --frontendAsks the frontend host's proxy to swap its frontend and waits.built, with gaps listed on Updates
migrateAdopts a host laid out by the earlier deploy tool into the installer's layout, or puts it back with --rollback.works today
backup, restoreDump the state database to a directory and keep the newest seven; restore one into an empty database. A timer runs backup daily on frontend and all-in-one hosts.works today
proxyServes a frontend host's public port and starts the frontend processes (kbf-proxy.service).works today
status, checkRead the installer's state; validate its configuration.specified: both exit 1, "not implemented". Read status.json instead.

Setup, by mode works today

# a daemon host: dry run first, then --apply
$ sudo kbf-installer setup --mode=daemon \
    --frontend-url=https://frontend.example.internal:ENROLL_PORT \
    --token-file=/root/kbf.token
$ sudo kbf-installer --apply setup --mode=daemon \
    --frontend-url=https://frontend.example.internal:ENROLL_PORT \
    --token-file=/root/kbf.token

# a single machine
$ sudo kbf-installer setup --mode=all-in-one --release-url=https://releases.example.internal/kbf \
    --database='postgres:///kbf?host=/run/postgresql' --create-local-database

--frontend-url is the frontend's enrollment address, the one it serves with --enroll-listen. The flags each mode takes:

Mode--frontend-url--token-file--databaseRelease source
storage, daemon, storage-and-daemonrequiredrequiredrefusedfrontend (default) or url
frontend, all-in-onerefusedrefusedrequiredurl only, so --release-url is required

The rest: --release-source url|frontend, --release-url (https, no credentials in it), --min-generation (a floor for orders that only goes up), --commit (40 hex, needs the url source), --no-start, and for frontend and all-in-one hosts the listener, certificate and store flags that become kbf.toml keys (--listen, --worker-listen, --reapi-tls-cert, --worker-tls-cert, --storage-url, --cold-store, --meta-dir, and so on). A frontend can sit behind the bundled proxy with --proxy. Every key is on the configuration page; the verb's exact behaviour is in the setup guide.

A flag with a bad value stops setup before it touches the host, naming the flag and the rule and never the value. A key or certificate must exist and be owned correctly; setup checks that a key file is a regular file owned by the service user with no group or other bits.

What setup writes, and where

Path (Linux)What
/etc/kbf/kbf.tomlThe runtime's settings: mode, the frontend URL, the enrollment token path, and the flags above. Readable by the service group, mode 0640. A file with settings of your own is kept; one whose keys differ from the flags is refused with the key names.
/etc/kbf/installer.tomlThe installer's settings: release source and URL, the floors, the database URL (no password), the proxy table. The release source is read only from this file, never from an order.
/etc/kbf/enroll.tokenA node's enrollment token, mode 0600, owned by the service user.
/etc/kbf/api-tokenOn a frontend or all-in-one host, the first operator token: 32 random bytes as hex, mode 0600, made once. setup prints the path and never the secret.
/var/lib/kbf-installer/The installer's tree, owned by root: releases/<commit>/ with current and previous links, state.json, status.json, and orders/, the one directory kbf can write.
/usr/share/kbf-installer/trust/From the package: the pinned gh, trusted_root.jsonl and installer.conf with the branch it trusts.
systemd unitskbf-<mode>.service and kbf-installer.service, enabled. A node's unit starts when a release is installed; a frontend's unit is enabled and never started by setup.

On a Mac the configuration directory is /usr/local/etc/kbf, the installer is under /usr/local/kbf-installer and its state under /var/db/kbf-installer. The package creates the accounts kbf (the runtime), kbf-server (frontend and storage units), kbf-fetch (the release download, which owns no file) and kbf-verify (created, not used by the installer yet). The units run /var/lib/kbf-installer/releases/current/kbf --mode=<mode> and first run kbf --mode=<mode> --check, which prints every missing prerequisite and exits 2 without starting.

Enrollment

A storage or daemon node gets its certificates by enrolling with the frontend when it starts; there is no kbf enroll command. The operator makes a token through the operator API, the node presents it once, and later starts renew without it.

  1. Make a token on the frontend works today

    Tokens are a route of the operator API, which takes writes only from loopback with the bearer token setup made. The answer is the only place the token string appears.

    $ T=$(cat /etc/kbf/api-token)
$ curl -H "Authorization: Bearer $T" -H 'Content-Type: application/json' \
    -d '{"roles": ["daemon"], "max_uses": 3, "expires_in": 86400, "label": "rack 4"}' \
    http://localhost:API_PORT/v1/enroll/tokens

    roles is daemon, storage or both. expires_in is seconds, at most 30 days. The token kbft1.<id>.<secret>.<pin> carries the SHA-256 of the farm's root CA, which the node pins at first contact. A token can be listed (GET, never the secret) and revoked (DELETE /v1/enroll/tokens/{id}); revoking a node (POST /v1/enroll/nodes/{id}/revoke) burns its id.

  2. Give it to the node works today

    Put the token in a file and pass it to setup as --token-file. At its first start the node makes one key per role, sends the token and a certificate request, and writes the certificates and node.json under its state directory. Certificates are ECDSA P-256 and live seven days by default; a node renews at half of that, with no token. A token that lacks a role the mode needs, or a node.json that does not cover the mode, exits 2 and the node is never enrolled again by itself.

  3. The frontend's enrollment listener works today, with a limit

    A frontend serves enrollment only when started with --enroll-listen, --ca-dir (an empty directory gets a new CA once; an existing CA is loaded and never overwritten), --frontend-name and a signer. The production signer is a separate kbf-signer process that holds the CA key; it is not among the released files yet. The other choice is --ca-dev-file-signer, which keeps the CA key as a file in the frontend process and is meant for development. Revoking a node refuses its renewal at once, but storage does not yet refuse a revoked node's current certificate, so --enroll-listen also needs --enroll-allow-unenforced-deny.

You can also bring your own certificates and skip enrollment: every listener takes its certificate, key and client CA as files. Each certificate names exactly one role in a URI subject alternative name (urn:kbf:role:frontend, storage or daemon), and a daemon certificate has exactly one DNS name, the node id. kbf-deploy linux verify-cert --row ROW --cert FILE --ca-cert FILE checks a certificate against its row before you point a unit at it.

The shortest path to a working farm

One Linux machine runs a whole farm in one process. The quick start takes it from there to a first remote build and has the .buckconfig; this section is the install half.

  1. Get and verify kbf works today

    Download kbf-<commit>-linux-x86_64.tar.gz (or linux-arm64), its .sigstore.json and SHA256SUMS from the release, run the checks above, unpack it and put kbf on the host, for example at /usr/local/bin/kbf.

  2. Prepare the host works today

    Install crun and uidmap, give the kbf user its subordinate ids, and have a Postgres server on the host (requirements). Make a CA, a worker listener certificate, and a daemon certificate for the node id node1, and check them with kbf-deploy linux verify-cert.

  3. Check, then start works today

    These are the flags kbf --mode=all-in-one --help requires, plus the stores. --server is the process's own worker listener (port 8981 by default, on loopback), so the worker certificate must carry the name you give there, or you set --tls-server-name.

    $ kbf --mode=all-in-one --check \
    --worker-tls-cert /etc/kbf/worker.pem --worker-tls-key /etc/kbf/worker.key \
    --worker-client-ca /etc/kbf/ca.pem \
    --server https://localhost:8981 \
    --ca-cert /etc/kbf/ca.pem --cert /etc/kbf/node1.pem --key /etc/kbf/node1.key \
    --node-id node1 --driver container --data-dir /var/lib/kbf/data \
    --cold-store file:///var/lib/kbf/cold --meta-dir /var/lib/kbf/meta

    --check prints each missing prerequisite and exits 2, or 75 if a restart may help, without starting. Drop it to run. The scheduler state defaults to the local Postgres socket (postgres:///kbf?host=/run/postgresql). Put the same settings in /etc/kbf/kbf.toml (see configuration) to run it under a unit.

  4. Point your build tool at it works today

    Send actions, cache reads and blobs to the REAPI address, port 8980 by default. The quick start has the .buckconfig and the first build.

With the installer, specified. The intended path is curl -fsSL https://kbf.dev/install.sh | sudo sh, then sudo kbf-installer setup --mode=all-in-one ..., which downloads, verifies and starts the first release by itself. Today you can use the installer for everything but the download: install the package, run setup without --commit, place the verified release at /var/lib/kbf-installer/releases/<commit>/kbf (owned by root, mode 0755), and run sudo kbf-installer --apply record-release --commit <commit>. Then start the unit. For a farm of several hosts, the architecture says which mode goes where and Updates says how the farm moves to a new release.
