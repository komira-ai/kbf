Architecture

kbf is a frontend, storage nodes and daemons. This page says what each does, how one remote execution moves through them, where state lives and how the parts talk. works today is in the code; specified is designed and not built. The reasoning behind the shape is on the design page.

Three roles

A farm is made of three roles. The kbf binary runs one of them, or two or three in one process, chosen by --mode.

  • frontend

    The one address clients, daemons and storage nodes know. It serves REAPI v2 to Buck2 and Bazel, schedules actions, serves the listener daemons and storage nodes connect to, and serves the operator API. It holds no blobs: cache calls are passed to storage. Its scheduler state is in a state store, Postgres or SQLite.

  • storage

    The content-addressable store and the action cache. Blobs are placed by digest across storage nodes, two copies of each. A node has a fast local tier, a metadata log on local disk, and a cold store, a directory or an S3-compatible bucket, where every blob ends up.

  • daemon

    The worker. It opens one outbound mutual-TLS stream to the frontend and listens on no port. It reports what the machine is, runs the leases it is given, and moves blobs to and from storage. A Linux daemon runs each action in a rootless crun container; a Mac daemon runs it as plain processes with the process tree, memory and network watched.

The two combined modes are the same roles in one process: storage-and-daemon reads and writes the node's own storage in-process, so the daemon's input cache and the storage node's local data are one cache on one disk, and all-in-one runs all three. Nothing else changes between a split farm and a single machine.

The picture

A remote execution, step by step

Buck2 or Bazel needs no kbf component. It speaks REAPI to the frontend's address.

  1. The client uploads what is missing works today

    The tool asks FindMissingBlobs and sends the inputs the farm lacks. The frontend passes the calls to the storage nodes by digest and does not hold a blob: a ByteStream write goes through it to the blob's primary node, which copies it to the second owner.

  2. The action cache is asked first works today

    On Execute, unless the client set skip_cache_lookup, the frontend looks the action up in the action cache. A hit must pass the closure check: the stored result and every blob it names are present and readable, or the lookup is a miss. A hit answers at once with cached_result set and nothing runs. Clients cannot write the action cache: UpdateActionResult is always PERMISSION_DENIED, and only a daemon that ran the action writes an entry.

  3. The inputs are checked works today

    The Action, its Command and the input tree must be in the CAS. Each missing blob becomes a MISSING violation in one FAILED_PRECONDITION, as REAPI asks, so the client uploads and calls again. A platform no daemon could ever run, or a malformed one, is refused here too.

  4. The action is queued works today

    The scheduler keys each operation by instance name and action digest. A second caller for the same hermetic action joins the running one instead of starting another. Work waits in a queue ordered by urgency, then arrival. While it waits, the open stream gets the operation again every 30 seconds by default, so a load balancer's idle timeout does not cut it.

  5. A lease is granted to a daemon works today

    The scheduler picks a live daemon that can run the platform and has room. It writes the grant to the state store, and only then sends Start; before that the daemon has only a LeaseOffer and runs nothing. A lease the store does not know can never run. How the daemon is chosen is on the design page.

  6. The daemon runs it works today

    On Linux the container driver reads the image from the container-image platform property, which must name one architecture's manifest by digest, not a tag. It builds the input tree in the lease's scratch directory, makes a lease cgroup and runs the action with crun in a fresh rootless container that is never reused. The container has a network namespace with nothing configured, so no action has network; its root is the read-only image, and it writes only to /tmp, /var/tmp, /run, /root and the input root. On a Mac the native driver runs the action as processes.

  7. Outputs go to storage works today

    The daemon hashes each output file once, asks which blobs storage lacks, and uploads them as whole segments to the nodes that own them, then sends Result on its stream. Until the frontend has sent a storage map, the daemon moves blobs through the frontend's worker listener; once it has one, directly to storage.

  8. The result is accepted and answered works today

    The frontend accepts a result only from the daemon that holds the operation's current lease and only if every output is stored. A result with exit code 0 and no do_not_cache is written to the action cache before the callers are answered, so the next build, on any machine, gets a hit. A run that exits non-zero, such as a failing test, is returned to the caller and not cached. Failures that are the farm's, not the action's, take other paths; the design page lists them.

Storage

Members and the map

A storage node registers with the frontend and heartbeats to it. It does not talk to the state store; the frontend keeps the member rows there and pushes the map, the list of members with the rule that places a blob, down the node's stream and to every daemon. A node's identity, its member id and its boot counter come from the state store, so no node picks its own.

StateMeaning
joiningAdmitted to a farm that already holds data. Takes writes at once, is never the primary and is read last.
catching_upRebuilding its index. A read it cannot find answers UNAVAILABLE, never NOT_FOUND, because it may hold a blob it has not indexed yet.
activeA full owner.
drainingTakes no new writes and is still read in rank order.
downIts membership row expired (15 seconds after its last heartbeat by default). It stays in the map for a dwell, 300 seconds by default, before it leaves and its blobs have other owners.

An operator can mark an active member planned_down for a restart (POST /v1/members/{id}): writes skip it at once while reads fail over, so a planned restart does not fail uploads. Updates uses it. An operator promotes a joining member with the same route.

Placement and replication

  • Placement is rendezvous hashing over the digest, the member id and the member's weight, so removing a member moves only the blobs that resolved to it and there is no ring state to coordinate. The top two members are the owners. Every storage call carries the map generation its caller used; a node that holds a newer one answers STALE_MAP and the caller refetches and retries.
  • Writes go once to the primary, the first write owner. It streams the blob to the second owner and acknowledges when both hold it on the hot tier, so a client on a slow link uploads each byte once. If the second owner is unreachable, the primary acknowledges after its own durable write and records a repair debt in its journal; the debt is settled later and the frontend is told of it. A blob is never held whole in memory on the way.
  • Reads try the owners in rank order, then the owners of the previous map generation, then the cold store through an owner's index. A read that breaks after its first byte resumes on the next owner from the bytes already passed.
  • Action cache entries are sharded by action digest. An entry is committed only after the blobs it names are acknowledged, so a hit never points at missing files.

The write tier and the cold store

--hot-store is a directory on a fast disk. Uploads from several callers are grouped into shared segments, one object-store PUT and one metadata commit per segment, written to the hot tier and flushed to the cold store in the background by the blob's first owner. The tier's budget is 80% of the filesystem's free space less a floor, or --hot-store-max-bytes; at the budget, writes go straight to the cold store. A blob over 16 MiB is streamed and never held whole. Without a hot store, every upload goes straight to the cold store.

The cold store is where every blob ends up: s3://bucket/prefix?endpoint=... for MinIO, RustFS or S3, with the key pair from the standard AWS_ variables, or file:///dir, which refuses writes that would leave under 5% of its filesystem free and evicts the least recently used objects to stay above that. Objects are keyed under the id of the node's metadata log. A daemon-only host needs no cold-store credential, and the unit checks in kbf-deploy refuse to give it one.

If both owners of an unflushed blob are lost, the digests get loss marks: an action-cache entry whose result blob is marked is a miss, and the action runs again. A node whose index is lost rebuilds it from the footers the segments carry; the action cache is not rebuilt, because its entries live only in the node's log, so those actions run again.

Metadata and state

Two kinds of log or store hold two kinds of state, and they are not the same thing.

StateKept inDetails
Operations, leases, the queue, membership, the map, cordons, the desired releaseThe frontend's state store: --state-store postgres:///kbf?host=/run/postgresql or sqlite:///pathWritten before each change is acknowledged and replayed at start. Postgres is required for two frontend processes side by side, which an update needs; SQLite is held by one process. A URL with a password is refused. Every start of a frontend is a new epoch, so a daemon kills the leases it held before; a handover to a successor keeps the epoch.
The CAS index, the action cacheA node's metadata log, --meta-dir (default <hot store>/meta)A single-voter Raft log on local disk. An empty directory makes a new log with a new id; every later start reads the id from the directory.
Blob bytesHot tier, then cold storeSegments with self-describing footers.

The metadata log has a machine version, V1 to V5 in this build. A start raises the log to the version a feature needs (the write tier, eviction, node writers) once, and the raise is one-way: an older binary refuses a log raised past what it runs. kbf --version --json reports the highest version a build runs as meta_log. Updates says what this means for rollback.

No log is replicated between nodes. Each storage node has its own single-voter log, and the second copy of a blob, not of the log, is what protects the data. The Raft core itself (kbf-raft) can run several voters; running three on three hosts is specified.

  • Roles are in the certificate. One urn:kbf:role:<name> URI subject alternative name says frontend, storage or daemon. Each listener has a table of which role may call which method; a method not in the table is refused whatever the certificate. A node that is both storage and daemon holds two certificates and presents the one that fits each connection.
  • Certificates come from files and are re-read every 30 seconds by default (--tls-reload-interval-secs). A new certificate applies to the next handshake, a working configuration replaces the old one only if the new files make one, and a renewal never ends a connection in flight.
  • Plain text is a choice, not a default you can miss. A listener without its TLS flags serves plain text on any address. When the REAPI or worker listener does so off loopback, the start line ends with a warning=plaintext-off-loopback token. A plain-text worker listener refuses every blob call.
  • Identity of a farm's certificates can come from your own CA or from enrollment; see Install. A certificate lifetime is the only bound on a leaked key beyond the deny list: there is no CRL or OCSP.
  • The frontend can sit behind a bundled proxy (kbf-installer proxy) that terminates TLS for every connection on one public port, verifies the client certificate when one is presented, and forwards each HTTP/2 stream to the active frontend process with the verified identity as headers only the proxy can set. It exists so a frontend can be swapped without cutting streams; see Updates.

Not built yet

specified These are in the design documents and absent from the code.

  • Several frontends sharing one queue, and a leader election among servers. The scheduler runs in one frontend process; a second process runs beside it only during an update.
  • Moving blobs when a member joins or drains. A joining node fills from the writes it takes; copying the old owners' blobs to it is designed in the rebalance design.
  • Three-voter metadata logs, and snapshots and compaction of the log.
  • A check that a blob call comes from a daemon that is connected and reads only the inputs of its own leases. Today any certificate the deny list does not refuse can read a blob whose digest it names.
  • Reading a QoS level from a request, preemption of low-urgency work, learned action sizes, and placement scoring beyond the spread described on the design page.
  • iOS devices and macOS VMs as lease kinds.
