# kbf-bench

Times blob uploads to a kbf-server's CAS, and reads back, the way a daemon stores an
action's outputs: so a slow output upload can be measured apart from the build that
made it, on the node that saw it, against the same server.

`kbf-bench upload` builds a tree, connects as `kbf-daemon` does, sends every distinct
blob, and prints what each request took. `kbf-bench read` reads the same blobs back and
checks each one against its digest.

`kbf-bench noop` times actions that do nothing, from sending each Execute to its done
operation, against one or more frontends: the no-op benchmark of
[docs/design/actions-as-jobs.md](../../docs/design/actions-as-jobs.md) (section 10.1),
which measures what a build action costs apart from its own work. It is described
[below](#noop-the-cost-of-an-action).

## The tree

Generated by default, in the shape of one measured output tree: 15 000 files, 144 of
them empty, in 989 directories, 307 MB in all (`--files`, `--empty`, `--dirs`,
`--total-bytes`; sizes take B, KB, MB, GB, KiB, MiB, GiB). File sizes spread over about
three decades and add up to the total exactly. Or `--from-dir PATH` sends a real
directory (symlinks and other entries are skipped and counted).

Every non-empty file holds the run's `--seed` (generated: in its first 8 bytes; read
from a directory: 16 bytes appended), so a run with a new seed finds nothing already
stored, and the server does the whole write. Upload picks a seed from the clock when
none is given; the report names it, and `read` needs it, with the same tree flags.

Besides the files, a run sends each directory's REAPI `Directory` message (the output
directory's too: 990 for the default tree) and one `Tree` message of them all, as the
daemon does for an output directory. Each digest is sent once (the 144 empty files are
one blob), as the daemon does.

## The connection

`--cas` is the blob service: a server's worker listener (`https://<server>:<worker
port>`, as the daemon's `--cas`), or its REAPI listener (`https://`, or `http://` when
it serves plain text). The TLS flags are the daemon's: `--ca-cert`, `--cert`, `--key`,
`--tls-server-name`; with `--cert` and `--key` the files are loaded by the daemon's own
loader. One HTTP/2 connection carries every request, as the daemon's does, with the
daemon's default HTTP/2 windows (`--transfer-stream-window-bytes`, 8 MiB per stream and
eight times that for the connection).

## The requests

- `--method bytestream` (the default): every blob through the daemon's transfer engine
  (`kbf_transfer::Transfers`), as the daemon moves it. An upload is the engine's
  `put_chunks`, the call the container driver stores an output file with: the engine
  asks FindMissing about the blob first (its FindMissing calls coalesce, one call at a
  time, up to 1000 digests each) and sends one ByteStream Write only when the server
  lacks it. A blob the server already holds is not sent again and still counts as
  moved: it is in the CAS. `read` is the engine's ByteStream Read of the blob into
  memory.
- `--method batch`: BatchUpdateBlobs (BatchReadBlobs) calls of up to `--batch-bytes` of
  blob data (default 4 MiB, the front's limit), made directly: the engine does not
  batch yet. A larger blob goes through the engine, as with `bytestream`.
- `--in-flight N` (default 64, the daemon's): the most requests at once, and the
  engine's limit for the whole run, as `--transfer-in-flight` is for a daemon; a
  FindMissing call takes one of those slots too. Every other engine limit is the
  daemon's default.
- `--find-missing on` (upload; default off): FindMissingBlobs about the whole tree
  first, 1000 digests a call, then only the missing blobs. The daemon does not ask for
  the whole tree first; with `bytestream` the engine still asks about each blob.
- `--timeout-secs N`: stop after N seconds and report what finished (default 0: wait).
- `--progress-secs N`: a progress line on stderr every N seconds, and one at the start
  (default 10; 0 for none).
- `--json FILE`: the report as JSON too.

## Reading the report

```text
upload bytestream, 64 in flight, find-missing off, seed 4242
tree: 15000 files (144 empty, 0 skipped), 989 dirs, 307000000 bytes, 15848 blobs
15848 of 15848 blobs, 308000000 bytes, 15848 of 15848 requests in 41.200 s: 384.7 blobs/s, 7.48 MB/s
request          count     p50 ms     p90 ms     p99 ms     max ms
write            15848    170.000    260.000    900.000   1300.000
failed: 0
```

(The numbers above show the layout only; they are not a measurement.)

- **Line 3**: blobs and bytes moved whole out of those planned, requests answered out of
  those planned, the wall time from the first request to the last answer (or the
  deadline), the blobs moved over the wall time, and the bytes moved (in millions)
  over it. Both rates count only what finished, so a run the deadline stopped shows
  the rate it reached. A blob counts
  once the server answered it committed (upload) or its bytes hashed to its digest
  (read).
- **The table**: per kind of request (`write`, `batch_update`, `find_missing`, `read`,
  `batch_read`), how many were answered, and the nearest-rank percentiles and maximum
  of their times in milliseconds. A request's time runs from when it got an in-flight
  slot to its answer: for a `write`, from the engine's FindMissing question about the
  blob to the committed size answered, so it is the wait for that question plus the
  server's whole store of that blob (for kbf-server: its object
  PUT, the read-back of the segment and the metadata commit) plus the network.
  kbf-bench cannot split that time into those stages; only the server's own timers
  can.
- **failed**: requests or blobs that failed, the first ten messages after it, and
  `timed out` when the deadline passed.

The JSON has the same fields: `blobs_planned`, `blobs_done`, `bytes_done`,
`requests_planned`, `requests_done`, `wall_secs`, `blobs_per_sec`, `mb_per_sec`,
`requests.<kind>.{count,p50_ms,p90_ms,p99_ms,max_ms}`, `failed`, `errors`,
`timed_out`, with the run's flags and the tree's counts.

How to read them together:

- **Requests in flight, rate and latency.** With every slot busy, rate x latency ~
  in-flight (Little's law): 64 in flight at a 1 s p50 is about 64 requests/s. If
  `--in-flight 1`, `8`, `64` give the same blobs/s while the p50 grows with N, the
  requests wait for one another on the server: it stores one at a time. If blobs/s
  grows with N, the server overlaps them, and the per-request time is the cost.
- **bytestream against batch.** kbf-server writes each call's new blobs into
  segments of their own (one, for a call under the segment size), so a batch of many
  small blobs costs one store where ByteStream costs one per blob. A
  large gap between the two methods' blobs/s on the same tree is per-call cost, not
  bytes.
- **p50 against max.** A p50 far below p99 and max points at a slow few (a disk's
  latency spikes, a retry); p50 near max at a high value points at a fixed cost per
  request. Steps of about 40 ms are the signature of a TCP delayed ACK held against
  Nagle's algorithm.
- **Read after upload.** `read` with the same seed times the read path alone; every
  blob is there, so a failure is a lost or damaged blob.

## On a pilot node

Build it (it is not in the release assets):

```sh
cargo build --release -p kbf-bench
```

Copy `target/release/kbf-bench` to the node and run it as the daemon's user (who can
read the daemon's key), with the daemon's TLS files and its `--cas` URL (placeholders as in
[docs/deploy/linux-build-host.md](../../docs/deploy/linux-build-host.md)):

```sh
sudo -u kbf ./kbf-bench upload \
    --cas https://<server>:<worker port> \
    --ca-cert /etc/kbf/ca.pem --cert /etc/kbf/node.pem --key /etc/kbf/node.key \
    --in-flight 64 --timeout-secs 600 --json upload-64.json
```

Then the same with `--in-flight 1` and `--in-flight 8` (each run picks a new seed), once
with `--method batch`, and a read of the first run's tree (its seed is in the report):

```sh
sudo -u kbf ./kbf-bench read --seed <seed from upload-64.json> \
    --cas https://<server>:<worker port> \
    --ca-cert /etc/kbf/ca.pem --cert /etc/kbf/node.pem --key /etc/kbf/node.key \
    --json read-64.json
```

A smaller tree (`--files 1500 --empty 14 --dirs 99 --total-bytes 30MB`) gives an answer
in a tenth of the time when the full one is slow. Every run stores its blobs in the
farm's cache, where they stay until retention collects them.

Exit status: 0 when every planned blob moved; 1 when a request failed, a blob did not
move or the deadline passed (the report says which); 2 when the run could not start.

## noop: the cost of an action

`kbf-bench noop` sends Executes of actions that do nothing to each frontend it is given
(an *arm*), and writes one JSON line per run with the time from sending the Execute to
receiving the done operation, as the client saw it. It asserts no number and judges
none: the lines are for `js-analysis`, and the table it prints is for a first look.

```sh
./kbf-bench noop \
    --arm a=https://<arm A frontend>:<REAPI port> \
    --arm c=https://<arm C frontend>:<REAPI port> \
    --ca-cert <ca.pem> --cert <client.pem> --key <client.key> \
    --platform <name>=<value> \
    --jsonl noop.jsonl
```

### The action

Its input root holds one file, `noop`, executable: a static Linux program of 129 bytes
(x86_64) or 132 bytes (aarch64) that `kbf-bench` writes itself, an ELF header, one
load segment and the `exit(0)` system call (`src/program.rs`). It links nothing and
opens nothing, so it runs in any root file system. Its Command is `./noop`, with
`KBF_BENCH_NOOP=<seed>-<arm>-<phase>-<run>` in its environment, so every run of every
arm is an action digest of its own; every Execute sets `skip_cache_lookup`. The action
is cacheable, as a build's is. `--platform NAME=VALUE` (repeated) sets the Action's
platform properties, sorted as REAPI asks; `--instance-name` the instance name of every
request; `--arch x86_64|aarch64` the program's machine (default: the machine
`kbf-bench` runs on).

### The order

Before any Execute, every blob (the program, the input root, each run's Command and
Action) is sent to each arm by BatchUpdateBlobs, 500 a call, so the timed part is the
Executes alone. A refused blob or call stops the run before any Execute (exit 2).

Then two phases, each through every arm:

- **serial**: `--serial-runs` runs per arm (default 300), one Execute open at a time;
- **parallel**: `--parallel-runs` runs per arm (default 300), `--in-flight` Executes
  open at once (default 64).

In each phase the runs are taken in blocks of `--block` runs per arm (default 20), the
arms' blocks alternating in the order the arms were given: block 0 of every arm, then
block 1 of every arm, and so on. They are sent in that order through a window of open
Executes, 1 in the serial phase and `--in-flight` in the parallel one, counted over all
arms together: a run is sent as soon as one finishes, so the window slides across block
ends rather than waiting for a block to drain. One at a time, the arms take turns block
by block; many at once, about `--in-flight / --block` blocks are open at any moment,
the arms' alike, so load and drift on the nodes fall on both arms the same.

`--seed` is in every action's environment (from the clock when left out; the table
names it), so two runs of `kbf-bench` share no action.

### The records

`--jsonl FILE` gets one line per run, written and flushed as the run finishes:

| Field | What |
|---|---|
| `arm`, `phase`, `block`, `run` | which run: the arm's name, `serial` or `parallel`, the arm's block (from 0), the run's number in its arm and phase (from 0) |
| `in_flight`, `open` | the phase's window, and the Executes open (all arms) when this one was sent, itself included |
| `action` | the action digest, `<sha256>/<size>` |
| `operation` | the operation's name, as the stream's first message named it (to join with the frontend's logs) |
| `execute_to_done_ms` | from sending the Execute to receiving the done operation; `null` when none came |
| `ok`, `error` | `true` for a done operation, status OK, an `ActionResult` not from the cache and exit 0; otherwise `false` and why |
| `exit_code`, `worker` | from the result, when there is one |
| `queued_ms`, `worker_ms` | the result's `queued_timestamp` to `worker_start_timestamp`, and `worker_start_timestamp` to `worker_completed_timestamp`: the frontend's own times for the lease |
| `input_fetch_ms`, `execution_ms`, `output_upload_ms` | the result's three phases: a daemon's own stamps (the fields of its `lease phases:` line), or under the executor the task's claim |
| `claimed` | the three phases are a task's claim, not a daemon's measurement (`kbf_proto::task_claim`) |

A phase is `null` when either of its stamps is missing or they are out of order. The
executor's own phases (`kbf_executor_phase_seconds`: prepare, start, queue, task, ingest)
are a histogram on the frontend, not per lease, and are not in the result; join them by
the time of the run, or the frontend's logs by `operation`.

The table on stdout has, per arm and phase, the runs, how many failed and the
nearest-rank p50, p90, p99 and maximum of `execute_to_done_ms` over the runs that
succeeded (`-` when none did), then the first ten failures:

```text
noop x86_64, seed 4242, blocks of 20, parallel 64 in flight
arm         phase        runs  failed     p50 ms     p90 ms     p99 ms     max ms
a           serial        300       0     40.000     52.000     70.000     81.000
a           parallel      300       0     90.000    120.000    160.000    170.000
c           serial        300       0    260.000    310.000    400.000    420.000
c           parallel      300       0    600.000    800.000    950.000    990.000
failed: 0
```

(The numbers above show the layout only; they are not a measurement.)

A run fails, and is counted and kept, when the Execute is refused, its stream breaks or
ends before the operation is done, the done operation carries an error or no
`ExecuteResponse`, the response's status is not OK or it has no `ActionResult`, the
result came from the action cache, or `./noop` exited other than 0. The other runs go on.

Exit status: 0 when every run succeeded; 1 when one failed (the table says which); 2
when the run could not start: an arm named twice, an arm's URL or TLS file refused, the
`--jsonl` file not made or not written, or an arm refusing the blobs.
