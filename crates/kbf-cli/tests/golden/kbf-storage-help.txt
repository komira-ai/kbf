The storage node: the cache, served over gRPC to frontends and workers.

Usage: kbf --mode=storage [OPTIONS]

Options:
      --cold-store <URI>
          The durable object store, where every blob ends up: `file:///absolute/path` (a directory, `kbf_objstore::FsStore`: locked while the server runs, a second server on it is refused; a write that would leave its filesystem with less free than it keeps, 5% of its size and at least 1 GiB, is refused and wakes the evictor, which forgets the least recently used objects (never one used in the last minute) and deletes their files while less than twice that is free) or `s3://bucket/prefix?endpoint=http://host:port` (MinIO, RustFS; the key pair is `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`; query keys `region`, `conditional-put=true` for a store that refuses to overwrite a key, and `min-put-rate=BYTES_PER_SEC`, the slowest rate a PUT body may reach the store at: a PUT is cut after 60 seconds plus its body's length at that rate, 1 MiB/s by default). Objects are keyed under `<prefix><log id>/` (`kbf/` for a directory and for an S3 URI without a path), the id of the metadata log. A directory is checked against the index by a start-up pass in the background; a lost or damaged object is also found when it is read, or before an action-cache hit that needs it is served (a miss). There is no `memory:` store: a `file://` path on a tmpfs is one. A storage node may instead be given the word `registered`: it holds no store of its own and, at each start, waits for the frontend's registration (`kbf cluster object-store`), then runs on the registered endpoint, bucket, prefix and keys, fetched over its storage certificate and held in memory only, after the probe of the keys; it never falls back to another store, and a registration that changes reaches it at its next start (until then the frontend shows it `pending`). With `registered`, `--cold-store-credentials-file` is refused and `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_ENDPOINT_URL` are not read
      --cold-store-credentials-file <PATH>
          The key pair of an `s3://` `--cold-store`, in a file: JSON `{"access_key_id": "...", "secret_access_key": "..."}`, a regular file (a symbolic link is refused) that the server's user owns and no one else can read (mode 0600 or 0400). The secret is never a flag: a command line is world-readable. Without it the key pair is read from `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, which is deprecated: the start logs one warning and a later release refuses the variables. A `file://` cold store has no keys, so the server refuses the flag with one; a `registered` one takes its keys from the registration, so the server refuses the flag with that too
      --hot-store <URI>
          The fast tier in front of the cold store: `file:///absolute/path`, a directory on an SSD (or a tmpfs). Uploads land there and are flushed to the cold store in the background; reads are served from it while a blob is still there. Its budget is not a flag: 80% of the filesystem's free space less what it keeps free (5% of its size, at least 1 GiB, and never more than half of what is free), at most `--hot-store-max-bytes`; at the budget, writes take the direct path to the cold store. Without it, uploads go straight to the cold store. A worker's outputs (a segment upload) and a ByteStream Write over 16 MiB are written through to it as they arrive, so a large one is never held in memory. Without it, or when it has no room, a blob over 16 MiB (`kbf_front::MAX_UNSTAGED_BLOB_BYTES`) is streamed to the cold store as it arrives (a ByteStream Write), never held whole and never refused for its size. The metadata log lives in `<dir>/meta`, unless `--meta-dir` says otherwise
      --hot-store-max-bytes <BYTES>
          The most bytes the hot store's block files may hold before they are flushed, lower than its automatic budget
      --hot-store-abandon <ID>
          Abandons this server's hot store tier `<id>` at start: every object staged on it is marked unreachable as missing (its blobs answer `Unavailable` until uploaded again; nothing is answered `NOT_FOUND`), and the directory becomes a new tier. For a lost or replaced disk, after a start was refused because the directory's `TIER` file is missing or names another tier. The id is the one the refusal names
      --meta-dir <DIR>
          The directory of the metadata log (the CAS index and the action cache, a single-voter Raft log), on a local disk; created if missing. An empty directory gets a new log with a new id; every later start over it reads the id from the directory. Left out, it is `<hot store directory>/meta`; required when there is no `file://` hot store. Given, it wins over the hot store's directory
      --cold-store-floor-bytes <BYTES>
          For tests only: the free bytes a `file://` cold store's filesystem must keep, in place of 5% of it, at least 1 GiB (a test's disk would decide what is evicted)
      --cold-store-size-bytes <BYTES>
          For tests of eviction only: a `file://` cold store's filesystem is taken to be this many bytes, holding nothing but the store's object files
      --cold-store-evict-grace-ms <COLD_STORE_EVICT_GRACE_MS>
          For tests of eviction only: how long after its last use an object in a `file://` cold store is never evicted, in milliseconds [default: 60000]
      --log-dir <DIR>
          The directory of the durable log file, `kbf-server.log` and its rotated `kbf-server.log.1`, `.2`, ... (created if missing): every event stderr gets, in the same format, kept across restarts. Left out, it is `<hot store directory>/log` when the hot store is a directory; with neither, there is no file and the server logs to stderr alone (the start logs which). A directory or file that cannot be written never stops the server ([`crate::log_file`])
      --log-max-bytes <BYTES>
          The most bytes one log file holds before it is rotated; a line longer than this goes alone to a fresh file. With `--log-files` it bounds the log's size on disk [default: 67108864]
      --log-files <N>
          How many log files are kept, the current one included; rotation drops the oldest. The log never exceeds `--log-max-bytes` times this, plus one line [default: 8]
      --tls-reload-interval-secs <TLS_RELOAD_INTERVAL_SECS>
          How often, in seconds, a TLS listener looks at its certificate, key and client CA files (the `--*-tls-cert`, `--*-tls-key` and `--*-client-ca` flags). A change is applied to the next TLS handshake, with no restart and without ending a connection already open: renew a certificate by replacing the files. Files that do not make a working configuration (unreadable, not PEM, a key that is not the certificate's, an expired certificate, a renewal caught between its two writes) are logged and counted in `kbf_tls_reloads_total{outcome="rejected"}`, and the previous files keep serving; the next look finds them whole and applies them. The files must be good at start [default: 30]
      --async-threads <N>
          Worker threads of the async runtime, which run every task between its waits. Default: every CPU the process may use
      --blocking-threads <N>
          The most threads the runtime's blocking pool runs at once, for calls that wait on a disk or a process (a thread is made when a call needs one and ends when idle). Default: 512 (tokio's)
      --cpu-threads <N>
          Threads for CPU-bound work, such as hashing, which never waits and so is held to the CPUs. Default: every CPU the process may use
      --segment-upload-max-bytes <BYTES>
          The most bytes, records and footers together, one segment upload on the worker listener may hold in memory (`docs/design/write-path.md`, section 4.2): the segments it declares that are not written to the hot store as they arrive (all of them, without one). Not a limit on a blob's size: a segment held in memory holds no record over 16 MiB (`kbf_front::MAX_UNSTAGED_BLOB_BYTES`), and an upload with a larger one and no room on the hot store is answered FAILED_PRECONDITION, so the worker sends its records by ByteStream, which streams a large blob to the cold store. Those ranges are held until the upload commits, admitted under `--write-bytes-in-flight` with every other upload: a `Begin` waits while that is spent. At least 33 MiB (`kbf_front::MIN_SEGMENT_UPLOAD_BYTES`), a worker's upload of small files with room to spare, and at most `--write-bytes-in-flight`, so any legal `Begin` can be admitted; the server refuses to start otherwise. At most `kbf_front::MAX_ADMISSION_BYTES`, the most one admission counts, so a `Begin` never holds more than it is counted for under the bound [default: 34603008]
      --segment-upload-idle-secs <SEGMENT_UPLOAD_IDLE_SECS>
          How long, in seconds, a segment upload may go without a call before it is dropped and its memory returned. An upload is also dropped when the connection that began it closes; one that is committing is kept until its commit ends [default: 60]
      --write-linger <WRITE_LINGER>
          How long, in milliseconds, the oldest blob of an open segment waits for concurrent uploads to join it before the segment is sealed and written (`docs/design/write-path.md`, section 3.1). No caller is answered before its segment has committed, so this is added to an upload's latency at most [default: 2]
      --write-own-segment-bytes <WRITE_OWN_SEGMENT_BYTES>
          Blobs of this many bytes or more are written as a segment of their own, past the group, so they neither wait for the linger nor hold up small writes [default: 16777216]
      --write-bytes-in-flight <WRITE_BYTES_IN_FLIGHT>
          The most bytes uploads may hold at once. A ByteStream Write is admitted before it reads past its first message, for its blob's size up to 16 MiB (`kbf_front::MAX_UNSTAGED_BLOB_BYTES`) and for 16 MiB above that (a larger blob is streamed onto the hot store, or to the cold store without room there, not held); a BatchUpdateBlobs for its total; a segment upload's Begin for what it holds in memory. A caller over the bound waits, nothing is refused for load. At least `--segment-upload-max-bytes` (by default 33 MiB, under the default 2 GiB). Not covered: each HTTP/2 stream's message as tonic decodes it, before the handler runs, up to 17 MiB per stream (about 3.4 GiB for 200 streams), times the streams one connection may open on each listener [default: 2147483648]
      --write-puts-in-flight <WRITE_PUTS_IN_FLIGHT>
          The most segment PUTs, each with its footer read-back, in flight at once. A segment sealed while all are busy waits; new blobs go to a new open segment [default: 4]
      --write-pool-writers <WRITE_POOL_WRITERS>
          The writers of the write pool: the ByteStream and storage `Write`s of a node with a write tier are appended to shared segment files by this many writers, each holding one range open, so the node keeps at most this many block files (plus the open grouped block) open for writing for those blobs, however many uploads are in flight. At least 1 [default: 8]
      --write-pool-queue <WRITE_POOL_QUEUE>
          The most blobs waiting for a write-pool writer. A blob that finds the queue full goes straight to the object store, as one does when the write tier has no room. At least 1 [default: 4096]
      --write-pool-stream-idle <WRITE_POOL_STREAM_IDLE>
          How long, in seconds, a streamed blob may go without sending a chunk before its write-pool writer is taken back and the upload fails UNAVAILABLE (the client sends it again). Without it, a stalled but connected large upload would hold a writer for ever, and with all writers held every other blob would wait. It limits stalls only: an upload that sends a chunk more often than this (a trickle) can still hold a writer. At least 1 [default: 30]
      --durable-wait <DURABLE_WAIT>
          How long, in seconds, a storage node waits for blobs it holds in RAM to be written to its disk when a caller asks for a durable answer that waits (`kbf-durable: wait`): an action-cache entry is committed only once every blob it names is on an owner's disk, and the writer of the entry asks each owner with this wait; the action's owner waits the same for its own copies. A blob still in RAM when it ends is reported missing and the write fails UNAVAILABLE, for the caller to try again. Nothing holds a blob in RAM yet, so no call waits. At least 1, and under half of the 120 seconds a chain's replica may take to commit a blob (`kbf_storage::replicate::ChainConfig`): a start with more is refused [default: 10]
      --ram-peer-grace <RAM_PEER_GRACE>
          How long, in seconds, after its own write of a blob it acknowledged from RAM a storage node waits before it asks the blob's other owner whether the blob is on its disk too, and journals a repair debt if it is not. Long enough that the usual answer is yes and nothing is journalled. Only a node that acknowledges from RAM (`--ram-ack-bytes`) asks. At least 1 [default: 5]
      --ram-ack-bytes <RAM_ACK_BYTES>
          How many bytes of blobs a storage node may hold in RAM, acknowledged to the writer and not yet written to its disk. 0, the default, is off: a write is acknowledged from disk, as before. Over 0, a blob of at most 4 MiB written to two owners is acknowledged once both hold it verified in RAM, and written to each disk afterwards: losing both owners' RAM before then loses the blob. A blob that finds the budget full is written through to the disk before it is acknowledged, never waited for. Set it on every storage node or none. A node that does hold blobs counts them in `kbf_storage_ram_unwritten_bytes`, writes them to its disk in the background and, when it stops, within `--ram-drain-deadline`. A node can hold this many bytes beside the `--write-bytes-in-flight` it receives. Storage nodes only: a server with no replica to hold a second copy holds nothing [default: 0]
      --ram-drain-deadline <RAM_DRAIN_DEADLINE>
          How long, in seconds, a storage node that is stopping waits, after its calls have ended, for the blobs it holds in RAM to be written to its disk (`--ram-ack-bytes`) and then for the blocks staged on its hot store to be flushed to the cold store: one bound for both. The blobs left in RAM when it ends are lost to the stop; the blocks left on the hot store are on its disk, flushed by the next start. Both are counted in the log. At least 1 [default: 30]
      --store-put-attempts <STORE_PUT_ATTEMPTS>
          How many times a segment PUT is tried. Only a PUT that did not complete (connect, reset, timeout) or that the store answered 5xx is tried again, after 100 ms and then four times longer each time, under a new object key; if every attempt fails, the segment's blobs are answered UNAVAILABLE [default: 3]
      --storage-listen <ADDR>
          Where the node serves gRPC. Without the TLS flags it serves plain text, and the address must be loopback. [default: 127.0.0.1:8982]
      --metrics-listen <ADDR>
          Serves GET /metrics (Prometheus text) over plain HTTP here. Off unless given. Reads are open to whoever reaches it: bind it where only operators do.
      --storage-tls-cert <PATH>
          The node's server certificate (PEM).
      --storage-tls-key <PATH>
          The server certificate's private key (PEM).
      --frontend <URL>
          Registers with this frontend (http:// or https://) and heartbeats to it. Without it the node is a one-member map of itself.
      --advertise-addr <HOST:PORT>
          The address callers dial, where --storage-listen is not routable. Default: the address the node bound.
      --storage-zone <LABEL>
          The zone label to register with. Default: none.
      --storage-weight <N>
          The node's share of the digests relative to the others. Default: 1.
      --storage-client-ca <PATH>
          The CA callers' certificates chain to; each must name a role (frontend, storage, daemon).
      --config <FILE>
          Read the mode's settings from this TOML file (default /etc/kbf/kbf.toml when it exists); a flag on the command line overrides its key
      --check
          Parse the flags and the file, run the startup checks, print each problem and exit (0 fine, 2 refused, 75 not ready) without starting
  -h, --help
          Print help
