The storage node and a worker daemon in one process, the daemon reading and writing the node's storage in-process (Linux, the container driver only).

Usage: kbf --mode=storage-and-daemon [OPTIONS] --server <SERVERS> --ca-cert <CA_CERT> --cert <CERT> --key <KEY> --node-id <NODE_ID> --driver <DRIVERS>

Options:
      --server <SERVERS>
          A kbf-server worker listener to connect to, as an `https://host:port` URL; repeatable, or several separated by commas. The host may be a DNS name with a record per server: every round of attempts resolves it again and tries each address. The daemon never stops trying (see `--reconnect-max-ms`)

      --ca-cert <CA_CERT>
          PEM file of the CA certificates that sign server certificates

      --cert <CERT>
          PEM file of this daemon's client certificate chain

      --key <KEY>
          PEM file of this daemon's private key

      --tls-server-name <TLS_SERVER_NAME>
          The name to verify in the server certificate, when it is not the URL's host

      --node-id <NODE_ID>
          A stable name for this node, unique within the cell

      --reconnect-ms <RECONNECT_MS>
          The wait, in milliseconds, after a session ends and after the first round of connection attempts that all failed. It doubles with each further failed round
          
          [default: 1000]

      --reconnect-max-ms <RECONNECT_MAX_MS>
          The longest wait between rounds of connection attempts, in milliseconds. Each wait is jittered down by up to half
          
          [default: 30000]

      --storage-dial-timeout-ms <STORAGE_DIAL_TIMEOUT_MS>
          The longest, in milliseconds, that dialling a storage node may take: for its TCP connection and for its TLS handshake each. Must be 1 to 3600000 (one hour)
          
          [default: 10000]

      --storage-ping-interval-ms <STORAGE_PING_INTERVAL_MS>
          How often, in milliseconds, a connection to a storage node with a call on it is pinged (HTTP/2 PING). Must be 1 to 3600000 (one hour)
          
          [default: 10000]

      --storage-ping-timeout-ms <STORAGE_PING_TIMEOUT_MS>
          How long, in milliseconds, a ping to a storage node may go unanswered before the connection is dropped and the calls on it fail over to the next owner. Must be 1 to 3600000 (one hour) and no more than `--storage-ping-interval-ms`
          
          [default: 10000]

      --driver <DRIVERS>
          How leases run; once per runtime. The daemon runs each lease on the driver that serves its kind and refuses to start when two serve the same kind. The node's own driver (native or container) is set up first, whatever the order given

          Possible values:
          - fake:                 Runs nothing; every action succeeds with an empty result. For bring-up only
          - container:            Each action in a fresh rootless container made by `crun` (Linux)
          - native:               Each action as plain processes on the node, for Macs
          - native-whole-machine: Each whole-machine lease as its own user in its GUI session, through `kbf-mac-session` (macOS)

      --cas <CAS>
          The server's worker listener, an `https://` URL (normally `--server`'s), that the container and native drivers read and write blobs through, over mutual TLS with this daemon's `--ca-cert`, `--cert`, `--key` and `--tls-server-name`. Plain `http://` is refused: the worker listener admits each blob call by the daemon's certificate. Every driver's blobs go through one transfer engine, over one connection, within the `--transfer-*` limits

      --data-dir <DIR>
          The directory the daemon keeps everything in, on a local disk: `leases/` (lease directories, the container and native drivers), and under the container driver (and the native driver on macOS) `cache/` (the input cache, `docs/design/worker-cache.md`) and `trees/` (shared read-only input trees, `docs/design/fast-sandbox.md#4-shared-trees`). Made if missing; absolute. The cache and trees are on (unless `--no-input-cache`), sized from the filesystem: half and a quarter of its size less what it keeps free (5%, at least 1 GiB), and the cache evicts entries no running lease links to keep that much free. A directory another daemon owns, or that cannot be used, is left alone: the daemon warns and runs uncached.
          
          Default `/var/lib/kbf`. A daemon with the fake driver alone touches no directory unless this is given.

      --data-max-bytes <BYTES>
          Lowers the size the cache and the trees are budgeted from (half and a quarter of it), under the filesystem's automatic one

      --no-input-cache
          Switches the host input cache off: no `cache/` and no `trees/`, so every action fetches its inputs from the CAS into its own input root and no later action reuses them (no hard link or clone from either). Leaves what an earlier start put in `<data-dir>/cache` and `<data-dir>/trees` alone. Without a cache a lease reports no input statistics (`cache_hits` and the rest exist only with a cache). For measuring what the cache saves

      --output-max-depth <MAX_DEPTH>
          The deepest directory an output directory may hold, in levels below it (its own entries are level 1)
          
          [default: 512]

      --output-max-entries <MAX_ENTRIES>
          The most entries (files, directories, symlinks and anything else) one action's outputs may hold together, the declared outputs included
          
          [default: 1000000]

      --output-max-bytes <MAX_BYTES>
          The most bytes one action's output files may hold together
          
          [default: 17179869184]

      --output-max-stdio-bytes <MAX_STDIO_BYTES>
          The most bytes each of the action's stdout and stderr may hold
          
          [default: 1073741824]

      --reserve-cpus <N>
          Logical CPUs the farm's own processes keep, in CPUs (hyperthreads count one each). The daemon gives its leases every CPU it may use but these, with no pinning, and sizes its own pools from them. Default: 4 physical cores with their hyperthreads, so 8 where two threads share a core and 4 where each core has one (half the CPUs on a smaller machine). 0 is allowed; a value that leaves no CPU for leases, or is more than the machine has, is refused. On a host that also runs the server, this covers both; the server has no reserve flag

      --reserve-share <N>
          How many of the farm's processes on this host share the reserve: the daemon sizes its pools from `reserve / share` CPUs. Default 1

      --async-threads <N>
          Worker threads of the async runtime, which run every task between its waits. Default: every CPU the process may use on the server; `max(2, reserve/4)`, at most the physical cores, on the daemon

      --blocking-threads <N>
          The most threads the runtime's blocking pool runs at once, for calls that wait on a disk or a process (a thread is made when a call needs one and ends when idle). Default: 512 (tokio's) for the server, 64 for the daemon

      --cpu-threads <N>
          Threads for CPU-bound work, such as hashing, which never waits and so is held to the CPUs. Default: every CPU the process may use on the server; `max(2, reserve/2)`, at most the physical cores, on the daemon

      --output-upload-deadline-secs <OUTPUT_UPLOAD_DEADLINE_SECS>
          How long one lease's whole output upload (its output files, stdout and stderr) may take, in seconds, before the lease fails with a reason naming the upload and the time it ran (container and native drivers). Without it, a store that stops answering holds the lease, and its slot, with no error
          
          [default: 1800]

      --transfer-in-flight <TRANSFER_IN_FLIGHT>
          The most blob requests in flight at once, for the whole daemon: ByteStream reads and writes, segment ranges and FindMissing calls, over its one connection to `--cas`. Uploads hold at most all but a quarter of them
          
          [default: 64]

      --transfer-bytes-in-flight <BYTES>
          The most bytes of blobs read into memory in flight at once, for the whole daemon. A blob larger than this is fetched alone
          
          [default: 268435456]

      --transfer-memory-blob-bytes <BYTES>
          The largest input file fetched through memory, where every lease asking for it at once shares one fetch; a larger one is streamed into its file
          
          [default: 1048576]

      --transfer-chunk-bytes <BYTES>
          The most bytes one ByteStream write message carries
          
          [default: 1048576]

      --transfer-find-missing-chunk <TRANSFER_FIND_MISSING_CHUNK>
          The most digests one FindMissing call asks about
          
          [default: 1000]

      --transfer-stream-window-bytes <BYTES>
          The HTTP/2 window of each stream to `--cas`; the connection's is eight times it
          
          [default: 8388608]

      --transfer-retries <TRANSFER_RETRIES>
          How many times a blob request is retried after UNAVAILABLE or a broken connection
          
          [default: 3]

      --segment-upload-streams <SEGMENT_UPLOAD_STREAMS>
          How many `PutRange` calls one segment upload of an action's outputs has in flight at once, as HTTP/2 streams on the one connection to `--cas` (`docs/design/write-path.md`, section 4.1); also the parallel `ReadRange` calls of a segment-range read
          
          [default: 16]

      --segment-uploads-in-flight <SEGMENT_UPLOADS_IN_FLIGHT>
          How many segment uploads of one action's outputs are in flight at once: the server checks and stages one upload while the next are sending (`docs/design/write-path.md`, section 4.1). Their `PutRange` calls still take permits of `--transfer-in-flight`'s uploads' share
          
          [default: 4]

      --pack-read
          Reads the blobs of a lease from the packs of the farm's object store before the storage nodes: the daemon asks the frontend where a blob lies (over the connection to `--cas`; for `kbf storage-and-daemon`, which has none, over one to the first `--server`), reads that range of that pack and checks it against the digest. A blob the frontend does not locate, and a frontend that serves no locations (it was started without `--pack-index`), leave the read where it was, and outputs are stored where they were. A pack that is gone, or whose bytes are not the digest, fails the read. Needs `--pack-store-endpoint`, `--pack-store-bucket` and `--pack-store-credentials-file`. Refused by `kbf all-in-one` and by `kbf storage-and-daemon` started without `--frontend`, whose daemon half reads blobs in-process. Left out, no object store is built or contacted and every blob is read as it always was

      --pack-store-endpoint <URL>
          The S3-compatible object store the packs are kept in, as `http://host:port`. The daemon reads packs from it, and with `--pack-write` writes them. Needs `--pack-read`

      --pack-store-bucket <BUCKET>
          The bucket of `--pack-store-endpoint` that holds the packs, under the keys `cas/`. Needs `--pack-read`

      --pack-store-region <REGION>
          The region the requests to `--pack-store-endpoint` are signed for; `us-east-1` if left out

      --pack-store-credentials-file <PATH>
          A file with the key pair for `--pack-store-endpoint`, as JSON `{"access_key_id": "...", "secret_access_key": "..."}`, readable by its owner alone (mode 0600 or 0400): a key that may read the objects under `cas/` and write none (`--pack-write` has a key of its own). The secret is never a flag: a command line is world-readable. Needs `--pack-read`

      --pack-read-cache-dir <DIR>
          A directory this process owns where the blobs read from packs are kept, one file each, checked by digest on every read; the least recently used are removed to stay within `--pack-read-cache-bytes`. The daemon's input cache already keeps blobs by digest, so left out nothing more is kept. Needs `--pack-read-cache-bytes`

      --pack-read-cache-bytes <BYTES>
          The most bytes of blobs `--pack-read-cache-dir` holds

      --pack-write
          Writes the outputs of a lease into packs: many blobs in one object of the pack store, written with a create-only request, then committed to the frontend (`CommitPack`), which records them before the put is acknowledged. Used only while the frontend says it takes commits (it has `--pack-index` and the pack store flags); a blob that cannot be packed is stored where it was. At start the daemon checks that the store refuses to replace an object, and refuses to start if it does not. Needs `--pack-read` and `--pack-store-write-credentials-file`. Left out, outputs are stored as they always were

      --pack-store-write-credentials-file <PATH>
          A file with the key pair `--pack-write` writes with, in the form of `--pack-store-credentials-file`: a key that may create objects under `cas/` (it also deletes the one it creates to check the store at start, and if it may not, that object is left for garbage collection). The secret is never a flag. Needs `--pack-write`

      --cgroup-parent <CGROUP_PARENT>
          The cgroup lease cgroups are made under, from the cgroup root (container). Left out, the daemon sets up its own cgroup, which its systemd unit must delegate (`Delegate=yes`): it moves itself into a `supervisor` leaf there and makes `actions` beside it, with cpu, memory and pids enabled. Given, it must already enable cpu, memory and pids for its children

      --actions-memory-max-gib <ACTIONS_MEMORY_MAX_GIB>
          Written to the actions cgroup's `memory.max` at start (container): the most memory all leases together may use, in GiB, so the rest stays for what else runs on the node. The node reports the lowest `memory.max` above its leases, or its memory when that is less, and the CPUs of their cpuset

      --actions-cpu-max <auto|on|off>
          Whether the actions cgroup's `cpu.max` is lifted (container). At start it holds the leases' CPUs, the node's minus `--reserve-cpus`; the server's Welcome then says, on every connect and reconnect, whether the farm places by the load the nodes measure (`Welcome.placement_load`), which a CPU limit would hide (a cgroup throttled at its limit never measures more than it). `auto` follows the Welcome: `cpu.max` is `max` when it says so, and the leases' CPUs when it says otherwise or nothing; `on` lifts the limit and `off` keeps it, whatever the Welcome says. Until the first Welcome the limit of the start stays. The heartbeat reports what was written (`NodeLoad.actions_cpu_limited`). Refused with a driver other than `container`

          Possible values:
          - auto: Follow the Welcome
          - on:   No limit
          - off:  The reserve's limit
          
          [default: auto]

      --supervisor-memory-min-mib <SUPERVISOR_MEMORY_MIN_MIB>
          Written to the daemon's `supervisor` leaf's `memory.min` at start, in MiB (container, without `--cgroup-parent`): memory the kernel does not reclaim from the daemon while it uses no more, so builds short of memory never take it. The kernel protects no more than the unit's and its slice's `MemoryMin=` allow; the daemon warns when one is lower. 0 protects nothing
          
          [default: 256]

      --container-pids-limit <CONTAINER_PIDS_LIMIT>
          Each container's `pids.max`: its tasks, threads included (container)
          
          [default: 8192]

      --container-shm-mib <CONTAINER_SHM_MIB>
          The size of each container's `/dev/shm`, in MiB (container)
          
          [default: 64]

      --container-nofile <CONTAINER_NOFILE>
          Each container's open-file limit, soft and hard (container). Rootless, it cannot exceed the daemon's own hard limit
          
          [default: 65536]

      --container-nproc <CONTAINER_NPROC>
          The process limit, soft and hard, of each container's user (container). Every container's root is the same host id, so it bounds all the node's actions together
          
          [default: 32768]

      --lease-swap-kill-mib <LEASE_SWAP_KILL_MIB>
          A lease at its own memory cap is killed, and reported out of memory, once it has pushed more than this many MiB into swap at its cap... (container)
          
          [default: 512]

      --lease-swap-kill-percent <LEASE_SWAP_KILL_PERCENT>
          ...or this percentage of its booked memory, whichever is more. The kernel caps each lease's RAM at its booking x 1.5 + 512 MiB and lets it swap without limit; a lease is killed by this rule only while its own cap keeps being hit (its `memory.events` `max` grew since the last sample) and its swap rose since the last sample, and only swap that rose so counts, never swap that host pressure moved out of it
          
          [default: 25]

      --memory-pressure-pause-percent <MEMORY_PRESSURE_PAUSE_PERCENT>
          The daemon takes no new lease while the node's memory stall time (the `some` line's `avg10` in `/proc/pressure/memory`, as a percentage) is above this and it runs a lease: it says so to the server, which places nothing on it until the stall falls, and the leases it runs go on. With no lease it serves whatever the stall, so it is never left idle for good. Off where the kernel reports no pressure stall information (macOS, a kernel built without it)
          
          [default: 10]

      --drain-deadline-secs <SECONDS>
          On the first SIGTERM or SIGINT the daemon drains: it takes no new lease, lets the running ones finish and report, waits for their acknowledgements, then exits 0, however long that takes. A second signal stops it at once and abandons the leases still running. Left out, the drain has no deadline. Given, this many seconds after the first signal the daemon logs a warning with the number of leases still running and keeps waiting; the value has no upper bound, and 0 warns at once. It never abandons a lease. Used by `kbf daemon`, `kbf storage-and-daemon` and `kbf all-in-one`, whose daemon half drains once its server half has no execution open, while the server half goes on serving it; a second signal stops both

      --lease-swap-poll-ms <LEASE_SWAP_POLL_MS>
          How often each lease's `max` events and swap are sampled, in milliseconds (container)
          
          [default: 1000]

      --memory-limit-percent <MEMORY_LIMIT_PERCENT>
          A lease's processes are killed past this percentage of its booked memory...
          
          [default: 150]

      --memory-headroom-mib <MEMORY_HEADROOM_MIB>
          ...plus this many MiB (native). A lease that booked nothing has no limit
          
          [default: 512]

      --memory-poll-ms <MEMORY_POLL_MS>
          How often a lease's memory is measured, in milliseconds (native)
          
          [default: 250]

      --native-term-grace-ms <NATIVE_TERM_GRACE_MS>
          How long a lease's processes are given to end after SIGTERM before they are killed, in milliseconds; 0 kills them at once (native). A workload that cleans up when asked to end, such as Python's multiprocessing resource tracker with the shared memory it made, does so in this time; one that ignores SIGTERM is named in the lease's stderr. A slot's clean uses the same value (at most its own time limit). More than 60000 is taken as 60000. The wait comes after the action's timeout and its memory watch have ended it (neither runs during it), and on top of the time given to the kill that follows. A lease past its memory limit is killed at once. Applies on every platform
          
          [default: 2000]

      --xcode-apps <XCODE_APPS>
          The directory searched for `Xcode*.app` (native). Each Xcode whose own `xcodebuild` answers `-version`, `-license check` and `-checkFirstLaunchStatus`, and for which `xcrun --find clang` does (each within a minute, under the actions' sandbox), is ready: it is reported as an `xcode` entry, and an action that names its build runs with it as `DEVELOPER_DIR`. One that is not is listed in the node's status with why and the command that fixes it, and logged at WARN. The daemon says Hello without waiting for its first survey, which runs in the background: until it ends, each Xcode is listed as not surveyed yet and none is reported
          
          [default: /Applications]

      --xcode-recheck-secs <XCODE_RECHECK_SECS>
          How often, in seconds, the Xcodes are asked again (native), so one fixed while the daemon runs becomes ready without a restart
          
          [default: 180]

      --require-metal-toolchain
          This node's actions use Metal (native): an Xcode whose Metal toolchain is not installed (`xcodebuild -showComponent MetalToolchain`) is not ready

      --image <IMAGE>
          A container image this node is pinned to, as an action names it: `docker://<repo>@sha256:<digest>`, one architecture's manifest digest (container; repeatable). At start the daemon makes sure each is in the node's image store, as the prepare step of every lease does: it fetches the image from its registry by that digest, checks every byte against a digest, and unpacks it once. It exits with status 2 if one cannot be fetched, fails a check, or names an image index. The node's status lists them (`GET /v1/nodes`, `software.container_images`). No work is placed by image yet: an action may still name another image

      --lease-placement <none|numa-node>
          Where each lease runs among the node's CPUs (container, Linux): `none`, the default, lets a lease use any CPU the daemon may; `numa-node` puts each lease on one NUMA node, its CPUs (`cpuset.cpus`) and memory (`cpuset.mems`), the node with the least CPU booked by running leases (the lowest id on a tie). `--reserve-cpus` is a quota on all leases together, so it still applies; it removes no CPU from a node. Needs the `cpuset` controller delegated to the daemon (the start fails and says how when it is not); a host with fewer than two NUMA nodes that hold CPUs runs as `none`, which the start logs. Refused with a driver other than `container` (macOS has no such driver)
          
          [default: none]
          [possible values: none, numa-node]

      --oci-runtime <OCI_RUNTIME>
          The OCI runtime that runs each action's container (container): `crun`, run directly. Each action gets a fresh rootless sandbox. It needs the daemon user's subordinate ids in one range, `newuidmap` and `newgidmap` (package `uidmap`) on `PATH`, and every directory down to `--data-dir` searchable by others
          
          [default: /usr/bin/crun]

      --mac-session-socket <MAC_SESSION_SOCKET>
          The socket `kbf-mac-session` serves (native-whole-machine)
          
          [default: /var/run/kbf-mac-session/socket]

      --daemon-user <DAEMON_USER>
          This daemon's own user, which keeps read and remove access to what a whole-machine lease's user writes in its lease directory (native-whole-machine)
          
          [default: _kbf]

      --pool-users <POOL_USERS>
          How many lease users the pool has (native, macOS, a daemon run as root): every action runs as one of `kbf-pool-0` .. `kbf-pool-<N-1>`, one lease per user at a time, as kbf-mac-provision makes them (`pool_users`). Required of a root daemon, which runs no action as root; refused for any other

      --pool-first-uid <POOL_FIRST_UID>
          The uid of `kbf-pool-0`, and the group id of all the pool users (`pool_first_uid` in kbf-mac-provision's profile); at least 600

      --config <FILE>
          Read the mode's settings from this TOML file (default /etc/kbf/kbf.toml when it exists); a flag on the command line overrides its key

      --check
          Parse the flags and the file, run the startup checks, print each problem and exit (0 fine, 2 refused, 75 not ready) without starting

  -h, --help
          Print help (see a summary with '-h')

  -V, --version
          Print version

      --cold-store <URI>
          The durable object store, where every blob ends up: `file:///absolute/path` (a directory, `kbf_objstore::FsStore`: locked while the server runs, a second server on it is refused; a write that would leave its filesystem with less free than it keeps, 5% of its size and at least 1 GiB, is refused and wakes the evictor, which forgets the least recently used objects (never one used in the last minute) and deletes their files while less than twice that is free) or `s3://bucket/prefix?endpoint=http://host:port` (MinIO, RustFS; the key pair is `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`; query keys `region`, `conditional-put=true` for a store that refuses to overwrite a key, and `min-put-rate=BYTES_PER_SEC`, the slowest rate a PUT body may reach the store at: a PUT is cut after 60 seconds plus its body's length at that rate, 1 MiB/s by default). Objects are keyed under `<prefix><log id>/` (`kbf/` for a directory and for an S3 URI without a path), the id of the metadata log. A directory is checked against the index by a start-up pass in the background; a lost or damaged object is also found when it is read, or before an action-cache hit that needs it is served (a miss). There is no `memory:` store: a `file://` path on a tmpfs is one

      --cold-store-credentials-file <PATH>
          The key pair of an `s3://` `--cold-store`, in a file: JSON `{"access_key_id": "...", "secret_access_key": "..."}`, a regular file (a symbolic link is refused) that the server's user owns and no one else can read (mode 0600 or 0400). The secret is never a flag: a command line is world-readable. Without it the key pair is read from `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, which is deprecated: the start logs one warning and a later release refuses the variables. A `file://` cold store has no keys, so the server refuses the flag with one

      --hot-store <URI>
          The fast tier in front of the cold store: `file:///absolute/path`, a directory on an SSD (or a tmpfs). Uploads land there and are flushed to the cold store in the background; reads are served from it while a blob is still there. Its budget is not a flag: 80% of the filesystem's free space less what it keeps free (5% of its size, at least 1 GiB, and never more than half of what is free), at most `--hot-store-max-bytes`; at the budget, writes take the direct path to the cold store. Without it, uploads go straight to the cold store. A daemon's outputs (a segment upload, or the in-process plane) and a ByteStream Write over 16 MiB are written through to it as they arrive, so a large one is never held in memory. Without it, or when it has no room, a daemon's blob over 16 MiB (`kbf_front::MAX_UNSTAGED_BLOB_BYTES`) is streamed to the cold store as it arrives (a ByteStream Write, or the in-process plane's own stream), never held whole and never refused for its size. The metadata log lives in `<dir>/meta`, unless `--meta-dir` says otherwise

      --hot-store-max-bytes <BYTES>
          The most bytes the hot store's block files may hold before they are flushed, lower than its automatic budget

      --hot-store-abandon <ID>
          Abandons this server's hot store tier `<id>` at start: every object staged on it is marked unreachable as missing (its blobs answer `Unavailable` until uploaded again; nothing is answered `NOT_FOUND`), and the directory becomes a new tier. For a lost or replaced disk, after a start was refused because the directory's `TIER` file is missing or names another tier. The id is the one the refusal names

      --meta-dir <DIR>
          The directory of the metadata log (the CAS index and the action cache, a single-voter Raft log), on a local disk; created if missing. An empty directory gets a new log with a new id; every later start over it reads the id from the directory. Left out, it is `<hot store directory>/meta`; required when there is no `file://` hot store. Given, it wins over the hot store's directory

      --cold-store-floor-bytes <BYTES>
          For tests only: the free bytes a `file://` cold store's filesystem must keep, in place of 5% of it, at least 1 GiB (a test's disk would decide what is evicted)

      --cold-store-size-bytes <BYTES>
          For tests of eviction only: a `file://` cold store's filesystem is taken to be this many bytes, holding nothing but the store's object files

      --cold-store-evict-grace-ms <COLD_STORE_EVICT_GRACE_MS>
          For tests of eviction only: how long after its last use an object in a `file://` cold store is never evicted, in milliseconds
          
          [default: 60000]

      --log-dir <DIR>
          The directory of the durable log file, `kbf-server.log` and its rotated `kbf-server.log.1`, `.2`, ... (created if missing): every event stderr gets, in the same format, kept across restarts. Left out, it is `<hot store directory>/log` when the hot store is a directory; with neither, there is no file and the server logs to stderr alone (the start logs which). A directory or file that cannot be written never stops the server ([`crate::log_file`])

      --log-max-bytes <BYTES>
          The most bytes one log file holds before it is rotated; a line longer than this goes alone to a fresh file. With `--log-files` it bounds the log's size on disk
          
          [default: 67108864]

      --log-files <N>
          How many log files are kept, the current one included; rotation drops the oldest. The log never exceeds `--log-max-bytes` times this, plus one line
          
          [default: 8]

      --tls-reload-interval-secs <TLS_RELOAD_INTERVAL_SECS>
          How often, in seconds, a TLS listener looks at its certificate, key and client CA files (the `--*-tls-cert`, `--*-tls-key` and `--*-client-ca` flags). A change is applied to the next TLS handshake, with no restart and without ending a connection already open: renew a certificate by replacing the files. Files that do not make a working configuration (unreadable, not PEM, a key that is not the certificate's, an expired certificate, a renewal caught between its two writes) are logged and counted in `kbf_tls_reloads_total{outcome="rejected"}`, and the previous files keep serving; the next look finds them whole and applies them. The files must be good at start
          
          [default: 30]

      --segment-upload-max-bytes <BYTES>
          The most bytes, records and footers together, one segment upload on the worker listener may hold in memory (`docs/design/write-path.md`, section 4.2): the segments it declares that are not written to the hot store as they arrive (all of them, without one). Not a limit on a blob's size: a segment held in memory holds no record over 16 MiB (`kbf_front::MAX_UNSTAGED_BLOB_BYTES`), and an upload with a larger one and no room on the hot store is answered FAILED_PRECONDITION, so the daemon sends its records by ByteStream, which streams a large blob to the cold store. Those ranges are held until the upload commits, admitted under `--write-bytes-in-flight` with every other upload: a `Begin` waits while that is spent. At least 33 MiB (`kbf_front::MIN_SEGMENT_UPLOAD_BYTES`), a daemon's upload of small files with room to spare, and at most `--write-bytes-in-flight`, so any legal `Begin` can be admitted; the server refuses to start otherwise. At most `kbf_front::MAX_ADMISSION_BYTES`, the most one admission counts, so a `Begin` never holds more than it is counted for under the bound
          
          [default: 34603008]

      --segment-upload-idle-secs <SEGMENT_UPLOAD_IDLE_SECS>
          How long, in seconds, a segment upload may go without a call before it is dropped and its memory returned. An upload is also dropped when the connection that began it closes; one that is committing is kept until its commit ends
          
          [default: 60]

      --write-linger <WRITE_LINGER>
          How long, in milliseconds, the oldest blob of an open segment waits for concurrent uploads to join it before the segment is sealed and written (`docs/design/write-path.md`, section 3.1). No caller is answered before its segment has committed, so this is added to an upload's latency at most
          
          [default: 2]

      --write-own-segment-bytes <WRITE_OWN_SEGMENT_BYTES>
          Blobs of this many bytes or more are written as a segment of their own, past the group, so they neither wait for the linger nor hold up small writes
          
          [default: 16777216]

      --write-bytes-in-flight <WRITE_BYTES_IN_FLIGHT>
          The most bytes uploads may hold at once. A ByteStream Write is admitted before it reads past its first message, for its blob's size up to 16 MiB (`kbf_front::MAX_UNSTAGED_BLOB_BYTES`) and for 16 MiB above that (a larger blob is streamed onto the hot store, or to the cold store without room there, not held); a BatchUpdateBlobs for its total; a segment upload's Begin for what it holds in memory. A caller over the bound waits, nothing is refused for load. At least `--segment-upload-max-bytes` (by default 33 MiB, under the default 2 GiB). Not covered: each HTTP/2 stream's message as tonic decodes it, before the handler runs, up to 17 MiB per stream (about 3.4 GiB for 200 streams), times the streams one connection may open on each listener
          
          [default: 2147483648]

      --write-puts-in-flight <WRITE_PUTS_IN_FLIGHT>
          The most segment PUTs, each with its footer read-back, in flight at once. A segment sealed while all are busy waits; new blobs go to a new open segment
          
          [default: 4]

      --write-pool-writers <WRITE_POOL_WRITERS>
          The writers of the write pool: the ByteStream and storage `Write`s of a node with a write tier are appended to shared segment files by this many writers, each holding one range open, so the node keeps at most this many block files (plus the open grouped block) open for writing for those blobs, however many uploads are in flight. At least 1
          
          [default: 8]

      --write-pool-queue <WRITE_POOL_QUEUE>
          The most blobs waiting for a write-pool writer. A blob that finds the queue full goes straight to the object store, as one does when the write tier has no room. At least 1
          
          [default: 4096]

      --write-pool-stream-idle <WRITE_POOL_STREAM_IDLE>
          How long, in seconds, a streamed blob may go without sending a chunk before its write-pool writer is taken back and the upload fails UNAVAILABLE (the client sends it again). Without it, a stalled but connected large upload would hold a writer for ever, and with all writers held every other blob would wait. It limits stalls only: an upload that sends a chunk more often than this (a trickle) can still hold a writer. At least 1
          
          [default: 30]

      --durable-wait <DURABLE_WAIT>
          How long, in seconds, a storage node waits for blobs it holds in RAM to be written to its disk when a caller asks for a durable answer that waits (`kbf-durable: wait`): an action-cache entry is committed only once every blob it names is on an owner's disk, and the writer of the entry asks each owner with this wait; the action's owner waits the same for its own copies. A blob still in RAM when it ends is reported missing and the write fails UNAVAILABLE, for the caller to try again. Nothing holds a blob in RAM yet, so no call waits. At least 1, and under half of the 120 seconds a chain's replica may take to commit a blob (`kbf_storage::replicate::ChainConfig`): a start with more is refused
          
          [default: 10]

      --ram-peer-grace <RAM_PEER_GRACE>
          How long, in seconds, after its own write of a blob it acknowledged from RAM a storage node waits before it asks the blob's other owner whether the blob is on its disk too, and journals a repair debt if it is not. Long enough that the usual answer is yes and nothing is journalled. Only a node that acknowledges from RAM (`--ram-ack-bytes`) asks. At least 1
          
          [default: 5]

      --ram-ack-bytes <RAM_ACK_BYTES>
          How many bytes of blobs a storage node may hold in RAM, acknowledged to the writer and not yet written to its disk. 0, the default, is off: a write is acknowledged from disk, as before. Over 0, a blob of at most 4 MiB written to two owners is acknowledged once both hold it verified in RAM, and written to each disk afterwards: losing both owners' RAM before then loses the blob. A blob that finds the budget full is written through to the disk before it is acknowledged, never waited for. Set it on every storage node or none. A node that does hold blobs counts them in `kbf_storage_ram_unwritten_bytes`, writes them to its disk in the background and, when it stops, within `--ram-drain-deadline`. A node can hold this many bytes beside the `--write-bytes-in-flight` it receives. Storage nodes only: a server with no replica to hold a second copy holds nothing
          
          [default: 0]

      --ram-drain-deadline <RAM_DRAIN_DEADLINE>
          How long, in seconds, a storage node that is stopping waits, after its calls have ended, for the blobs it holds in RAM to be written to its disk (`--ram-ack-bytes`) and then for the blocks staged on its hot store to be flushed to the cold store: one bound for both. The blobs left in RAM when it ends are lost to the stop; the blocks left on the hot store are on its disk, flushed by the next start. Both are counted in the log. At least 1
          
          [default: 30]

      --store-put-attempts <STORE_PUT_ATTEMPTS>
          How many times a segment PUT is tried. Only a PUT that did not complete (connect, reset, timeout) or that the store answered 5xx is tried again, after 100 ms and then four times longer each time, under a new object key; if every attempt fails, the segment's blobs are answered UNAVAILABLE
          
          [default: 3]

      --storage-listen <ADDR>
          Where the node serves gRPC. Without the TLS flags it serves plain text, and the address must be loopback.
          
          [default: 127.0.0.1:8982]

      --metrics-listen <ADDR>
          Serves GET /metrics (Prometheus text) over plain HTTP here. Off unless given. Reads are open to whoever reaches it: bind it where only operators do.

      --storage-tls-cert <PATH>
          The node's server certificate (PEM).

      --storage-tls-key <PATH>
          The server certificate's private key (PEM).

      --frontend <URL>
          Registers with this frontend (http:// or https://) and heartbeats to it. Without it the node is a one-member map of itself.

      --advertise-addr <HOST:PORT>
          The address callers dial, where --storage-listen is not routable. Default: the address the node bound.

      --storage-zone <LABEL>
          The zone label to register with. Default: none.

      --storage-weight <N>
          The node's share of the digests relative to the others. Default: 1.

      --storage-client-ca <PATH>
          The CA callers' certificates chain to; each must name a role (frontend, storage, daemon).
