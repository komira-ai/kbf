Configuration

tierstore is configured by flags or by one TOML file given with --config. The two make the same settings and run the same code. A file holds no secret, only the paths of key files.

The configuration file is not in a release yet. --config and --print-config are on main only: no released tierstore reads a TOML file. The command-line flags work with every released tierstore; the sections below that use --config or --print-config need a build of main, and will be in the first release after v0.0.38.

The file on main, next release

tierstore --config <path> reads one TOML file in place of the flags that describe the data path (the listen address, the tiers, the key files, the limits and the reconciler's settings). This release reads the storage-node shape: [server], [hot_store] and [cold_store], and an optional [[policy]]. A file for a storage node:

[server]
listen              = "192.0.2.10:9000"
proxy_id            = "tierstore-1"
bucket              = "tierstore"
region              = "us-east-1"
max_request_bytes   = 268435456
access_key_file     = "/etc/tierstore/access.key"
read_only_key_files = ["/etc/tierstore/daemons.key"]
presign_key_files   = ["/etc/tierstore/pack-presign.key"]
gc_key_files        = ["/etc/tierstore/pack-gc.key"]

[hot_store]
kind              = "s3"
bucket            = "tierstore-hot"
endpoint          = "http://s3-hot.example:9000"
region            = "us-east-1"
credentials_file  = "/etc/tierstore/hot.credentials"
budget            = "1TiB"
high_water        = 80
low_water         = 70
critical          = 95
copy_parallel     = 16
lease_ttl         = "30s"
reconcile_interval = "5s"
usage_stale_after = "2m"
journal_linger    = "20ms"
journal_retention = "24h"

[cold_store]
kind             = "s3"
bucket           = "tierstore-cold"
endpoint         = "http://s3-cold.example:9000"
credentials_file = "/etc/tierstore/cold.credentials"
skip_checks      = []

A key that is left out has the default of its flag (tierstore --help lists them). listen, proxy_id, bucket and access_key_file of [server], kind of each tier and budget of [hot_store] are needed. Durations are a whole number and ms, s, m or h, as in the flags. The water marks are percents, 1 to 100. A number above 9223372036854775807 (the largest TOML integer) cannot go in a file.

The values are examples: 192.0.2.10 is a documentation address and s3-hot.example is not a host. From packaging/tierstore/README.md, "The configuration file".

A message about a file repeats no value except a [[policy]] prefix: a syntax refusal names the line, the column and the key; any other refusal names the key. A refusal of the file or the flags exits 2.

Which key each flag has

The flags are in every released tierstore; the keys are for the file, which is not released yet.

Every flag that describes the data path has the key or keys below, and no other has one. A flag that takes a list (--read-only-key-file, given once for each key) is a list in the file. A tier flag is a kind and the key its kind needs: --hot dir:<path> is kind = "dir" and path, --hot s3:<bucket> is kind = "s3" and bucket. The keys of the reconciler, the journal and the lease are in [hot_store], since only a process with a hot tier has them. The crate's tests walk the flags of the binary against this table, so a flag added without a key fails them.

These stay flags, since they describe one run and not the data path: --config, --print-config, --drain-lb-wait and --drain-deadline. A start that gives --config and any other flag is refused with status 2 and a message that names the flags (--drain-lb-wait and --drain-deadline may go with it).

Defaults of the flags used on this site, from the binary: --high-water 80, --low-water 70, --critical 95, --copy-parallel 16, --lease-ttl 30s, --reconcile-interval 5s, --journal-linger 20ms, --journal-retention 24h, --usage-stale-after 2m, --drain-lb-wait 10s, --drain-deadline 15m, --backend-check-wait 5m, --presign-max-expires 15m, --region us-east-1. --hot-bytes has no default.

What the loader refuses

Each of these exits with status 2 and names the file and the key:

  • a key or a table the format does not have (the file is a closed set), and a value of the wrong type;
  • a key that holds a secret: keys and credentials are paths of files, whose names end in _file or _files; secret_access_key, access_key_id, password, a name with token in it and the like are refused wherever they are;
  • [local_cache], which is reserved for a later release and refused as not supported yet, and a file without both [hot_store] and [cold_store];
  • a key of a tier that its kind does not take (path for a memory tier, endpoint for a dir tier), a dir tier without path, an s3 tier without bucket, endpoint or credentials_file, and a key only one tier has in the other (budget and the reconciler's keys are [hot_store]'s; skip_checks is [cold_store]'s);
  • a water mark outside 1 to 100, and a budget, a count or a limit of zero;
  • a [[policy]] prefix that is listed twice, that lies inside another listed prefix (or holds one), that does not end in /, or that is under _journal/ or _tiering/, which tierstore keeps for itself.

[[policy]] has a prefix (empty for all the rest) and cache. In this release a policy is read and checked and has no effect, since nothing is cached yet; cache = true is refused as not supported yet.

From flags to a file on main, next release

tierstore --print-config with the flags of a unit (without --config) prints the equivalent file on stdout and exits 0 without starting anything. It prints the key files by path, never what is in them, and loads the file back before printing it. A --print-config that cannot write its output exits 1.

$ /usr/libexec/kbf/tierstore --print-config --listen 192.0.2.10:9000 ... > /etc/tierstore/tierstore.toml

Then change ExecStart= of the unit to:

ExecStart=/usr/libexec/kbf/tierstore --config /etc/tierstore/tierstore.toml --drain-lb-wait 10s --drain-deadline 15m

The flags and the file are both accepted in this release. The README says the flags are to go in the release after, and --config is then the way to configure the data path.

Key files and roles

Every key file (access, read-only, hot and cold credentials, presigning, GC and scoped) is read by path and must be mode 0600 or 0400; a file others or the group can read is refused at start. The access key ids of all the keys of one server must differ, or the start exits 2. A --read-only-key-file, a --presign-key-file, a --gc-key-file and a --scoped-key-file may each be given once for each key.

A key file for --access-key-file, --read-only-key-file and the credentials flags holds its key in one of two forms; the process tells them apart by the first byte that is not white space ({ is JSON):

{"access_key_id": "AKIDEXAMPLE", "secret_access_key": "the secret"}
AKIDEXAMPLE
the secret

tierstore needs exactly those two fields in the JSON form, both non-empty strings, and refuses a file with another field or an empty value.

RoleFlagMay do
full--access-key-fileeverything the front serves: put, get, head, list, delete and the calls of a multipart upload
read-only--read-only-key-fileget, head and list (objects and open multipart uploads); every write, delete and multipart call is 403 AccessDenied, before its body is read
presigning--presign-key-filesign presigned PUT URLs for one object each under a prefix
GC--gc-key-filelist, head, delete and abort uploads under one prefix
scoped--scoped-key-fileread, create and delete under the prefixes of three lists

A role belongs to a key, not to a prefix: a read-only key may read every object of the bucket.

Presigned PUT URLs

A client that holds a presigned URL writes one object with a plain PUT of the URL. The server checks SigV4 query-string authentication (payload UNSIGNED-PAYLOAD, host signed). Only a presigning key can sign a URL, and the file holds the key and its ceiling, all required:

{"access_key_id": "pack-presign", "secret_access_key": "the secret",
 "ceiling": {"prefix": "cas/b/", "max_expires_secs": 600, "max_object_bytes": 134217728}}

A URL is good for one PUT of a key that starts with the prefix (never _journal/ or _tiering/), with an X-Amz-Expires of at most the smaller of max_expires_secs and --presign-max-expires, and a body of at most max_object_bytes (5 GiB at most), held to --max-request-bytes too (256 MiB by default). The object appears only after a complete body; a second PUT of the key is 412; no multipart call, If-Match, read, list or delete is allowed. The signature does not cover the body, so the reader of the object must check its content.

GC keys

A GC key file is JSON of access_key_id, secret_access_key and prefix. It signs in the header only and may do these, only for a key that starts with its prefix (which ends in /) and is longer than it:

Scoped keys

A scoped key reads, creates and deletes under prefixes that its file lists, and does nothing else. The file is JSON of exactly five fields, all required:

{"access_key_id": "frontend-packs", "secret_access_key": "the secret",
 "read_prefixes": ["cas/"],
 "write_prefixes": ["cas/f/frontend/"],
 "delete_prefixes": []}

Every prefix ends in / and is not empty. None may be _journal/ or _tiering/, be under one, be a prefix of one, or have one as a segment. A list may be empty, but a key whose three lists are all empty is refused. A key or a listing prefix that has .. anywhere in it is refused.
