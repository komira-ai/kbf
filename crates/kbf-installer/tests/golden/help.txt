=== kbf-installer --help ===
The one root tool for setting up a kbf host and for updating it.

Mutating verbs only say what they would do unless --apply is given. Exit codes: 0 ok, 1 failed, 2 usage or a missing prerequisite, 3 refused (verification or policy), 4 busy (another run holds the lock), 5 needs an operator.

Usage: kbf-installer [OPTIONS] <COMMAND>

Commands:
  setup       First install: accounts, directories, installer.toml, the first release
  status      What is installed, staged and pending, and the last refusal
  run         Run by kbf-installer.service: act on the orders kbf wrote, revert an expired swap
  update      Order an update of this host's own frontend (root, inline)
  confirm     Keep the pending swap, naming its activation
  revert      Undo the pending swap, naming its activation
  rollback    Point `current` at `previous`, with no confirm window
  gc          Remove the releases nothing needs: current, previous, staged, the swap on trial and any a process executes from stay, and so do the newest `--keep` others
  boot-check  Run before each start of a release on trial; counts the start
  quiesce     For maintainer scripts: take the lock; exit 5 while a swap is pending
  check       Validate the installer's configuration, trust files and path chain
  proxy       Serve the frontend host's public port: route each stream to the active child frontend
  help        Print this message or the help of the given subcommand(s)

Options:
      --json
          Print the result as one JSON object on standard output

      --apply
          Do what the verb says. Without it a mutating verb is a dry run

  -h, --help
          Print help (see a summary with '-h')

  -V, --version
          Print version

=== kbf-installer setup --help ===
First install: accounts, directories, installer.toml, the first release

Usage: kbf-installer setup [OPTIONS] --mode <MODE>

Options:
      --json
          Print the result as one JSON object on standard output
      --mode <MODE>
          The kbf mode this host runs (`kbf --mode=...`) [possible values: frontend, storage, daemon, storage-and-daemon, all-in-one]
      --apply
          Do what the verb says. Without it a mutating verb is a dry run
      --release-source <RELEASE_SOURCE>
          Where releases are fetched from. Default: the frontend for the modes that enroll, a file server (`url`) for `frontend` and `all-in-one` [possible values: url, frontend]
      --release-url <RELEASE_URL>
          The https base URL of the file server, for --release-source url
      --min-generation <MIN_GENERATION>
          Refuse orders below this generation. A floor only goes up
      --commit <COMMIT>
          The first release to install (40 hex characters); needs --release-source url
      --frontend-url <FRONTEND_URL>
          The frontend to enroll with, as https://host[:port]. For `storage`, `daemon` and `storage-and-daemon`; written to kbf.toml
      --token-file <TOKEN_FILE>
          The enrollment token (a file of mode 0600 or tighter); setup keeps a copy that only kbf reads. For the modes that enroll
      --database <DATABASE>
          The state database, as postgres:///NAME?host=SOCKET_DIR (no password). Required for `frontend` and `all-in-one`: written to installer.toml and, as `state-store`, to kbf.toml, and setup creates (or brings forward) its schema. The server, the database and the role exist before setup runs
      --no-start
          Enable the units without starting them
      --listen <LISTEN>
          The public REAPI listener, as IP:PORT (kbf's --listen). frontend, all-in-one
      --worker-listen <WORKER_LISTEN>
          The worker listener (daemons and storage nodes dial it), as IP:PORT. frontend, all-in-one
      --api-listen <API_LISTEN>
          The operator API listener, as IP:PORT; default 127.0.0.1:8982. frontend, all-in-one
      --reapi-tls-cert <REAPI_TLS_CERT>
          The REAPI listener's certificate (PEM file, absolute path); needs --reapi-tls-key
      --reapi-tls-key <REAPI_TLS_KEY>
          The REAPI listener's private key (a file of mode 0600 owned by the service user)
      --worker-tls-cert <WORKER_TLS_CERT>
          The worker listener's certificate; needs --worker-tls-key and --worker-client-ca
      --worker-tls-key <WORKER_TLS_KEY>
          The worker listener's private key (a file of mode 0600 owned by the service user)
      --worker-client-ca <WORKER_CLIENT_CA>
          The CA that daemons' and storage nodes' certificates must chain to
      --storage-url <STORAGE_URL>
          The storage node the frontend proxies blobs to (kbf's --storage), as http(s)://host[:port] with nothing after it. Required for frontend. https needs --storage-ca, --storage-client-cert and --storage-client-key; http is for a loopback host only
      --storage-ca <STORAGE_CA>
          The CA the storage node's certificate chains to. frontend
      --storage-client-cert <STORAGE_CLIENT_CERT>
          The frontend's certificate toward the storage node. frontend
      --storage-client-key <STORAGE_CLIENT_KEY>
          The private key of --storage-client-cert (a file of mode 0600 owned by the service user). frontend
      --cold-store <COLD_STORE>
          The cold store, as file:///absolute/path. Required for all-in-one
      --meta-dir <META_DIR>
          The directory of the metadata log, an absolute path outside the data directory. Required for all-in-one
      --daemon-server <DAEMON_SERVER>
          The worker listener the daemon half dials, as https://host[:port] (kbf's --server); the host must be a name of the worker certificate. Required for all-in-one
      --daemon-ca-cert <DAEMON_CA_CERT>
          The CA of the worker certificate, for the daemon half (kbf's --ca-cert). Required for all-in-one
      --daemon-cert <DAEMON_CERT>
          The daemon half's client certificate (kbf's --cert), role daemon. Required for all-in-one
      --daemon-key <DAEMON_KEY>
          The private key of --daemon-cert (a file of mode 0600 owned by the service user). Required for all-in-one
      --node-id <NODE_ID>
          The daemon half's node name, a DNS label unique in the cell. Required for all-in-one
      --installer-config <INSTALLER_CONFIG>
          The installer.toml `setup` writes (and reads, to keep what it does not set), under the host root. The same flag, with the same meaning, as on `run` [default: /etc/kbf/installer.toml]
  -h, --help
          Print help

=== kbf-installer run --help ===
Run by kbf-installer.service: act on the orders kbf wrote, revert an expired swap

Usage: kbf-installer run [OPTIONS]

Options:
      --json
          Print the result as one JSON object on standard output
      --update-dir <UPDATE_DIR>
          Root's directory: status.json goes here. Root-owned, mode 0755, so the node can read it [default: /var/lib/kbf-installer]
      --apply
          Do what the verb says. Without it a mutating verb is a dry run
      --orders-dir <ORDERS_DIR>
          The order spool: owned by the service user, mode 0700, inside a root-owned parent [default: /var/lib/kbf-installer/orders]
      --unit <UNIT>
          The systemd unit to restart after a swap (Linux)
      --launchd-label <LAUNCHD_LABEL>
          The launchd label to kickstart after a swap (macOS)
      --window-secs <WINDOW_SECS>
          The confirm window the boot check gives a release on trial (120 to 1800) [default: 900]
      --starts <STARTS>
          The starts a release on trial gets before it is reverted (Linux) [default: 3]
      --min-activation-interval-secs <MIN_ACTIVATION_INTERVAL_SECS>
          The fewest seconds between one activation and the next [default: 60]
      --passes <PASSES>
          Stop after this many passes (a rehearsal or a test); without it, run until stopped
      --installer-config <INSTALLER_CONFIG>
          installer.toml, under the host root: its `database` key is the state database the installer migrates to what a release needs before that release is activated. Required when the unit restarted after a swap is a frontend's or the all-in-one's
  -h, --help
          Print help
