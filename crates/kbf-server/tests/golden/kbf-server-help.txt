The kbf farm server

Usage: kbf-server [OPTIONS]

Options:
      --role <ROLE>
          The roles to run

          Possible values:
          - all: Front, scheduler and metadata in one process
          
          [default: all]

      --cold-store <URI>
          The durable object store, where every blob ends up: `file:///absolute/path` (a directory, `kbf_objstore::FsStore`: locked while the server runs, a second server on it is refused; a write that would leave its filesystem with less free than it keeps, 5% of its size and at least 1 GiB, is refused and wakes the evictor, which forgets the least recently used objects (never one used in the last minute) and deletes their files while less than twice that is free) or `s3://bucket/prefix?endpoint=http://host:port` (MinIO, RustFS; the key pair is `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`; query keys `region`, `conditional-put=true` for a store that refuses to overwrite a key, and `min-put-rate=BYTES_PER_SEC`, the slowest rate a PUT body may reach the store at: a PUT is cut after 60 seconds plus its body's length at that rate, 1 MiB/s by default). Objects are keyed under `<prefix><log id>/` (`kbf/` for a directory and for an S3 URI without a path), the id of the metadata log. A directory is checked against the index by a start-up pass in the background; a lost or damaged object is also found when it is read, or before an action-cache hit that needs it is served (a miss). There is no `memory:` store: a `file://` path on a tmpfs is one. A storage node (not `all-in-one`) may instead be given the word `registered`: it holds no store of its own and, at each start, waits for the frontend's registration (`kbf cluster object-store`), then runs on the registered endpoint, bucket, prefix and keys, fetched over its storage certificate and held in memory only, after the probe of the keys; it never falls back to another store, and a registration that changes reaches it at its next start (until then the frontend shows it `pending`). With `registered`, `--cold-store-credentials-file` is refused and `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_ENDPOINT_URL` are not read

      --cold-store-credentials-file <PATH>
          The key pair of an `s3://` `--cold-store`, in a file: JSON `{"access_key_id": "...", "secret_access_key": "..."}`, a regular file (a symbolic link is refused) that the server's user owns and no one else can read (mode 0600 or 0400). The secret is never a flag: a command line is world-readable. Without it the key pair is read from `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, which is deprecated: the start logs one warning and a later release refuses the variables. A `file://` cold store has no keys, so the server refuses the flag with one; a `registered` one takes its keys from the registration, so the server refuses the flag with that too

      --hot-store <URI>
          The fast tier in front of the cold store: `file:///absolute/path`, a directory on an SSD (or a tmpfs). Uploads land there and are flushed to the cold store in the background; reads are served from it while a blob is still there. Its budget is not a flag: 80% of the filesystem's free space less what it keeps free (5% of its size, at least 1 GiB, and never more than half of what is free), at most `--hot-store-max-bytes`; at the budget, writes take the direct path to the cold store. Without it, uploads go straight to the cold store. A daemon's outputs (a segment upload, or the in-process plane) and a ByteStream Write over 16 MiB are written through to it as they arrive, so a large one is never held in memory. Without it, or when it has no room, a daemon's blob over 16 MiB (`kbf_front::MAX_UNSTAGED_BLOB_BYTES`) is streamed to the cold store as it arrives (a ByteStream Write, or the in-process plane's own stream), never held whole and never refused for its size. The metadata log lives in `<dir>/meta`, unless `--meta-dir` says otherwise

      --hot-store-max-bytes <BYTES>
          The most bytes the hot store's block files may hold before they are flushed, lower than its automatic budget

      --hot-store-abandon <ID>
          Abandons this server's hot store tier `<id>` at start: every object staged on it is marked unreachable as missing (its blobs answer `Unavailable` until uploaded again; nothing is answered `NOT_FOUND`), and the directory becomes a new tier. For a lost or replaced disk, after a start was refused because the directory's `TIER` file is missing or names another tier. The id is the one the refusal names

      --meta-dir <DIR>
          The directory of the metadata log (the CAS index and the action cache, a single-voter Raft log), on a local disk; created if missing. An empty directory gets a new log with a new id; every later start over it reads the id from the directory. Left out, it is `<hot store directory>/meta`; required when there is no `file://` hot store. Given, it wins over the hot store's directory

      --state-store <URI>
          Where the scheduler keeps its state, written before each change is acknowledged and replayed at start: `postgres:///kbf?host=/run/postgresql`, the database `kbf` on a local Unix socket, reached as this process's own user (peer authentication; a URL with a password is refused, as the command line is world-readable). The server must flush commits before it acknowledges them (`synchronous_commit` on) or the start is refused; the tables are created if missing. Or `sqlite:///absolute/path`, a file on a local disk that this process owns (created, with its directory, if missing: 0600, and 0700 for a directory it makes; a second frontend on it refuses to start); SQLite is removed in the next release, so a start on it logs a warning (see the upgrade notes). A start keeps the epoch the store holds, so daemons that reconnect keep the runs of the leases they hold; an operator raises it with `kbf cluster epoch-bump`, after a restore from a backup. `kbf frontend` refuses to start without it; left out of `kbf-server`, the scheduler's state is in memory and a restart loses it

      --log-dir <DIR>
          The directory of the durable log file, `kbf-server.log` and its rotated `kbf-server.log.1`, `.2`, ... (created if missing): every event stderr gets, in the same format, kept across restarts. Left out, it is `<hot store directory>/log` when the hot store is a directory; with neither, there is no file and the server logs to stderr alone (the start logs which). A directory or file that cannot be written never stops the server ([`crate::log_file`])

      --log-max-bytes <BYTES>
          The most bytes one log file holds before it is rotated; a line longer than this goes alone to a fresh file. With `--log-files` it bounds the log's size on disk
          
          [default: 67108864]

      --log-files <N>
          How many log files are kept, the current one included; rotation drops the oldest. The log never exceeds `--log-max-bytes` times this, plus one line
          
          [default: 8]

      --listen <LISTEN>
          The REAPI listener. Without `--reapi-tls-cert` and `--reapi-tls-key` it serves plain text, on any address; off loopback the start line carries a warning
          
          [default: 127.0.0.1:8980]

      --reapi-tls-cert <REAPI_TLS_CERT>
          PEM certificate (chain) of the REAPI listener. With `--reapi-tls-key` it serves TLS with this server certificate only; clients present no certificate. It is meant for a certificate from the farm's own internal CA, trusted by the front's proxy (its hop to this server) and by clients that dial this server directly; TLS for the farm's client-facing name still ends at the front. `--reapi-auth-policy` applies over TLS as over plain text

      --reapi-tls-key <REAPI_TLS_KEY>
          PEM private key of the REAPI listener; it must match `--reapi-tls-cert`, or the server refuses to start

      --reapi-auth-policy <REAPI_AUTH_POLICY>
          A JSON file with the REAPI listener's authentication policy and authorizers (`docs/reapi-auth.md`), read once at start; a file that is not a valid policy stops the server. Without it every REAPI call is accepted and allowed. The worker listener does not read it; on the operator API only the build pages and the blob route do, and they are off unless it names their authorizers

      --storage <URL>
          Proxy mode (`docs/design/architecture-v2.md`, section 7): the URL of a storage node (`kbf storage`), such as `http://127.0.0.1:8990`. The REAPI listener then answers a client's CAS, ByteStream and action-cache calls from that node, passing ByteStream through without holding a blob. The local stores are still opened: Execution and the worker listener use them (`kbf frontend` is this mode without them: Execution reads the node too). Plain text (`http://`) only here; `kbf frontend` takes the flags of the mutual TLS to the node. Without it, the server answers those calls itself

      --worker-listen <WORKER_LISTEN>
          The `kbf.worker.v1` listener. Without mutual TLS (`--worker-tls-cert`, `--worker-tls-key`, `--worker-client-ca`) it serves plain text, on any address; off loopback the start line carries a warning
          
          [default: 127.0.0.1:8981]

      --api-listen <API_LISTEN>
          The operator API listener (HTTP/JSON under `/v1`). Off unless given. Reads are open to whoever reaches it: bind it where only operators do

      --api-token-file <API_TOKEN_FILE>
          A file holding the token operator API writes (cordon, drain, uncordon) must present as `Authorization: Bearer <token>`. It must be owned by the server's user with mode 0600 or 0400, or the server refuses to start; run the server as a user other than the daemon's, whose builds could read it. Without it, writes are refused

      --invocations-open
          Serves the build pages (`GET /v1/invocations/{id}` and below) and the blob route (`GET /v1/blobs/{digest}`) on the operator API to every caller the REAPI policy accepts, with no `invocations` or `blobs` key in the policy file (`docs/design/invocations.md` section 4.3): it fills in `allow` for whichever of the two keys the file leaves out. Without it, and without the keys, those routes answer 404. Pages and blobs hold build outputs and logs: give it only for a listener that only trusted people reach

      --readyz-store-timeout-ms <READYZ_STORE_TIMEOUT_MS>
          How long, in milliseconds, `GET /readyz` on the operator API and the REAPI listener's `grpc.health.v1` service wait for the object store to answer their read-only probe before they answer not ready
          
          [default: 2000]

      --worker-tls-cert <WORKER_TLS_CERT>
          PEM certificate of the worker listener. With `--worker-tls-key` and `--worker-client-ca` it serves mutual TLS; without all three, plain text

      --worker-tls-key <WORKER_TLS_KEY>
          PEM private key of the worker listener

      --worker-client-ca <WORKER_CLIENT_CA>
          PEM CA that client certificates must chain to. Each must also name the role the method it calls takes: the daemon role (`urn:kbf:role:daemon`) for the worker session and blob calls, the storage role (`urn:kbf:role:storage`) for `kbf.map.v1.Membership`, with DNS or IP names that cover the host of the instance id and of the address it registers; a frontend certificate may call nothing here

      --worker-deny-list <WORKER_DENY_LIST>
          The worker listener's deny list: certificate serials, public keys and node ids it refuses (format in the `identity` module docs). Read at start, then again at every check (a daemon's `Hello`, `Heartbeat`, `Result`, `NodeStatus` and blob calls, a storage node's `Register` and `Heartbeat`), so an edit takes effect without a restart. A `node` entry also refuses a storage certificate with that DNS name. A list that cannot be read after start refuses all of those calls. Needs mutual TLS, or `--proxy-auth-file` (then only `node` entries can name a caller: the proxy forwards a node id, not a certificate, so a `serial` or `spki-sha256` entry never matches)

      --proxy-auth-file <PATH>
          A file holding the per-boot secret of the TLS-terminating proxy in front of this server (`docs/design/frontend-proxy.md`, section 3): exactly 32 bytes, owned by the server's user with mode 0600 or 0400, read at start. The proxy presents them as 64 lower-case hex digits in `x-kbf-proxy-auth`. With it, the REAPI, worker and operator listeners take calls from loopback only, and believe `x-kbf-node-id` and `x-kbf-role` only from a call that presents the secret; every other `x-kbf-*` header is dropped. The worker listener then takes the proxy's identity in place of a client certificate (it needs no TLS flags), and the operator API's writes must come through the proxy as well as carry the token (a local `curl` write is refused). The storage listener is not covered: it keeps its own mutual TLS. Without it, behavior is as before

      --tls-reload-interval-secs <TLS_RELOAD_INTERVAL_SECS>
          How often, in seconds, a TLS listener looks at its certificate, key and client CA files (the `--*-tls-cert`, `--*-tls-key` and `--*-client-ca` flags). A change is applied to the next TLS handshake, with no restart and without ending a connection already open: renew a certificate by replacing the files. Files that do not make a working configuration (unreadable, not PEM, a key that is not the certificate's, an expired certificate, a renewal caught between its two writes) are logged and counted in `kbf_tls_reloads_total{outcome="rejected"}`, and the previous files keep serving; the next look finds them whole and applies them. The files must be good at start
          
          [default: 30]

      --heartbeat-interval-ms <HEARTBEAT_INTERVAL_MS>
          The heartbeat interval daemons are asked for, in milliseconds, at most half the window in which a daemon may act on a `Start` (each `Start` names the newest heartbeat the server took, so a longer interval would leave it too little)
          
          [default: 5000]

      --unservable-wait-secs <UNSERVABLE_WAIT_SECS>
          How long, in seconds, queued work waits while no connected daemon can run it (none satisfies its platform, or none that does is large enough) before it is refused FAILED_PRECONDITION. The wait restarts whenever one can
          
          [default: 300]

      --default-platform <DEFAULT_PLATFORM>
          The OS and architecture, as `<os>/<arch>` (`linux` or `macos`; `x86_64` or `arm64`), of an action whose platform names no OS, no architecture and no ISA level, so that it is not given to whichever node sorts first, a Mac among them. Not applied to an action that asks for `xcode` or an iOS device, which only a Mac reports. `none` applies no default: such an action runs on any node that fits. Placement only: the action's digest and cache key do not change
          
          [default: linux/x86_64]

      --qos-allowed <QOS_ALLOWED>
          The QoS levels a call may ask for with the `x-kbf-qos` request header, as a comma list of `ci`, `batch` and `interactive` (`ci` is always allowed: it is what a call with no header, or a header naming a level not on the list, gets, and that call is never refused). The level orders the queue, most urgent first: a `batch` action waits behind every queued `ci` action. It is not part of the action digest, so it does not split the cache. A client that sends no header stays at `ci`
          
          [default: ci,batch]

      --memory-ladder-gib <MEMORY_LADDER_GIB>
          The memory rungs of an action, in GiB, ascending and each at least 1. The first is what an action that names no size (`kbf-book-mem-gib`) books. An action that passes its own memory limit runs again on the next rung above what it booked, and after the last on a whole host: the memory of the largest node that could run it, so that no other lease fits there. A rung not below that node's memory is skipped for the whole host. An action that does finish keeps its rung: later runs of it start there
          
          [default: 4 16 32]

      --exclusive-actions
          Every `action` lease books the whole worker it lands on: all of its CPUs and all of its memory, whichever worker that is, so that exactly one action runs per worker and a second waits for it. The action digest is the client's and does not change (the per-action `kbf-book-cpus` and `kbf-book-mem-gib` properties would split the action cache); this is a setting of the server. `kbf-book-cpus` and `kbf-book-mem-gib` are still checked, but no longer change what is booked. `kbf-lease=whole_machine` and `vm` leases are as they were. An action killed for passing its own memory limit has no larger booking to climb to, so `--memory-ladder-gib` has no further rung to give it: it finishes out-of-memory, as an action that already books the largest node does, and its memory floor is not raised. A worker books by what it reported at registration. The setting is not kept in the state store, so a server restart ends it for the operations the store holds: one that was queued is read back as an ordinary action, and one that was running is recovered holding only the booking the front computed for it, not the worker, so ordinary actions can be placed beside it and, if it is lost or requeued, it runs again as an ordinary action. A run that needs one action per worker must not restart the server. Off by default

      --no-memory-climb
          Keeps an action's memory booking where it started. An action that passes its own memory limit is not run again on the next rung of `--memory-ladder-gib`: the kill finishes it, FAILED_PRECONDITION with reason `ACTION_OUT_OF_MEMORY`, as a kill at the largest node does, and its attempt is recorded with `memory_kill` `own_limit`. A booking is therefore the first rung, or the GiB the action names in `kbf-book-mem-gib`. No floor is raised, so with `--learned-sizes on` an own-limit kill leaves none either. A kill the node made under memory pressure is not the action's: it runs again with the same booking, as it does without this flag. Needs `--scheduler-core legacy`; a server given it with `js` refuses to start (exit status 2)

      --vm-host-floor-cpus <VM_HOST_FLOOR_CPUS>
          The cores a node that reports VM slots (`vm.slots`) keeps for the host itself: subtracted from the CPUs placement may book on it, so that guests cannot take the host's own share. A node that reports none books the whole machine
          
          [default: 2]

      --vm-host-floor-mem-gib <VM_HOST_FLOOR_MEM_GIB>
          The memory, in GiB, a node that reports VM slots (`vm.slots`) keeps for the host itself, subtracted as `--vm-host-floor-cpus` subtracts cores
          
          [default: 8]

      --learned-sizes <LEARNED_SIZES>
          What the farm does with `kbf-estimator`, which predicts an action's memory from what its earlier runs used. `off` calls it never. `shadow` shows it every attempt that finishes and logs, for every new operation, a `size estimate:` line with what it would book, and counts how the attempts fall against its estimates (`kbf_estimator_shadow_total`); it books exactly what `off` books. `on` is `shadow` plus one change to a booking: a kill at an action's own memory limit leaves a floor under the action's key (instance, platform class, instrument and shape), which every later digest of the key, queued or new, books at least, strictly below the memory of the largest node that could run it. The floor falls only by the estimator's decay: it halves once the key has run 256 times and 7 days have passed without an own-limit kill or a sample above half of it, and a floor that falls to the first rung or below is dropped; a kill raises it again. Only an action whose memory the client did not name, on a platform that pins the OS, is keyed. The size summaries and the keys are kept in the state store, in rows of their own that a release without this flag never reads; `off` neither reads nor deletes the summaries, and ignores the keys. The memory a floor raised a queued operation to is not stored: a restart, or a rollback to `off`, books such an operation at its submitted memory until it ends

          Possible values:
          - off:    The estimator is never called and nothing is read from or written to the store
          - shadow: The estimator hears of every finished attempt and is asked for every new operation; the answers are logged and counted. Bookings are unchanged
          - on:     `shadow`, and one change to a booking: a kill at an action's own memory limit leaves a floor under the action's key that its later digests book at least, until the estimator's decay lowers it
          
          [default: off]

      --scheduler-core <SCHEDULER_CORE>
          Which core drives the farm's scheduling. `legacy`, the default, is the driver the server has always had. `js` runs the farm on the js scheduler core: it learns sizes in `shadow` at most (`--learned-sizes on` with it is refused at start, exit status 2), and it answers an operation by its `operations/<id>` name only. Either core reads the rows the other wrote to the state store, so a restart with the other value takes them up. The core a server runs is logged at start and exported as `kbf_scheduler_core{core}`, 1 for it and 0 for the other

          Possible values:
          - legacy: The scheduler driver the server has always had
          - js:     The farm on the js scheduler core

      --placement-load <PLACEMENT_LOAD>
          Whether placement reads the load the nodes report. `off`, the default, books by the CPUs a lease asks for, as the server always has, and reads no load. `on` admits and ranks nodes by the load they report and the load a lease is predicted to add; a node that reports none is charged by prediction alone, and a node that has never sent a reading the server accepted is charged at least 1000 m for each lease (the node's whole CPU capacity, if that is less), so a prediction under one core changes nothing for such a node. It is read under either `--scheduler-core`. With `js`, `on` is the scheduler's placement by load as a whole, with settings the server fixes (`placement_load.rs`; none is a flag): besides the reading it applies the guard that keeps the flat memory charged to a node within its memory, and scores nodes by balance. It also sets a learned time profile charged per minute and an expected-life charge that ends a new lease at its key's expected life plus two minutes; both are idle, since the farm gives the scheduler no learned profile and no curve source. The memory guard counts only leases that carry a memory (a retry up the memory ladder, a VM) unless `--placement-predictions on` gives leases one

          Possible values:
          - off: Placement books by the CPUs a lease asks for, as it always has; the load is not read
          - on:  Placement admits and ranks nodes by the load they report and the load a lease is predicted to add

      --placement-predictions <PLACEMENT_PREDICTIONS>
          Whether the farm gives its scheduler the estimator's prediction of what a new operation costs, from the rows `--learned-sizes` keeps, so that placement charges the learned cores and memory instead of the cores the request asked for and no memory. `off`, the default, computes none. `shadow` computes the prediction at submit, gives the scheduler nothing, and compares it with the run when it ends: the cores the run used on average, its peak memory and its life in whole minutes, each counted as under (the run used more than predicted), fit (at most the prediction and at least half of it) or over (less than half of it) in `kbf_prediction_vs_run_total`; the operations given a prediction are counted in `kbf_prediction_made_total` and those given none, by why, in `kbf_prediction_unset_total`. Placement is exactly what `off` does. `on` gives the scheduler the prediction as the cost of the operation's lease, at submit (on the legacy core also again for an operation read back from the state store at a start), which charges the learned memory as well as the cores: a lease is admitted to a node only while the memory charged to the node's leases stays within the node's memory. An operation the estimator has no usable row for, or is not asked about (not an action, one that asks for a GPU, no OS pinned, no subject), gets none and is charged as it is with `off`. `shadow` and `on` need `--learned-sizes shadow` or `on`; `on` needs `--placement-load on`; a prediction only changes what the lease is charged: the memory limit and the cores it is booked and run with stay the request's and the ladder's. A server given a combination that breaks one of these refuses to start

          Possible values:
          - off:    No prediction is computed, counted or given to the scheduler
          - shadow: The prediction is computed and counted at submit and compared with the run when it ends; the scheduler is given nothing, so placement is what `off` does
          - on:     The prediction is computed at submit (on the legacy core, and again for an operation read back from the state store) and given to the scheduler as the cost of the operation's lease

      --usage-profiles <USAGE_PROFILES>
          Whether the farm learns what its leases use, for the scheduler's admission by load. `off`, the default, learns nothing. `record` and `on` need `--scheduler-core js` and `--state-store`; `on` also needs `--placement-load on` and `--placement-predictions on`, since the scheduler reads a curve only for an action that has a prediction. In this build a value other than `off` changes only the start line `usage profiles: <mode>` and the gauge `kbf_usage_profiles_mode{mode}`, 1 for the mode and 0 for the others: nothing is learned or stored yet. A server given a combination that breaks one of these refuses to start

          Possible values:
          - off:    Nothing is learned or stored
          - record: Runs are learned and stored; the scheduler does not read the curves
          - on:     Runs are learned and stored, and the scheduler reads the curves

      --whole-node-max <WORKERS>
          Turns on the whole-node drain and caps for whole-machine requests (`kbf-lease` `whole_machine`), and names the most workers that may be whole at once: held by a whole-machine lease or reserved for a queued request (a request that fits nowhere reserves the worker that will empty soonest, and nothing newer is placed there). The ceiling is also at most the workers that serve whole-machine leases less `--whole-node-keep-for-ordinary`, and falls as workers leave. Left out, the scheduler books whole-machine requests as it always has, and the other `--whole-node-*` flags are refused. A request's reservation is given up at its action's timeout, and a client may send none: without `--whole-node-drain-deadline-secs` the reservation of such a request is never given up (it ends when its worker is empty), so set that flag when clients may send no timeout

      --whole-node-max-draining <WORKERS>
          The most workers reserved for a queued whole-machine request that still run other leases at once: the idle capacity a drain may cost. Default 1

      --whole-node-keep-for-ordinary <WORKERS>
          The fewest workers that carry neither a reservation nor a whole-machine lease, so ordinary work always has them. 0 lets whole-machine requests take every worker

      --whole-node-allow-last-capable
          Lets a reservation start on the last worker an older ordinary request that waits could run on. Off, the request waits for another worker, so a whole-machine request never takes the only worker such a request has

      --whole-node-drain-after-secs <SECONDS>
          How long, in seconds, a whole-machine request waits before it reserves a worker; until then it takes only a worker with no lease. 0, the default, reserves at once

      --whole-node-drain-deadline-secs <SECONDS>
          How long, in seconds, a reservation may drain its worker before it is given up (nothing running is stopped): the worker is barred to the request for `--whole-node-reserve-backoff-secs` and another is reserved. Left out, the request's longest wall time, the `timeout` of its action; an action that names none has no wall time, and without this flag its reservation is never given up

      --whole-node-reserve-backoff-secs <SECONDS>
          How long, in seconds, a worker stays barred to a request after the request gave its reservation up. Default 300

      --whole-node-max-reserve-attempts <COUNT>
          The reservations a request gives up before its next one has the request's longest wall time as its deadline, and so ends in a grant. Default 2

      --finished-retention-secs <FINISHED_RETENTION_SECS>
          How long, in seconds, a finished operation is kept after its callers are answered. Within it, WaitExecution on the operation's name streams its result (a client whose Execute stream broke gets a result the action cache does not keep, such as a failure); after it, the name is NOT_FOUND. Every operation finished within it is held in memory
          
          [default: 60]

      --shutdown-timeout-secs <SHUTDOWN_TIMEOUT_SECS>
          The operator's hard stop, in seconds, for a stop (SIGINT or SIGTERM). A stop refuses new Execute calls (UNAVAILABLE, which Buck2 retries) and sends GOAWAY, and every open Execute and WaitExecution stream stays open until its action is done, however long that takes; the exception is a stream whose operation was never started and that no worker on this frontend can run (say every capable worker is cordoned) and no other frontend can take, which ends UNAVAILABLE as the drain begins (Buck2 retries only the opening of a call). The operation stays queued. The default, 0, is no deadline: the stop waits indefinitely, and a second signal is the other way to end it at once. Buck2 never recovers a stream that breaks mid-action, so set one only to force a stop: when it runs out, the open streams end UNAVAILABLE (a client still uploading is cut off). `--drain-deadline` on a frontend over a state store only reports
          
          [default: 0]

      --progress-interval-secs <PROGRESS_INTERVAL_SECS>
          How often, in seconds, every open Execute and WaitExecution stream is sent its operation again (same name, not done, current stage), so a load balancer's idle timeout never cuts a long action. 0 sends none
          
          [default: 30]

      --http2-keepalive-interval-secs <HTTP2_KEEPALIVE_INTERVAL_SECS>
          How often, in seconds, the REAPI and worker listeners send an HTTP/2 PING on a quiet connection. 0 sends none (and `--http2-keepalive-timeout-secs` is unused)
          
          [default: 30]

      --http2-keepalive-timeout-secs <HTTP2_KEEPALIVE_TIMEOUT_SECS>
          How long, in seconds, a PING may go unanswered before the connection is closed
          
          [default: 20]

      --async-threads <N>
          Worker threads of the async runtime, which run every task between its waits. Default: every CPU the process may use on the server; `max(2, reserve/4)`, at most the physical cores, on the daemon

      --blocking-threads <N>
          The most threads the runtime's blocking pool runs at once, for calls that wait on a disk or a process (a thread is made when a call needs one and ends when idle). Default: 512 (tokio's) for the server, 64 for the daemon

      --cpu-threads <N>
          Threads for CPU-bound work, such as hashing, which never waits and so is held to the CPUs. Default: every CPU the process may use on the server; `max(2, reserve/2)`, at most the physical cores, on the daemon

      --invocation-memory <INVOCATION_MEMORY>
          The memory, in bytes, the invocation records may take together (`docs/design/invocations.md`, section 3.5). At the bound, records of a minted id go first, then idle ones, least recently seen first; with only open builds left, the largest stops taking rows. Records are kept in memory only and lost on restart. Their heap was measured at up to 1.08 times this at 200 kB and above, and 1.12 at 50 kB (section 3.5)
          
          [default: 268435456]

      --segment-upload-max-bytes <BYTES>
          The most bytes, records and footers together, one segment upload on the worker listener may hold in memory (`docs/design/write-path.md`, section 4.2): the segments it declares that are not written to the hot store as they arrive (all of them, without one). Not a limit on a blob's size: a segment held in memory holds no record over 16 MiB (`kbf_front::MAX_UNSTAGED_BLOB_BYTES`), and an upload with a larger one and no room on the hot store is answered FAILED_PRECONDITION, so the daemon sends its records by ByteStream, which streams a large blob to the cold store. Those ranges are held until the upload commits, admitted under `--write-bytes-in-flight` with every other upload: a `Begin` waits while that is spent. At least 33 MiB (`kbf_front::MIN_SEGMENT_UPLOAD_BYTES`), a daemon's upload of small files with room to spare, and at most `--write-bytes-in-flight`, so any legal `Begin` can be admitted; the server refuses to start otherwise. At most `kbf_front::MAX_ADMISSION_BYTES`, the most one admission counts, so a `Begin` never holds more than it is counted for under the bound
          
          [default: 34603008]

      --segment-upload-idle-secs <SEGMENT_UPLOAD_IDLE_SECS>
          How long, in seconds, a segment upload may go without a call before it is dropped and its memory returned. An upload is also dropped when the connection that began it closes; one that is committing is kept until its commit ends
          
          [default: 60]

      --write-linger <WRITE_LINGER>
          How long, in milliseconds, the oldest blob of an open segment waits for concurrent uploads to join it before the segment is sealed and written (`docs/design/write-path.md`, section 3.1). No caller is answered before its segment has committed, so this is added to an upload's latency at most
          
          [default: 2]

      --write-own-segment-bytes <WRITE_OWN_SEGMENT_BYTES>
          Blobs of this many bytes or more are written as a segment of their own, past the group, so they neither wait for the linger nor hold up small writes
          
          [default: 16777216]

      --write-bytes-in-flight <WRITE_BYTES_IN_FLIGHT>
          The most bytes uploads may hold at once. A ByteStream Write is admitted before it reads past its first message, for its blob's size up to 16 MiB (`kbf_front::MAX_UNSTAGED_BLOB_BYTES`) and for 16 MiB above that (a larger blob is streamed onto the hot store, or to the cold store without room there, not held); a BatchUpdateBlobs for its total; a segment upload's Begin for what it holds in memory. A caller over the bound waits, nothing is refused for load. At least `--segment-upload-max-bytes` (by default 33 MiB, under the default 2 GiB). Not covered: each HTTP/2 stream's message as tonic decodes it, before the handler runs, up to 17 MiB per stream (about 3.4 GiB for 200 streams), times the streams one connection may open on each listener
          
          [default: 2147483648]

      --reapi-max-streams <REAPI_MAX_STREAMS>
          The most HTTP/2 streams one connection to the REAPI listener may have open. buck2 keeps one Execute stream open per outstanding action, idle until the action finishes, so this bounds how large a backlog one buck2 invocation can show the farm. The connection's flow-control window is this many streams' windows; above about 2000 streams each stream's window is smaller than 1 MiB so that the product stays under HTTP/2's largest window. At least 1, at most 32767
          
          [default: 10000]

      --worker-max-streams <WORKER_MAX_STREAMS>
          The most HTTP/2 streams one connection to the worker listener may have open: a daemon's persistent session stream and its short transfer streams. At least 1, at most 32767
          
          [default: 200]

      --write-puts-in-flight <WRITE_PUTS_IN_FLIGHT>
          The most segment PUTs, each with its footer read-back, in flight at once. A segment sealed while all are busy waits; new blobs go to a new open segment
          
          [default: 4]

      --write-pool-writers <WRITE_POOL_WRITERS>
          The writers of the write pool: the ByteStream and storage `Write`s of a node with a write tier are appended to shared segment files by this many writers, each holding one range open, so the node keeps at most this many block files (plus the open grouped block) open for writing for those blobs, however many uploads are in flight. At least 1
          
          [default: 8]

      --write-pool-queue <WRITE_POOL_QUEUE>
          The most blobs waiting for a write-pool writer. A blob that finds the queue full goes straight to the object store, as one does when the write tier has no room. At least 1
          
          [default: 4096]

      --write-pool-stream-idle <WRITE_POOL_STREAM_IDLE>
          How long, in seconds, a streamed blob may go without sending a chunk before its write-pool writer is taken back and the upload fails UNAVAILABLE (the client sends it again). Without it, a stalled but connected large upload would hold a writer for ever, and with all writers held every other blob would wait. It limits stalls only: an upload that sends a chunk more often than this (a trickle) can still hold a writer. At least 1
          
          [default: 30]

      --durable-wait <DURABLE_WAIT>
          How long, in seconds, a storage node waits for blobs it holds in RAM to be written to its disk when a caller asks for a durable answer that waits (`kbf-durable: wait`): an action-cache entry is committed only once every blob it names is on an owner's disk, and the writer of the entry asks each owner with this wait; the action's owner waits the same for its own copies. A blob still in RAM when it ends is reported missing and the write fails UNAVAILABLE, for the caller to try again. Nothing holds a blob in RAM yet, so no call waits. At least 1, and under half of the 120 seconds a chain's replica may take to commit a blob (`kbf_storage::replicate::ChainConfig`): a start with more is refused
          
          [default: 10]

      --ram-peer-grace <RAM_PEER_GRACE>
          How long, in seconds, after its own write of a blob it acknowledged from RAM a storage node waits before it asks the blob's other owner whether the blob is on its disk too, and journals a repair debt if it is not. Long enough that the usual answer is yes and nothing is journalled. Only a node that acknowledges from RAM (`--ram-ack-bytes`) asks. At least 1
          
          [default: 5]

      --ram-ack-bytes <RAM_ACK_BYTES>
          How many bytes of blobs a storage node may hold in RAM, acknowledged to the writer and not yet written to its disk. 0, the default, is off: a write is acknowledged from disk, as before. Over 0, a blob of at most 4 MiB written to two owners is acknowledged once both hold it verified in RAM, and written to each disk afterwards: losing both owners' RAM before then loses the blob. A blob that finds the budget full is written through to the disk before it is acknowledged, never waited for. Set it on every storage node or none. A node that does hold blobs counts them in `kbf_storage_ram_unwritten_bytes`, writes them to its disk in the background and, when it stops, within `--ram-drain-deadline`. A node can hold this many bytes beside the `--write-bytes-in-flight` it receives. Storage nodes only: a server with no replica to hold a second copy holds nothing
          
          [default: 0]

      --ram-drain-deadline <RAM_DRAIN_DEADLINE>
          How long, in seconds, a storage node that is stopping waits, after its calls have ended, for the blobs it holds in RAM to be written to its disk (`--ram-ack-bytes`) and then for the blocks staged on its hot store to be flushed to the cold store: one bound for both. The blobs left in RAM when it ends are lost to the stop; the blocks left on the hot store are on its disk, flushed by the next start. Both are counted in the log. At least 1
          
          [default: 30]

      --store-put-attempts <STORE_PUT_ATTEMPTS>
          How many times a segment PUT is tried. Only a PUT that did not complete (connect, reset, timeout) or that the store answered 5xx is tried again, after 100 ms and then four times longer each time, under a new object key; if every attempt fails, the segment's blobs are answered UNAVAILABLE
          
          [default: 3]

      --input-tree-cache-entries <INPUT_TREE_CACHE_ENTRIES>
          The most decoded Directories an Execute's input check keeps in memory (`docs/design/storage.md#input-tree-check`). Least recently used go first
          
          [default: 1048576]

      --input-tree-cache-bytes <INPUT_TREE_CACHE_BYTES>
          The most bytes of decoded Directories the input check keeps (each costs its digests, 40 bytes apiece, and 160 bytes)
          
          [default: 268435456]

      --input-tree-reads-in-flight <INPUT_TREE_READS_IN_FLIGHT>
          The most Directory blobs the input check reads from the store at once, across all Executes
          
          [default: 64]

      --member-ttl-secs <SECONDS>
          How long, in seconds, a storage node's membership row lives without a heartbeat before the state store expires it and the member goes down in the storage map. Nodes are asked to heartbeat three times as often
          
          [default: 15]

      --member-dwell-secs <SECONDS>
          How long, in seconds, a down storage member stays in the map before it leaves and its blobs move to other owners
          
          [default: 300]

      --ui[=<BOOL>]
          Serves the web UI on the operator API (`--api-listen`): read-only pages under `/ui` (`docs/design/kbf-ui-v1.md`). On by default; `--ui=false` turns it off, and `/ui` is then a `404`. The UI is open: it asks for no login or certificate, and it shows everything unredacted, the logs of builds and the arguments of failed commands, to whoever reaches the operator API's port, whatever the REAPI policy says of `--invocations-open`. Only `GET` and `HEAD` are served; the operator API's write routes and their token are unchanged. Keep the operator API on loopback, or behind the proxy and a network you trust
          
          [default: true]
          [possible values: true, false]

      --pack-index
          Opens the pack index at start: the tables in the Postgres state store that say which pack holds each blob and where. A frontend given `--pack-store-endpoint` reads and writes them; without it nothing does, and the flag only checks that the store can hold them. Needs `--state-store` as a `postgres://` URL whose schema has the pack tables (`kbf-installer setup` makes them); a `sqlite://` store is refused. Left out, no pack table is touched

      --history-index-root <ROOT>
          Where history's index rows live in the state store: `ui/`, or `<prefix>ui/` for a prefix that ends in `/`, so that one state store can hold several farms' history apart. Left out, it is `ui/`. Needs `--history-objects`

      --history-objects <URI>
          Where build history is kept: an object store, `s3://bucket/prefix?endpoint=http://host:port` (the key pair is the `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` of the environment) or `file:///absolute/path` (a directory this process owns, not the cold store's). The attempts and cache hits of each invocation a client named are recorded under `<prefix>history/` after their results are sent, never before and never delaying one; the index rows go to `--state-store`, which this flag needs. A full queue, a slow object store or a slow state store drops records and counts them (`kbf_history_dropped_total` on `/metrics`), and never fails or delays a call. The writer reads and writes only keys under `history/`. Left out, nothing is recorded
