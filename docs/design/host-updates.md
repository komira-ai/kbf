## Changes in rev 4

The shape changed; rev 3 is superseded. What was decided:

1. **The updater is generic and knows no service.** The per-service strategy library and the closed set of root verbs are gone.
2. **Each service ships its hook in its release.** The hook is **any executable** (a binary or a script) that the declaration names by a path within the verified release; the updater requires nothing of its language. Our own services follow the repository rule, which is a rule for our code and not part of the updater contract: the hook is a subcommand of the service's own binary (for example `tierstore update-hook <step>`), Rust, tested with the service, no shell. The cutover logic for a version ships with that version.
3. **A fixed step contract:** `prepare <artifact>`, `cutover`, `verify`, `rollback`, `cleanup`. Each step is safe to run twice; the updater persists the step it reached and resumes after a crash (3.2, 3.5).
4. **Hooks are declared in a root-owned file the package installs** (`/etc/updater.d/<service>.toml`): the hook binary, the rights it needs, bounds per step. They are never registered at runtime. At runtime a service registers only liveness and version (2). A hook runs with exactly its declared rights (3.4).
5. **Trust (3.3):** the hook binary is the artifact the updater verified (sha256 and attestation) before anything from it runs; a declaration that is not root-owned, or is group- or world-writable, is refused.
6. **The tierstore nftables swap and the js-agent cordon and drain become those services' hooks** (4.1, 4.2). The kbf daemon's current behaviour becomes a hook too (4.3). The coordinator stays generic (5).
7. **Superseded and removed:** the strategy interface and its capability flags, the closed root verb set, the executor's per-verb concurrency table (replaced by the step runner and its persisted step record), the registry transport, privilege and strategy-location questions.
8. **Kept from rev 3:** `Deferred` and `halt` outcomes and their advertisement (`deferred-v1`, `halt-v1`), `promotion_pending` as a heartbeat state, release/environment gate classification, per-(service, role) slots with a named pool, canary and bake, `priority` and `urgent`, selector membership with `excluded` and `unmanaged`, the services-file load rules (as the declaration's), observability.

Earlier revisions (2, 3, 3.1, 3.2) answered an independent review of the strategy-library design; their changelogs are dropped with that design.

## 0. The proposal in one page

Today every host runs an unprivileged agent (`kbf-updater agent`) beside a root helper (`kbf-host-install --serve`) per product, and a coordinator that keeps a desired version per service. The agent runs one fixed sequence (fetch, drain the node, switch, health, confirm or revert, undrain); the helper installs a component whose name is the literal `kbf`. What it takes to move a particular product from one version to the next is written into the updater.

The decided shape moves that knowledge out of the updater and into the service:

1. **The updater is a generic process.** On every host it fetches the release, verifies it (sha256 and attestation), stages it, runs the service's hook through a fixed five-step contract, persists which step it reached, reports to the coordinator, and rolls back. It knows no service.
2. **Each service ships its update hook in its release, as any executable.** The cutover logic for a version ships with that version. For our own services it is a subcommand of the service's binary, written in Rust and tested in the service's own CI; that is the repository rule for our code, not a requirement of the updater. The updater never contains a service's cutover logic.
3. **The declaration of a hook is a root-owned file the package installs.** It names the hook binary and the rights it needs. A service cannot register code at runtime; at runtime it registers only that it is alive and which version it runs.
4. **The coordinator is generic over services**: it holds the desired version per service, the hosts, slots, canary and bake (5).

**What this replaces.** The earlier direction was that no update logic lives in a service and that the updater stays a simple program that fetches, verifies, replaces binaries and restarts units. This design keeps the generic half (the updater is one process that is the same for every service and decides nothing about any of them) and replaces the other: the cutover of a service is the service's own code, shipped with it as a hook that runs only when an update runs, never in the serving process.

## 2. The registry and the declaration

There are two different things, and keeping them apart is the security property.

**The declaration** is a file, `/etc/updater.d/<service>.toml`, root-owned, installed with the package (3.3). It says what the updater may run for this service and with what rights. It is read by the updater; it is never written by a service at runtime.

**The runtime registration** is a message from the running service to the updater's socket. It carries only **liveness and version**: the service name, the version text it runs, and a loopback health address and path. It carries no command, no path to run, no rights and no parameter of any hook. A process that reaches the socket can therefore claim to be alive; it cannot make the updater run anything. Running code as root is only ever the result of a verified artifact and a root-owned declaration.

### 2.1 The registration socket

A unix socket in a directory owned by root with group `updater-register`, mode 0750, the socket 0660 in that group; a service account joins the group in its unit (`SupplementaryGroups=`). Authentication is `SO_PEERCRED`, the pattern the repository already uses for its signing socket (`crates/kbf-signer/src/server.rs:44-53`, which refuses a world-accessible directory, `:59-82`). The uid must be the one the declaration names for that service; one uid per service (a name mapped to a shared uid is refused when the declarations load). The uid name in a declaration is resolved at start and again on reload; a uid that changed is refused. The health address must be loopback and its port within the range the declaration grants; the updater, unprivileged, only issues a `GET` to it.

| field | meaning | checked against |
|---|---|---|
| `name` | service name (`wire::is_service_name`, at most 64 bytes) | a declaration exists |
| `version` | the version text the service runs | the version the updater recorded when it staged the release; a mismatch is reported unhealthy, never believed |
| `health` | **optional**: a loopback address and path answering 2xx when ready | loopback; port in the declared range. A service with no listener (the js-agent) omits it and its health is the hook's `verify` |

### 2.2 A service that is not running, or never registered

- **Declared, never registered:** reported to the coordinator as `absent` (a new health value; today there are `healthy` and `unhealthy`, `wire.rs:29-35`). The coordinator does not count an absent service toward `min_up` and does not order it unless the service definition says `install_when_absent`.
- **Registered, now not running:** the connection closed. The registration stays for `registration_ttl` (a declaration value); the service is reported unhealthy with `stopped`. A hook is told the service is stopped (an input, not a different step set).
- **Registered twice:** a second registration of the same name from the same uid replaces the first; from another uid it is refused and logged. For `root` this is not a separation: a root service's registration is trusted only as far as root is, and it carries only liveness and version.
- **A service with no registration client or listener** (the js-agent today) would read `absent` for ever. Two ways out: it links the **registration client**, a tiny crate with no kbf product dependency that sends the three fields over the socket (a migration step, 8); or, as the **fallback only for a service that cannot link it**, the declaration can ask for a synthetic registration, in which case the updater reports liveness from the unit's state and the version from the staged release.
- **kbf itself** has a declaration like any service; hosts configured today with `--service` flags get a synthetic declaration read from the same file format until the flags are retired (8).

### 2.3 Persistence across an updater restart

The accepted registration is written to the updater's state directory (mode 0700) by temporary file, fsync, rename and directory fsync. On start the updater loads it, marks every service `unconfirmed`, and reports it as last known until the service reconnects; one that does not within `registration_ttl` becomes `stopped`. Capabilities are never read from this file: the declarations are re-read on every start.

### 2.4 The declaration

```toml
# /etc/updater.d/tierstore.toml   root:root, mode 0644, installed with the release
# Top-level keys come first: in TOML a key after a table header belongs to that table.
name   = "tierstore"
binary = "tierstore"                    # path of the hook executable within the verified release (a binary or a script)
# hook_args = ["update-hook"]           # leading arguments before the step; this is the default (our convention); [] for an executable that takes the step first
signer = { repository = "...", workflow = "artifacts.yml" }   # whose attestation the artifact must carry
uid    = "tierstore"                    # the account the service runs as and registers as
registration_ttl_secs  = 300
health_ports           = [9301, 9302]   # loopback ports a registration may name (omit for a service with no listener)
verify_deadline_secs   = 1600           # after cutover succeeds: verify must succeed by then, or the updater runs rollback
promotion_ceiling_secs = 3600           # the only ceiling: the updater applies it and passes it to the hook (3.2)
cleanup_retries        = 3              # cleanup failing is re-run forward this many times, never rolled back
state_dir              = "/var/lib/updater/hooks/tierstore"   # owned by the hook's account, 0700, outside the service's write paths (3.4.1)
boot                   = "restore"      # a boot-time entry point run at the updater's start, before units start (3.5)
min_version            = "..."          # the first release that carries a hook; below it a fleet rollback goes through the first-install path (7)

[hook]
user  = "tierstore-update"              # not `uid`: the hook's account owns the record, the service cannot write it (3.4.1)
group = "tierstore-update"
capabilities = []                       # hook-wide grant; the fallback for a step with no entry below
read_paths   = ["/usr/libexec/kbf", "/usr/sbin/nft", "/etc/tierstore"]
write_paths  = []                       # state_dir is writable implicitly; the cache directory is not touched by any step
units        = ["tierstore@9301.service", "tierstore@9302.service"]   # the only units the hook may start and stop (never mask: 3.4)
address_families = ["AF_UNIX", "AF_INET", "AF_INET6", "AF_NETLINK"]
environment  = { }                      # only these variables; nothing is inherited

[hook.step_capabilities]                # per step: held only in the steps that need it (the tierstore owner's list)
prepare  = ["CAP_NET_ADMIN"]
cutover  = ["CAP_NET_ADMIN"]
verify   = []
rollback = ["CAP_NET_ADMIN"]
cleanup  = []

[hook.timeout_secs]                     # per step; the updater kills a step that passes its bound
prepare  = 600
cutover  = 300
verify   = 1000
rollback = 600
cleanup  = 1300

[hook.params]                           # opaque to the updater; written to a file and passed as `--params <file>`; numbers and booleans only
promotion_bound_secs = 900              # how long verify waits for v-next to take the cache lock before it reports promotion_pending
# a service with a cordon puts its lease and cap here, e.g. cordon_lease_secs = 300, cordon_max_secs = 13500
```

`[hook.params]` is an opaque table: the updater validates only that it is a table of scalars, writes it once per update to a file in a directory the updater owns (root-only, kept until the update ends or is abandoned) and passes the path as `--params <file>` to every step (configuration is flags, not environment). The file also carries reserved keys under the prefix `updater.`, written by the updater and never set by a declaration; a `[hook.params]` that sets any `updater.*` key is refused at load:

| key | value |
|---|---|
| `updater.staged_release` | absolute path of the verified staged tree |
| `updater.previous_release` | absolute path of the release being replaced; absent on the first install |
| `updater.target_version` | the version being installed |
| `updater.previous_version` | the version being replaced; absent on the first install |
| `updater.artifact_digest` | `sha256:<hex>` of the release artifact the updater verified (its attested tarball); an identity, for the hook to key its record and to see that every step is about the same release. The hook does not re-verify it: the staged tree is root-owned and read-only (3.4.1) |
| `updater.promotion_ceiling_secs` | the declaration's `promotion_ceiling_secs` (3.2) |

A hook may refuse a key of its own `[hook.params]` it does not know, but it must ignore an `updater.*` key it does not know: the updater may add reserved keys, and an older hook must keep working. The updater writes one params file per update and passes the same file, with the same values, to every step (`prepare`, `cutover`, `verify`, `rollback`, `cleanup`); `prepare`'s `<artifact>` argument is byte-for-byte the string in `updater.staged_release`, so a hook may compare them exactly. There is no `release_dir` key in the declaration: the updater owns the release layout, and a hook learns the paths only from these keys. A hook does not trust them blindly: it checks each path against its own `state_dir` and its declaration (3.4.1) before it reads or writes anything through it. The updater itself reads only `promotion_ceiling_secs`, `cleanup_retries`, the timeouts and `verify_deadline_secs`.

**Placement is checked.** A repository test parses every declaration shipped in the repository and asserts that each key is in the table the loader reads it from (the rights under `[hook]`, the deadlines at the top level, nothing but scalars under `[hook.params]`); the loader refuses an unknown key anywhere. Quoted numbers above are the tierstore owner's (`tierstore-handover.md`, section 2); the account `tierstore-update`, `state_dir`, and the empty `write_paths` are changes this document asks of that section (3.4.1).

Load rules, applied to every declaration and across all of them: `hook.user` differs from `uid` unless it is `root`; `state_dir` is not inside any path the service's account can write; the file is root-owned and not group- or world-writable (else refused); a name mapped to a uid that another declaration uses is refused (`root` excepted: several services may run as root, and uid isolation does not separate them anyway); two declarations that claim the same unit or port range are refused; two declarations whose `state_dir` is the same path or one inside the other are refused; a unit name must match the grammar for that service (never an existing system unit); `verify_deadline_secs` must be at least the `verify` bound plus the `rollback` bound (else the updater would roll back a verify that is still allowed to run). **A declaration that fails a rule refuses that one service** (it becomes `unmanaged` and raises an alert); the updater goes on with every other service. Grants (user, capabilities, paths, units, signer) and tunables (timeouts, deadlines) may be kept in two files per service so a change of tunables in review is not mistaken for a change of grant.

## 3. The generic updater

### 3.1 The pipeline

For one update order of one service, in this order, each step only if the one before it succeeded. Before each step the updater writes the step record (3.5).

1. **Precondition.** The host is healthy enough to update; the service is declared; no other update runs on the host (the coordinator enforces it, `decide.rs:105`; the updater enforces it again because it is the one that would be hurt).
2. **Fetch and verify.** Download the release the version names from the channel the declaration's signer names; check the sha256 against the signed sums and the attestation (repository, signer workflow, issuer, hosted runners, commit, branch) on the host, with the pinned `gh` and trusted root (`crates/kbf-installer/src/attest.rs:1-17`); lay it out beside the running release. The updater never takes a URL or a path from the coordinator's reply: the version is the only input. **Nothing from the artifact runs before this step has succeeded** (3.3).
3. **Declaration.** The new release carries its declaration; 3.3 says when and how it is installed.
4. **`prepare <artifact>`**, then **`cutover`**, then **`verify`**, then **`cleanup`**, each a run of the hook (3.2), each with its bound. What runs next after each outcome is the table of 3.2; in short, **`rollback`** after a failed `prepare` or `cutover` or a failed `verify`, and **`cleanup` only after `verify` succeeded**.
5. **Report** in the next heartbeat, including `Deferred`, `halt` and `promotion_pending` (3.8).

The updater decides nothing about any service in this sequence: it does not drain, restart, swap or cordon. Everything that touches the service happens inside a hook.

### 3.2 The step contract

A hook is **any executable**: a binary or a script. The declaration names it (`binary`, a path within the verified release) and declares its rights; the updater runs `<executable> <hook_args> <step> [args]`, where `hook_args` defaults to `["update-hook"]`, the convention our services follow (`tierstore update-hook <step>`), and is `[]` for an executable that takes the step as its first argument. It is run by the updater with the rights of the declaration (3.4). **The contract below applies to whatever executable it is:** the arguments, the exit codes, the last-line JSON and the idempotency; the declared rights apply to it too, and it must come from the verified release (3.3). Our own services follow the repository rule (Rust, tested with the service, no shell); that is a rule for our code, not part of this contract. The five steps:

| step | arguments | what it must do | reversibility is the hook's |
|---|---|---|---|
| `prepare` | `<artifact>`: the staged release directory; always equal to `updater.staged_release` in the `--params` file | check the host can take the update, make the new version ready beside the old, and change nothing a client can see; place anything it must undo later (a cordon, a started instance) | |
| `cutover` | | the visible change: make the new version take over | |
| `verify` | | observe that the new version serves and is the one running; may be run again and again | |
| `rollback` | | undo what `prepare` and `cutover` did, as far as they can be undone | |
| `cleanup` | | finish: remove what only the update needed (the old instance, a cordon, staged files) | |

**Every step is safe to run twice.** The updater does not know what a step did; it knows only that a step it started and did not see finish may be started again, and that doing so leaves the same state. The conformance suite (9) enforces this on every hook.

**Exit codes.** `0` success. `1` failure. `75` deferred: the host is busy or not ready, nothing irreversible happened, try later (rev 3's `Deferred`). `76` halt: the failure is one no version can repair and acting further would make it worse (rev 3's `halt`, 3.8). A step killed by its timeout or a signal is a failure. Any other code is a failure.

**Structured output.** The last line the hook writes to stdout is one JSON object, which the updater reads; a missing line, or one that is not a JSON object, is read as `{}`. A JSON object is read field by field: a field of the wrong type, or a `reason` outside the token grammar (`[a-z0-9_]`, 1 to 64 bytes), takes its default and is logged, and the other fields stand; a `reversible` that is present but not a boolean is read as `false`, so a step that may have committed is treated as having committed:

```json
{"class":"release","reason":"...","retry_after_secs":300,
 "reversible":true,"promotion_pending":false,"detail":"..."}
```

`class` is `release` or `environment` (3.8); a step that dies without the line, or a hook that cannot run or panics, is `release`, and `environment` only when the hook says so. The hook does not set the phase: **the updater assigns `before_commit`, `gate_release`, `gate_environment`, `after_commit` or `halt` itself** from the step, the exit code and `reversible`. `retry_after_secs` is used with `75`. `reversible` says whether the hook can still undo what it has done (the updater reports it; it does not decide with it). `promotion_pending` is set by `verify` when the service is serving but not yet fully its own (3.8). `detail` is a short text for the log and the alert. The hook's stderr goes to the log.

Defaults, for an absent field or one read as invalid: `class` `release`, `reason` empty, `retry_after_secs` absent (the declaration's backoff applies), `reversible` `true` (except a present non-boolean, read as `false`), `promotion_pending` `false`, `detail` empty. A field the updater does not know is ignored.

**Every step acts on the hook's own durable record.** The updater does not know what a step did, and a step may be started again after a crash. A hook therefore keeps its own record (what it placed, what it changed, how far it got, whether it did something irreversible) and every step, `rollback` and `cleanup` included, decides what to do from that record and not from the order the updater called it in. In particular **`cleanup` after a failure must not commit**: the updater never calls it after a failure, but a hook must also refuse to act as a finish unless its record says `verify` succeeded.

**The commit.** A step that reports `"reversible": false` is the commit; if no step does, it is the success of `cutover`. A `cutover` that was killed by its timeout, or by a signal, is treated as irreversible unless the hook's record says otherwise: the updater asks the hook to decide, by running `rollback`. A hook that has an irreversible step of its own should put it in `cleanup`, after `verify`, so that `rollback` stays available through verification (tierstore's stop of v-current); a hook for which the visible change cannot be undone puts it in `cutover` (the js-agent's stop of the agent) and its `rollback` is then a repair that does not give back what was lost, which it says with `"reversible": false`. `verify` is bounded by `verify_deadline_secs` of the declaration, and if the deadline passes with `verify` not yet successful the updater runs `rollback` by itself.

**What the updater runs next, per outcome of each step.**

| step ran | success (0) | failure (1), timeout, killed | deferred (75) | halt (76) |
|---|---|---|---|---|
| `prepare` | `cutover` | `rollback`, then report `Failed` (phase `before_commit`, or `after_commit` if a step reported `reversible: false`) | `rollback`, then report `Deferred` | stop, run nothing further, report `halt` |
| `cutover` | `verify` | `rollback` (the hook decides from its record whether it was reversible), then report `Failed` | `rollback`, then report `Deferred`; only valid if nothing irreversible happened | stop, report `halt` |
| `verify` | `cleanup` | `rollback`, then report `Failed` with the hook's class | `verify` again with the backoff, until `verify_deadline_secs`, then `rollback` | stop, report `halt` |
| `rollback` | report the original `Failed` or `Deferred` | **before the commit:** report `halt` (a host nothing automatic can repair). **After the commit** (the hook reported `reversible: false`): exit `1` is `Failed` (phase `after_commit`); `halt` only if the hook reports it cannot repair (`76`, or `1` with no line or with `reversible: true`, a host the old release cannot be restored on) | run `rollback` again up to its bound, then as for failure | stop, report `halt` |
| `cleanup` | report `Succeeded` (with `promotion_pending` from the last `verify`) | run `cleanup` again, forward, up to `cleanup_retries`, then `Failed` (phase `after_commit`); **never `rollback`** | run `cleanup` again later, within the same retries | stop, report `halt` |

**The post-success watcher is outside this table.** After `cleanup` has succeeded and `verify` reported `promotion_pending`, the updater keeps running `verify` (idempotent) until it exits `0` without the flag, which clears the state. Any other result, or the updater's own **`promotion_ceiling_secs`**, ends the watch as `Failed` with phase `after_commit` and the hook's class, and **never runs `rollback`**: the commit has happened. The ceiling has one source of truth, the declaration's `promotion_ceiling_secs`; the updater applies it and passes it to the hook in the `--params` file under the reserved key `updater.promotion_ceiling_secs`, so the hook must not exit `1` for it. That key is one of the reserved `updater.*` keys of 2.4, which also carry the staged and previous release paths and the target and previous versions; the hook validates them against its own `state_dir` and declaration. A new order for the host stops the watcher first, before its `prepare`. A `halt` runs no further step. When it comes after the commit it skips `cleanup`, so a cordon the hook placed is not lifted by the update; because the cordon is a renewable lease (3.6) it expires, which is harmless for the case a `halt` stands for: a tainted js-agent refuses to start, so no work is lost to the cordon. If `rollback` fails **before the commit**, the host is in a state nothing automatic can repair, which is a `halt`; after the commit the table above decides (`Failed(after_commit)` unless the hook reports it cannot repair).

### 3.3 Which binary runs, from where, and what is trusted

**Trust.**
- The declaration is **root-owned and installed with the package**. A declaration that is not owned by root, or is group- or world-writable, or lives in a directory that is, is refused.
- The hook executable (binary or script) is **inside the artifact the updater verified** (sha256 and attestation). The updater runs a hook only from a staged release it verified; a hook from an unverified artifact never runs, as root or as anything. The check is made again when a step is resumed after a crash (the staged directory's digest is in the step record).
- Running the hook as root is never an effect of a runtime message: the registration socket carries liveness and version only (2).

**Which binary runs which step.**

| step | binary | from |
|---|---|---|
| `prepare <artifact>` | the **new** version's hook | the staged release, `<artifact>/<binary>` |
| `cutover`, `verify`, `cleanup` | the **new** version's hook | the staged release (or, once the updater has moved the link, the current path, which is the same file) |
| `rollback` | the hook of the version that did the cutover, i.e. the **new** one, because it knows what it changed | the staged release |
| `rollback`, **only if the new hook cannot run at all** (the binary is missing or killed by a signal on start; a hook that starts and then fails is the failure row of 3.2, not a reason to try another hook) | the **previous** version's hook | the previous release, which the updater keeps staged until `cleanup` has succeeded |
| any step of an update **to an older version** (a rollback of the fleet) | that older version's hook | its staged release; it is an ordinary update whose "new" version is the older one |

**The declaration and the package.** The declaration comes **with the release**: each artifact carries `updater.d/<service>.toml`, and the updater's own trusted install step, not the hook and not a runtime message, installs it into `/etc/updater.d/` after the artifact is verified and **before `prepare`**, because `prepare` runs the new hook and the new hook is declared by the new release. **The record is read one version back:** a hook writes its record so that the previous version's hook can read it (a `schema` field and a backward-read rule; the conformance suite writes with N and reads with N-1), because `rollback` may run the previous hook. **`min_version`** in the service definition is the first release that carries a hook; the coordinator's `last_good` never names an older one, and a fleet rollback below it goes through the first-install path (7). **The first release that carries a hook has no previous hook,** so it cannot be installed by the updater's hook path (there is no previous version's `rollback` to fall back to, and no declaration yet). It is installed through the interim workflow (7) as an ordinary package or release install, which also places its first declaration. A package manager that installs the same file on a host that has one is equivalent and wins; the updater installs the file only when no package manager owns it. Two copies are kept, the active declaration and the previous one, because `rollback` of the previous version and the fall-back above need the old rights. **A declaration may not widen rights by itself.** *Widening* is **any change other than removing an element from a set or lowering a number**, in **every** field: `signer`, `hook.user`, `group`, `uid`, `binary`, `capabilities` and `step_capabilities` (a step that gains a capability is a widening even if the total shrinks), `read_paths`, `write_paths`, `state_dir`, `units`, `address_families`, `environment`, `health_ports`, the keys of `[hook.params]`, the timeouts and every bound. A change of `signer`, `hook.user` or `binary` always needs approval, and any field the comparer does not know is a widening (fail closed). If the new declaration widens, the update is `Deferred` with the reason `rights_change` until an operator has approved that exact declaration (`updater approve <service> <sha256>`, a root act, audited); equal or narrower is installed automatically. A declaration with `hook.user = "root"` (the kbf hook, the js-agent hook) therefore **is `Deferred` as `rights_change` the first time it is installed**, until approved. This is expected behaviour, done once per host with `updater approve`, or once for a fleet by an approval file the operator installs (a root-owned `/etc/updater.d/approved`, a list of declaration digests); an approved digest is not asked about again. Also: the load rules keep a **reserved-path deny list** (`/`, `/etc`, `/usr`, `/boot`, `/root`, `/etc/updater.d`, `/etc/sudoers.d`, the polkit and systemd unit directories, the updater's own directories) that no `read_paths`, `write_paths` or `state_dir` may **name or contain** (a reserved directory is neither named nor an ancestor of an entry); a **single file inside** a reserved directory, such as the one declaration under `/etc/updater.d`, may be listed in `read_paths` and never in `write_paths`, and a grammar for paths and unit names that excludes systemd's `-`, `+` and `!` prefixes and anything but absolute paths. `[hook.params]` values are numbers and booleans unless the declaration lists a string key in its schema, which a hook that runs as root may not have unless whitelisted. A declaration installed before `prepare` is **restored** (the previous one reinstalled) if the update fails and rolls back. Reason: a compromise of a service's release pipeline can already run a hook of its choosing with the rights already granted; it must not also be able to grant itself more.

### 3.4 Rights: how a hook runs

The updater runs each step as a **transient systemd unit** with the properties its declaration fixes and nothing else (`systemd-run --wait --collect --pipe` with properties). From the declaration:

| declaration | systemd property |
|---|---|
| `hook.user`, `hook.group` | `User=`, `Group=` |
| `hook.step_capabilities.<step>`, falling back to `hook.capabilities` | `AmbientCapabilities=` and `CapabilityBoundingSet=` set to exactly the list for that step; `NoNewPrivileges=yes`. A capability is held only in the steps that need it (`CAP_NET_ADMIN` in tierstore's `prepare`, `cutover` and `rollback`, not in `verify` or `cleanup`) |
| `hook.read_paths`, `hook.write_paths` | `ProtectSystem=strict`, `ProtectHome=yes`, `PrivateTmp=yes`, `ReadOnlyPaths=`, `ReadWritePaths=` |
| `hook.address_families` | `RestrictAddressFamilies=` |
| `hook.environment` | `Environment=` of exactly those, and no inherited environment |
| `hook.timeout_secs.<step>` | `RuntimeMaxSec=` |
| (fixed) | `ProtectKernelTunables=yes`, `ProtectKernelModules=yes`, `ProtectKernelLogs=yes`, `ProtectControlGroups=yes`, `RestrictNamespaces=yes`, `RestrictRealtime=yes`, `LockPersonality=yes`, `MemoryDenyWriteExecute=yes`, `SystemCallFilter=@system-service`, `SystemCallArchitectures=native` |

**Controlling units.** A hook that must start or stop a unit (`hook.units`) needs authority over those units and no others. The first way: the updater installs a polkit rule generated from the declaration that grants `org.freedesktop.systemd1.manage-units` for exactly the listed units; the root job of migration step 3 shows `pkcheck` holds that rule to the listed units. **A hook never masks or unmasks a unit**: `mask` needs `manage-unit-files`, from which systemd's policy implies `manage-units` for every unit, so a rule that allows it cannot be held to the listed units (the same probe shows it); the updater never grants `manage-unit-files`. A hook that must keep a unit from starting does it with a condition the hook controls (for example `ConditionPathExists=` on a link in its `state_dir`, as the tierstore hook does). If a service's units cannot be covered by a unit-scoped rule on a supported host, the second way is a declaration with `user = "root"`, which is the widest right there is: it is accepted only with the approval of 3.3, and it keeps every other property above (a read-only filesystem except the declared paths, only the declared capabilities, a bounded environment). The kbf daemon's hook (4.3) is of the second kind today.

**Least privilege of the updater.** Two parts of one program, as the agent and the helper are today. The part that talks to the coordinator over mutual TLS, parses its reply and reads the registration socket runs unprivileged (`kbf-updater-agent.service:32-43`, empty capability set). The part that needs root runs only to **launch hooks with the declared rights, to install a verified release and its declaration, and to replace binaries**; it takes no free-form command, path or nft text from the other part, only "run step S of service N for version V", and everything it runs comes from a verified release and a root-owned declaration. It writes the step record (3.5). It is reached over a unix socket of mode 0600 owned by the one account (`local/serve.rs:1-30` is the pattern), and is concurrent: it serves queries and the step record on threads of their own, so a step that runs for an hour never delays a read of the record or the enforcement of a deadline.

#### 3.4.1 What a hook may trust

A hook that runs as the service's own account trusts nothing the service can write. The rules:

- **The record directory** (`state_dir` in the declaration) is created by the updater, owned by the hook's account (or root), mode **0750 where units execute from it** (the tierstore slot links: the kernel checks traversal for the service's user at `execve`), with the service's group as the group, and **0700 for a root hook with no such need**; it lies **outside every path the service's account can write**: the load rules refuse a declaration whose `state_dir` is inside the service's data or write paths. The hook's slot links, markers and lock live there. Because it must not be writable by the service, **the hook runs as an account other than the service's** (`hook.user`, for example `tierstore-update`, distinct from `uid`) unless it is `root`; the service may **read and traverse** only what its units must execute or read (the slot links and the releases they point to) through the group, and **write none of it**: the load rule that the service cannot write `state_dir` is checked for the group as well as the owner, and by `stat` at every step start.
- **Every value a hook reads** from its record, its params file or the environment is untrusted input: it validates ports, units and paths against the declaration (it never takes a port from the record).
- **The staged release tree** is root-owned and read-only (`/var/lib/updater/releases/<service>/<digest>/`, mode 0555, in root-owned parents), so it cannot be swapped between the digest check and the exec; the hook is executed from that path.
- **Polkit scope.** A rule that lets the hook's account manage the listed units attaches to the account, so it must be a hook-only account: with a distinct `hook.user` the service itself gains nothing. For a service that cannot have one, the root-with-restrictions option applies.
- **Reads are not confined by `read_paths`.** Under `ProtectSystem=strict` the whole file system stays readable, so `ReadOnlyPaths=` confines nothing and `read_paths` is a statement of intent (systemd's documented behaviour; no probe asserts it). A hook's inability to read a service's secrets rests on file modes and ownership: the secret files are readable only by the service's account and group (for example tierstore's key files, mode 0600), and the hook's account is in neither.
- **Test:** a state file planted in the service-writable area must not change what the hook does (9).

### 3.5 The step record, resume and the dead-man

Before each step the root part writes and fsyncs a **step record**: `{schema, service, target version, artifact digest, step, attempt, state: running, started (boot id and a monotonic base), deadline}`; when the step ends it records `done` with the exit code and the hook's last line. The record is the updater's memory; it holds no secrets and is versioned with a `schema` number (a record newer than the binary is read-only).

- **After a crash** of the updater, the root part or the host, the updater reads the record. A step that is `running` is **run again**, but never while the previous run may still be alive: hook steps run as transient units that outlive an updater crash, so the unit is named deterministically (`updater-<service>-<step>-<generation>`), and **resume first stops that unit and waits for it to end**, records that it did, and only then starts the step again. A hook also takes an **exclusive lock on its record directory for the whole step**, so a second copy would refuse. "Safe to run twice" means one after the other; the conformance suite adds a concurrency case (start a step, kill the updater, resume, assert a single writer). Before it kills a step for its bound, the updater reads the step's own `done` marker in the hook's record; a hook that finished and was killed anyway is read as finished. A `stop_begun`-style marker set with the signal never sent counts as irreversible and as `after_commit` toward the fleet count: conservative, and it is the hook's record that says so. A step that is `done` is not run again. The next step is the one after the last `done`. A step record under a different boot id is treated as running.
- **The dead-man.** The root part enforces the deadlines itself, on a thread of its own, whatever the unprivileged part is doing: a step that passes its bound is killed and recorded as failed; after `cutover` succeeds, if `verify` has not succeeded by `verify_deadline_secs` it runs `rollback`. So a host whose unprivileged updater is gone is still brought back, which is the property today's helper has (`local/core.rs:173`).
- **Resume and the first step.** If the artifact digest in the record no longer matches the staged directory, the update stops as a `halt` and pages; nothing from the directory runs.
- **Boot.** Nothing in the updater starts a service's units. A declaration may name a boot-time entry point (`boot = "restore"`) which the root part runs at its own start, before the units, with the same rights and step record; for tierstore it re-applies the rule for the active port and starts the active slot, and when the step record says a step is pending it follows the table of 3.2 (a pending `cutover` is rolled back). Services whose units have an `[Install]` (the kbf units) need none.
- **Updating the updater itself.** The updater and its root part are part of the kbf release and are updated by the kbf daemon's hook as today, but never inside the trial they guard: after `verify` of the kbf update has succeeded, a follow-on step stages the new binary beside the old, finishes the current step record, replies and exits cleanly, and systemd starts the new binary; an `OnFailure=` fallback unit flips the binary link back to the previous one after `StartLimitBurst` failed starts, and the test plants a binary that exits at start. A hook that needs a newer updater than the one running declares it (`min_updater_protocol`); the update is `Deferred` with the reason `updater_old` until the follow-on step has run.

### 3.6 Cordons and drains

A drain is the hook's. The generic rules, to which every hook that cordons or drains is held:

- **A drain bound that passes with work still running is `75` (deferred), never a stop.** The hook lifts what it placed (a cordon), exits `75` with `retry_after_secs`, and nothing is stopped. This is today's behaviour for kbf (`docs/design/updates.md`, section 4, step 2: it never installs over running leases) and the safe one wherever a stop can taint a host.
- **A cordon is a renewable lease**, not a fixed expiry: the hook sets an expiry of a few minutes and renews it at every step it takes while it waits, up to a cap from the declaration; a dead updater then costs minutes, a live one keeps the cordon through a long update. The hook records the cordon where `prepare`, `rollback` and `cleanup` can find it, so a cordon is lifted by whichever step runs last.
- **A cordon is per service, through that service's own route**: the kbf hook calls the frontend's own-node calls (`docs/design/updates.md`, section 5); the js-agent hook calls the lease server's own-host route (4.2). `kbf cluster drain` reaches kbf nodes only.
- **The js-agent route, as built in jobscheduler#545 [F] (merged as 65dcc94eb).** The cordon persists in the job registry's host record plus the lease server's agents state (not `js-store`), written before the `200` answer; a write failure answers `503` with `cordon-unsaved`. Routes: `GET /v1/hosts/{id}`, `POST /v1/hosts/{id}:cordon` with `{"lease_secs"}`, `POST /v1/hosts/{id}:uncordon`. Auth is the host credential of that same host id (or the one-time token that registered it) only: a foreign host, the pool token or a join token past its expiry gets `403` (`join-token-expired`), and a client token, a retired token (the server no longer knows it) or none gets `401`, and an unknown host id gets `409` `unknown-host`. The cordon lease defaults to 300 s with a per-request maximum of 3600 s (a longer request is cut to the maximum, `0` is refused with `400`); a repeat extends and never shortens; expiry lifts it lazily. The server has no total cap: the hook enforces `cordon_max_secs`, with 1 s of rounding slack. There is no placer identity, so `uncordon` lifts any cordon; the cordon reply's `already_cordoned` tells the hook whether it placed the cordon, and the hook uncordons only a cordon it placed, so an operator's manual cordon survives an update. The host reading adds `epoch` (+1 per hello) and `session_started_ms`. A hook that dies leaves its cordon to lapse within `lease_secs`.

### 3.7 What the updater reports

The heartbeat carries four facts per service today (`wire.rs:57-100`). The updater adds, per service: the step it is in and the attempt, the commit state, the outcome class, `promotion_pending`, and the duration of each step. They are shown in the coordinator's `/v1/status`. Alerts named by this design: `no_instance_up`, `halt`, `drain_bound` deferrals older than a service's cap, a cordon older than its cap, a step record that is `running` after its deadline, an artifact digest mismatch on resume, a declaration refused at load, an instance read-only for longer than its service says it should be.

### 3.8 Outcomes: Succeeded, Failed, Deferred, halt

The wire has two outcomes (`wire.rs:39-44`). A `Failed` for the desired version stops the coordinator from ordering that host again for it, keeps its slot, and makes the service `blocked` (`decide.rs:95-99`, `converge.rs:1-14`). A busy host that cannot drain within its bound is not a bad release, and must have none of those effects.

**`Deferred`** (a hook exits `75`). The update did not start or was stopped before anything irreversible, for a reason about the host's moment and not the release (`drain_bound`, `rights_change`, `updater_old`, a plan precondition). Its line says `class: environment`, since nothing about the release caused it. A hook's own waits and hints (how long `prepare` waits for a drain, the `retry_after_secs` it suggests) are values of its `[hook.params]`, like `cordon_lease_secs`, so an operator tunes them without a release. The hook has undone what it placed. It holds **no slot** and does not make the service `blocked`; the coordinator does not re-order the host until `retry_after` (`defer_backoff = { initial, factor, max }` in the service definition); convergence shows `deferred` hosts as a count.

**Failure classes.** A failed `verify` after `cutover` is classed by the hook: `release` (the new version is wrong) or `environment` (a check that depends on something remote or shared failed, such as the lease server being unreachable). Only `release` failures count toward automatic rollback of the fleet (5.3); an environment outage cannot roll a healthy release back. The shipped default of `rollback_after_failed` is a fraction of the set (and at least two hosts), never one.

**`halt`** (a hook exits `76`, or `rollback` fails): **a check whose failure no version can repair.** The failure means the host, not the release, is in a state that neither the new version, the old one, nor a retry can repair, so acting further can only make it worse. The first instance is a js-agent taint or an `owed-*` record: a tainted agent refuses every start, the old release included, and nothing clears a taint. Other services may declare their own. A `halt` runs no further step (3.2) and is reported as `Failed` with phase `halt`; it **pages**; it **halts the rollout of that service fleet-wide** (the coordinator orders no further host, the service's convergence state is `halted`, shown in the convergence JSON with the host and the check named); it is **not retried** and **never triggers automatic rollback**; and it is held until an operator clears it. **Only the operator token may clear it** (the same restriction as `urgent`, 5.2), every clear is audited, and setting another desired version does not clear it.

**`promotion_pending`** (set by `verify`): the service is serving but not yet fully its own (for a storage node, the cache promotion of the tierstore hook). The update is `Succeeded`, but the service reports `promotion_pending` in the heartbeat; the coordinator **holds the host's slot** until it clears; the updater keeps running `verify` (idempotent, so a watcher) with its own bound; a ceiling declared by the service turns it into `Failed` with phase `after_commit` where the service says it must, or into an escalated alert.

**Wire and compatibility.** `UpdateResult` keeps its two outcomes. The new information is optional heartbeat fields that old coordinators ignore (`docs/design/updates.md`, section 3): `deferred: { target, reason, retry_after_secs }`, and, on `last_update`, `phase: before_commit | gate_release | gate_environment | after_commit | halt`. **The agent uses them only after the coordinator advertises support.** The reply has a closed shape (`wire.rs:298`, `:324`), so the advertisement follows the existing precedent that a reply for another service is sent only to an agent whose last heartbeat carried `services`: a new agent adds `agent_features: ["deferred-v1", "halt-v1"]` to its heartbeat; a new coordinator answers a heartbeat that carries it with a reply that has `features` naming the ones it supports; an old agent never sends the field and never receives one; an old coordinator ignores it and never echoes it.

| agent | coordinator | what happens |
|---|---|---|
| new | new | the agent reports `deferred` and `halt`, declines the order for its persisted `retry_after`; the coordinator holds no slot and backs off |
| new | old | no `features` comes back: a deferred step is reported as `Failed` as today and the agent never declines an order it could accept; a halt is a plain `Failed` and the agent still does not retry or roll back itself (an old coordinator sees `blocked` for that version, but neither halts the fleet nor pages) |
| old | new | the old agent never sends the field; its failures are `Failed` as today |

The reason for the gate: under an old coordinator a host that declined orders would not cost nothing. An order the host does not act on ends only by ageing at `ORDER_AGE` (120 s, `fleet.rs:132-139`), and the next heartbeat orders it again (`decide.rs:100-110`), so the host would hold its role's slot about 120 s of every 135 s for the whole backoff. The coordinator is rolled first (5.3) and the agent half ships after it (8).

## 4. Hooks

Each service ships its hook with its own binary; the updater contains none of them (3). This section describes the hooks that exist or are planned. 4.1 and 4.2 are written by the service owners: what each of the five steps does, its exit codes and its declaration, with the tests that run in that service's own CI against the conformance suite (9).

### 4.1 tierstore: the port-forward hand-over (the tierstore hook)

> Restated as the tierstore hook (rev 4): `tierstore update-hook <step>`. The mechanics in 4.1.1 to 4.1.5 are what the hook's `cutover` and `cleanup` do and are the tierstore owner's; `forward-apply`, `forward-confirm`, `retire-slot`, "the executor" and "a job" mean steps of the hook, which keeps its own record. The updater's part is the generic step record and its deadline (3.5).

**Hook side.** The contract, code references, failure cases and tests are in [tierstore-handover.md](tierstore-handover.md).
The service registers liveness only: name `tierstore`, its version, health `GET /readyz` on its private port. Exit codes and
the last-line JSON are those of 3.2; every step reads the hook's record (`state.json` in `state_dir`, owned by the hook's
account, outside the service's write paths) through a validator that accepts only the two declared ports and units, a
fixed set of modes and markers, and sets state, so a re-run after a crash converges. A value outside them is `1` with no
`nft` or `systemctl` call.

| step | what it does | why a re-run converges |
|---|---|---|
| `prepare <artifact>` | `tierstore --capabilities` of both releases must list `handover-v1` (else `mode=restart`); `75` if the guard, conntrack timeout or table fill fails; start v-next on the idle port, read-only; wait for `/readyz` | idle port derived from the state; link, `systemctl start` and guard table are set-to-state |
| `cutover` | the 4.1.2 swap in one `nft -f`; probe through 9300 until v-next answers; on a failed probe swap back, exit 1 | the file replaces the table and names the port |
| `verify` | the gate: counted probes, the staged version; exit 0 with `promotion_pending` while v-current holds the lock (always, before `cleanup`); after `cleanup`, wait for `read-write` up to `promotion_bound_secs`, then `0` with `promotion_pending`; **no ceiling in the hook**, the updater applies `promotion_ceiling_secs` | observation only |
| `rollback` | swap back, stop v-next; valid only before `cleanup` writes `stopping`; after that `1` with `reversible:false`, which is `Failed(after_commit)` | stop of a stopped unit and a repeated swap are no-ops |
| `cleanup` | **the commit point**: without `verified` it exits `1` and stops nothing; with it, write `stopping` (every exit then says `reversible:false`), remove the old slot's link first (its unit's `ConditionPathExists=` then keeps a crash `Restart=` or a manual start from bringing it back; the running process keeps its exec), then stop v-current (70 s settle, drain, exit), then clear `previous`; no mask; re-run forward up to `cleanup_retries` | each part is set-to-state |

Declaration: `hook.user` `tierstore-update`, not the service's account; `CAP_NET_ADMIN` in `prepare`, `cutover`,
`rollback` only (`hook.step_capabilities`); `AF_NETLINK`; units `tierstore@9301`, `tierstore@9302` from one template
(`%i` is the port, `--drain-lb-wait 70s`, `--proxy-id tierstore-%i`, `ExecStart` under `state_dir/slots`, `ConditionPathExists=` on its slot link under `state_dir/slots`); lock
`<cache>/.lock` or `/var/lib/tierstore/instance.lock`; tables `kbf_forward_tierstore`, `kbf_guard_tierstore`; timeouts
600, 300, 1000, 600, 1300 s, deadline 1600, ceiling 3600, `promotion_bound_secs` 900. At boot the declaration's
`boot = "restore"` runs `tierstore update-hook restore` before any unit: it re-applies the rule and starts one slot (the
previous slot if an update was in flight and not past `stopping`). No unit is enabled. Asks of the 2.4 example: the
declaration in `read_paths` (the validator reads the ports and units from it), `state_dir` mode 0750 with the service in
its group (the slot links must be executable by the service).

New in tierstore: wildcard listeners (a repeatable `--listen`, `IPV6_V6ONLY` explicit; `--listen` is one `SocketAddr`
today, `server/cli.rs`); the cache lock, which decides the mode (an instance that finds it held is read-only and takes
it by itself when it frees, so there is no promote verb and a reboot, crash or hung v-current all resolve); the drain
(`Connection: close` from drain start; a lingering close of idle connections at the end of the settle; the race that
remains is counted); clients never retry (a retried create-only put is ambiguous). Storage node: a proxy id per slot, the
reconciler gated on `--lock-file`, a `dir:` hot tier keeps the plain restart. Metrics: the directory gauges double-count
while both run; the build and mode gauges are new.

**Shape [D].** Clients always call the public port, here 9300. No process listens on it. Each tierstore instance listens on its own private port, 9301 or 9302, alternating. One nftables redirect per family sends public-port connections to the current instance. In hook terms (the tierstore owner restates this): `prepare` starts v-next on the idle private port in read-only mode and waits for its `/readyz`; `cutover` swaps the rule (4.1.2) and observes v-next through the public port; `verify` is the gate and reports `promotion_pending` while v-next has not taken the cache lock; `rollback` swaps back and stops v-next; `cleanup` stops v-current (the irreversible step, after `verify`), waits out the settle and retires the old slot. v-next takes the cache by itself when v-current's lock is released (4.1.6).

#### 4.1.1 The ruleset and the listeners (what the cutover step does; the tierstore owner's from now on)

One `inet` table per service for the redirect and one for the guard. The `inet` family handles IPv4 and IPv6 in one rule; NAT in an `inet` chain needs Linux 5.2 or later (nftables wiki, "Performing Network Address Translation (NAT)": stateful NAT in the inet family "since Linux kernel 5.2") **[V on the oldest supported kernel]**. For an older kernel the same rules are generated twice, once for `ip` and once for `ip6`. The families generated are those the hook's own configuration lists (a service that is IPv4 only gets no IPv6 rule).

```
table inet kbf_forward_tierstore {
    chain pre {
        type nat hook prerouting priority dstnat; policy accept;
        fib daddr type local tcp dport 9300 redirect to :9301
    }
    chain out {
        type nat hook output priority -100; policy accept;
        fib daddr type local tcp dport 9300 redirect to :9301
    }
}

table inet kbf_guard_tierstore {
    chain in {
        type filter hook input priority filter; policy accept;
        iifname "lo" tcp dport { 9301, 9302 } accept
        tcp dport { 9301, 9302 } ct status dnat ct original proto-dst 9300 accept
        tcp dport { 9301, 9302 } drop
    }
}
```

The nft syntax above is the intended text; the first rule-generation test loads it with `nft -c -f` in a root network namespace to pin it **[V]**. Points about it:

- **`fib daddr type local` on both rules.** Without it, `tcp dport 9300` in the output chain also redirects the host's own outgoing connections to port 9300 of *other* hosts, and in prerouting it would redirect forwarded traffic if the host routes. The match restricts the rule to addresses that are the host's own. It is valid in both hooks without an interface qualifier (kernel `nft_fib` validation; reviewed **[V]**).
- **Redirect, not DNAT; and what the listener must therefore be.** `redirect` rewrites the destination to the local machine. For packets arriving from outside the destination becomes the **first address of the incoming interface** (IPv4: the first address of the interface; IPv6: the first usable address of matching scope); for locally generated packets it becomes 127.0.0.1 or ::1 (iptables-extensions, REDIRECT; the kernel's `nf_nat_redirect` follows it, reviewed **[V]**). If the incoming interface has no usable address the packet is dropped. So the private listener must accept connections on **both** the node's addresses and loopback: it must listen on the **wildcard** of each family. A loopback-only listener behind this rule refuses every remote client; this document and the tierstore deep dive must not say otherwise.
  What tierstore's listener must be: **two sockets per private port, `0.0.0.0:P` and `[::]:P` with `IPV6_V6ONLY` set explicitly** (so the outcome does not depend on `net.ipv6.bindv6only`), or, for an IPv4-only service, the first alone. `--listen` is one `SocketAddr` today (`komira-ai/tierstore:crates/tierstore/src/server/cli.rs`, the `listen` field), so this is new tierstore work: a repeatable `--listen`, one value per bind, with an explicit `IPV6_V6ONLY`, which is what the tierstore owner's section already specifies.
  The alternative, `dnat to 127.0.0.1:P` with a loopback-only listener, does not work for packets from outside unless `net.ipv4.conf.<interface>.route_localnet=1` is set (kernel documentation: "Do not consider loopback addresses as martian source or destination while routing. This enables the use of 127/8 for local routing purposes", default false). That setting makes the host accept packets to 127/8 from the wire for every service on the interface, a known attack surface. **Chosen: redirect plus wildcard listeners plus the guard (Question 6).** The price is that the private port is open on every interface unless the guard is loaded; the guard is therefore loaded by `prepare` and re-applied by the hook's boot-time `restore`.
- **A trap in the guard.** After the redirect the packet reaches the *input* hook with destination port 9301, not 9300. A host firewall that allows 9300 from some networks stops matching: remote callers are dropped by the host's own policy even though the redirect worked. The guard's second rule accepts the redirected flows in the guard table, but an accept ends only its own base chain; another table's drop or default-drop policy is **not** overridden. So the operator's firewall must match `ct original proto-dst 9300` instead of `dport 9300`. This is stated in the service's packaging notes and checked by a test that connects from a veth peer with a restrictive second table loaded (9).
- **The third rule drops** anything else to the private ports, so a remote caller that addresses 9301 directly reaches nothing. Loopback sources are accepted (the first rule), so the hook can probe v-next directly. Any local process can reach the private port directly too; that gives it nothing it lacks on the public port, because the service authenticates every request itself. The guard does not distinguish interfaces beyond `lo`; there is no UDP service on these ports.

#### 4.1.2 The atomic swap

The swap is one file given to one `nft -f`, containing

```
add table inet kbf_forward_tierstore
flush table inet kbf_forward_tierstore
add chain inet kbf_forward_tierstore pre { type nat hook prerouting priority dstnat; policy accept; }
add chain inet kbf_forward_tierstore out { type nat hook output priority -100; policy accept; }
add rule inet kbf_forward_tierstore pre fib daddr type local tcp dport 9300 redirect to :9302
add rule inet kbf_forward_tierstore out fib daddr type local tcp dport 9300 redirect to :9302
```

The same file installs the rules the first time (`add table` is a no-op when it exists), applies a swap and applies a rollback; only the port differs. The wiki ("Atomic rule replacement") says `nft -f` reads the whole file, builds the new objects beside the existing configuration and swaps "in one single transaction", so "there is no moment when the firewall is partially configured"; it documents `flush table` at the top of a file for exactly this use. A packet is evaluated against the old ruleset or the new, never a mix and never an empty chain. The guard table is separate and is not in the file, so a swap never flushes it. `flush table` does not clear sets; the redirect table has none (the guard's port set is inline).

What clients see during a swap: nothing. The redirect runs only for the first packet of a connection (wiki: "No rule lookup happens for follow up packets in the flow"); a SYN just before the swap is mapped to v-current, one just after to v-next, and neither is dropped or refused by the swap. The swap is the hook's `cutover`: it records its intent in its state file before it applies, probes through the public port to confirm, and swaps back itself if the confirm fails. A crash between the apply and the record is resolved by the updater re-running `cutover`, which is idempotent, or by the updater's dead-man running `rollback` when `verify` has not succeeded by its deadline (3.5). Not claimed: that the swap is free of every race; 4.1.3 names the ones that matter.

#### 4.1.3 Conntrack

A flow's NAT mapping is stored in its conntrack entry when the first packet creates it, and every later packet of the flow uses that entry, whatever the rules now say. So connections established before the swap keep going to v-current, which is what the hand-over needs; connections made after go to v-next.

- **The handshake race and the settle.** A connection whose SYN was mapped to v-current just before the swap may still be completing its handshake, or sit in v-current's accept queue, when the swap happens. v-current must **keep accepting for a settle period after the swap** and only then stop; closing the listener resets what is queued. The existing `--drain-lb-wait` does this (`server/mod.rs:596-615`); its meaning changes from "time for a load balancer to notice" to "time for connections already mapped to me to arrive". It is a config value and never zero here.
- **SYN retransmits beyond the settle, reasoned from conntrack.** A client whose SYN is unanswered retransmits at about 1, 3, 7, 15, 31 and 63 s after its first SYN (Linux default `tcp_syn_retries=6`; the kernel documentation gives 131 s as the total before it gives up, which includes the last wait after the final retransmit, so the last SYN that can arrive is the one at about 63 s). What the swap does to a retransmit depends on whether the first SYN created a conntrack entry. (1) If the first SYN reached the host before the swap, the entry exists with a NAT binding to v-current's port; its retransmits keep that mapping (the rule is not consulted again), whatever the swap did. Such a flow exists only if v-current did not answer (the SYN queue or backlog was full, or the SYN-ACK was lost on the way back). The entry lives in `SYN_SENT` for `nf_conntrack_tcp_timeout_syn_sent` (120 s by default, verified against the kernel documentation). If v-current has by then closed its listener, the retransmit is refused. (2) If the first SYN never reached the host, no entry exists; the retransmit is a new flow and the swap sends it to v-next: harmless. So a SYN aimed at v-current after the swap is harmless only in case (2). The 10 s default of rev 1 does **not** cover case (1) past 7 s. The quantity that matters is the **last retransmit still mapped to v-current**, measured from the swap: a flow whose first SYN arrived just before the swap sends its last mappable SYN about 63 s after the swap. The settle runs from the stop of v-current, which is after the swap and after the gate, so **a settle of about 70 s from the stop covers a default client** with a margin, and costs only update time because v-current serves everything throughout (rev 2 said 130 s, derived from the give-up time; that was the wrong event). The other way to cover it is the executor removing the `SYN_SENT`/`SYN_RECV` entries mapped to the old port at the end of a shorter settle, so retransmits become new flows (a conntrack netlink operation in the hook, more machinery). **Recommended: the 70 s settle** (Question 13). The guarantee assumes the client uses the operating system's default `tcp_syn_retries`; a tuned value voids it, a newer kernel with `tcp_syn_linear_timeouts` shortens the schedule (about 67 s total), and the documentation says so.
- **Idle flows and conntrack timeouts.** The established-TCP timeout is `nf_conntrack_tcp_timeout_established`, default 432000 s (5 days). A keep-alive connection idle longer than its entry's timeout loses its entry. When the client then sends on it, the packet is not a SYN, but with `nf_conntrack_tcp_loose` enabled (the default) conntrack picks it up as a new entry and the NAT hook runs for it: it is mapped by the **current** rule, which after a swap is v-next, and v-next answers with a reset. Before the swap the same pickup would have been mapped to the same port as the socket and worked, so the hand-over adds one failure mode, for one kind of flow. Two bounds close it: the service closes idle keep-alive connections itself after its idle bound (`header_timeout`, 60 s default, `server/mod.rs:346`, `:409`), far below five days; and `prepare` exits `75` if `nf_conntrack_tcp_timeout_established` read from `/proc` is not longer than that bound plus a margin. Both are configuration checks, not timing.
- **Conntrack pressure.** An entry exists per flow, with its NAT binding. A full table (`nf_conntrack_max`) drops new flows, and, **as I understand the kernel (unverified [V])**, early drop evicts unreplied, non-assured entries first: a handshake in `SYN_RECV` can lose its entry, so its final ACK is picked up loosely and mapped by the current rule, to v-next, which has no such connection, while v-current holds a half-open socket. Established, assured flows are evicted last, so draining flows are mostly safe. `prepare` reads `nf_conntrack_count` against `nf_conntrack_max` and exits `75` above a threshold from the hook's configuration. This design adds the failure mode for handshakes in flight at swap time, so "with or without this design" was wrong in rev 1.
- **Other failures to name.** `conntrack -F` drops all mappings: later packets on established flows are picked up as new entries and mapped by the current rule, so a flush during the drain resets the flows still on v-current. The hook does not run `conntrack`.

#### 4.1.4 On-node callers

A process on the host connecting to 9300 goes through the **output** chain (its destination is local, so `fib daddr type local` matches), mapped to 127.0.0.1:P or ::1; a container on a bridge arrives at **prerouting** like a remote caller. A process that connects to the node's own LAN address uses the output chain as well. Loopback must be up in the namespace the rules live in (a test namespace forgets).

#### 4.1.5 Readiness and metrics on private ports

The probes (`/healthz`, `/readyz`) and `/metricz` are served by the same listener as the data path, so they exist on each private port. The hook probes v-next directly on `127.0.0.1:<idle port>` (accepted by the guard's first rule) and probes the public port from the host to see who answers it (the build gauge names the slot). A remote scraper or a load balancer that addresses 9300 sees whichever instance is current and never the other. A scraper that wants both instances scrapes the node's two private ports locally; the instance label is the service's proxy id, which differs between the instances (the unit comments already require "one of its own" per process over the same tiers, `komira-ai/tierstore:packaging/tierstore/tierstore.service`). Counters reset per process, as they do at any restart.

#### 4.1.6 What the hook needs from the service

The service-side contract is in the deep dive; this is what the hook relies on, with the points that rev 2 changed.

- **Promotion is self-promotion on the cache lock.** There is no promote signal and no promote verb. Every instance tries the exclusive, non-blocking lock on the cache directory at start and on a polled interval; the one that holds it is read-write, the others are read-only and promote themselves when the lock frees, which is when v-current exits. Reasons: the unprivileged updater cannot signal a process of another account, the hook runs with no right over the service's process beyond its units, and a release without a handler for the signal would be killed by it (tierstore handles only SIGTERM and SIGINT, `server/cli.rs:924-926`). It also covers a **reboot**: the one instance that starts takes the lock and is read-write, so the mode is a function of the lock and not of an in-flight update. Requirements on the lock (the owner's section carries the detail): `O_CLOEXEC` and no inherited descriptors (the signer documents the trap, `crates/kbf-signer/src/server.rs:118-134`), `O_NOFOLLOW`, a local filesystem checked at open. `/readyz` still means "serves", and the mode shows in the body and in a `tierstore_cache_mode` gauge; the hook's `verify`, once `cleanup` has stopped v-current, waits for `read-write` before it reports no pending promotion.
- **Where the lock lives.** For a storage node the lock file must be in a directory nothing removes: a `StateDirectory=` (or `/var/lib/...`) shared by both slots, **not** a `RuntimeDirectory=`, which systemd removes when the unit that owns it stops and would unlink the file under v-next, after which a third instance would create a new one and two processes would each hold "the" lock. The holder also re-checks, periodically while holding, that the file it locked is still the file at the path (`fstat` against `stat`), not only once after taking it. A build node's lock in the cache directory is fine. (For the tierstore owner's section.)
- **The wait for read-write after commit is bounded, is a heartbeat state, and is resolved.** Taking the lock runs `clear_stage`, a scan and an index replacement, which can take minutes on a large cache. The hook's `verify` watches `cache_mode` for `promotion_bound_secs` (900, in `[hook.params]`, sized from the cache); before `cleanup` it always exits `0` with `promotion_pending`, because v-current still holds the lock. If the bound passes afterwards, the update is `Succeeded` and the service reports the state `promotion_pending` in the heartbeat (3.8). The coordinator **holds the host's slot** while the state lasts, so the next host is not ordered into a fleet that is read-only, and the updater keeps running `verify` after it has reported (a post-success watcher with its own bound), so a late promotion clears the state. The declaration's `promotion_ceiling_secs` (3600), applied by the updater and passed to the hook as `updater.promotion_ceiling_secs`, turns it into `Failed(after_commit)` on a storage node and a build node alike (on a storage node a v-next that never promotes copies nothing from the hot tier to the cold one and the hot tier fills); the hook itself never exits `1` for it. On timeout `verify` names the holder of the lock in `detail`, read from `/proc/locks` (world-readable **[V]**), so the hook needs no root.
- **The first release with the lock** cannot be handed over to or from a release that has no lock (an older v-current runs without it and would race v-next's `.stage/` cleanup). The `requires = ["handover-v1"]` capability (3.3) makes `prepare` record `mode=restart` in that case (a plain restart with a gap).
- **The drain.** `Connection: close` on every answer from the drain's start. At the end of the settle the server closes idle keep-alive connections with a **lingering close**: `shutdown(SHUT_WR)`, keep reading until the peer's EOF, then close; a request already received is served (with `Connection: close`), bytes that arrive after the FIN are dropped and counted. A plain close of an idle connection races a request the client has already sent and the client sees a reset with no response byte; the half-close removes that race for a conforming HTTP/1.1 client. Requests on already-open connections are served until the connection closes, bounded by the drain deadline for a client that never closes. Today's drain answers 503 on connections it still holds from the moment it stops accepting until in-flight work is done (`server/mod.rs:614`, `:748-749`); that would turn every keep-alive client of v-current into a failure after the swap, and the drain is the main service change for this strategy.
- **One client policy.** Clients do **not retry**. The zero-failure claim holds without retries, in this document, in the deep dive and in every test. A retried create-only PUT is ambiguous (a 412 after a retry cannot tell the retry's own earlier success from a competing writer), so the hammering clients never retry and any failure fails the test.

#### 4.1.7 Alternatives considered for the hand-over itself

Two ways to hand over a listening socket without a second port, conntrack or a root `nft` were weighed.

- **Socket activation by the service manager.** The socket is held by the manager and survives the process, so a restart refuses nothing. It was built and parked as a draft pull request for reference (`--listen-from-systemd`, kbf#2091). It covers a restart, not an overlap: the new and the old process cannot both be set up as separate instances over one socket unit, and the drain changes it needs are the same ones this design needs. It also puts the socket in the manager's unit system, one more place to keep in step with the flags.
- **`SO_REUSEPORT` with `tcp_migrate_req`** (kernel 5.14 or later). Two processes bind the same port; the kernel can migrate connections queued on a closing listener to another listener in the group. It has no rule to swap and no conntrack dependence. It is not chosen because the kernel decides how connections are spread between the two listeners while both run, so there is no moment at which "all new connections go to v-next" can be asserted or reverted, there is no equivalent of the confirm before the old process is stopped, and it needs a kernel feature every supported host would have to be checked for. The frontend studied file-descriptor passing against `SO_REUSEPORT` (`docs/design/`, frontend handover) with its own constraints.

The forward was chosen because the swap is one atomic, reversible, observable step with a confirm, at the price of a netfilter dependency (conntrack sizing, firewall coexistence, the `flush ruleset` hazard of 3.5). That is the decision; it is recorded here so it is not reopened without a new fact.

### 4.2 js-agent: lease-drain-restart (the js-agent hook)

Written by the js-agent owner as `js-agent update-hook <step>` under the rules of 3.2 (contract, commit point), 3.6 (cordons, drains) and 3.8 (outcomes). Facts are from the jobscheduler repository: **[F]** is merged code on its main (a path or PR is given), **[F-open]** an open pull request (jobscheduler#509 the farm unit, #493 the image pull and the store lock, #516 the `crun` runtime wiring, #507 the keeper; all four have since merged, and the facts that depend on them are marked **[F]** with their merge commits), **[new]** work this design adds, **[D]** a design choice, **[V]** to verify before building on it.

**The shape [D].** The hook cordons the host, waits for it to hold no lease, and only then stops the agent, links the staged release and starts it, and waits to see it join the lease server again. **The commit point is the success of `cutover`** (3.2). Today's text put it at the SIGTERM; the two differ only in that a `cutover` which fails between the stop and the start has already done the irreversible part. The updater then runs `rollback` (3.2), and the hook decides from its record (below) that the agent was stopped and reports `"reversible": false`. Everything before `cutover` can be aborted: a drain bound that passes with a lease still running exits `75` and the agent is never signalled.

The agent is never killed first. Nothing inside the agent ties `crun run` to the agent's life until the keeper exists: only a graceful exit kills it, and there is no parent-death signal (`PR_SET_PDEATHSIG`), so after a crash (SIGKILL, abort) `crun run` and its container keep running. What ends them is the unit: lease cgroups sit under the unit's delegated cgroup (`<unit>/actions/<lease>`), and when the main process dies systemd stops the unit and `KillMode=mixed` kills everything left in it before any restart **[F]** (the unit and the test that asserts it are jobscheduler#509, merged as abd519c95; the in-code comments that still say otherwise are corrected by jobscheduler#536). This holds **only for an agent run under that unit**. The start sweep then clears the stale lease state **[F]** (jobscheduler#508). No lease is handed over: a job finishes before the stop or the update does not pass `prepare`; the lease server reruns a job from its rerun budget only when the agent or the host dies on its own.

**What exists.**
- *The agent's own drain [F]* (`crates/js-agent/src/lib.rs`, `cli.rs`): SIGTERM or SIGINT sends a heartbeat with the phase `draining` at once, takes no new job, lets running jobs finish for `--drain-wait` (default the stop grace, at most 3600 s), stops the rest after `--stop-grace` (default 10 s, at most 3600 s), keeps heartbeating until the server has acknowledged every result, then exits 0. A second signal ends it at once. After the hook's own drain it finds no lease and returns quickly; it stays the worst-case bound of the stop.
- *The unit [F] (jobscheduler#509, merged as abd519c95)* (`packaging/js-agent/js-agent-crun.service`): `Delegate=yes`, `DelegateSubgroup=supervisor` (agent in `<unit>/supervisor`, leases in `<unit>/actions`), `KillMode=mixed`, `--drain-wait 3600 --stop-grace 120`, `TimeoutStopSec=3900`, `Restart=always`, `RestartSec=30`. A host that lacks what `crun` needs makes the agent exit 2 with every missing piece named (`crun_host.rs`).
- *The sweep [F]* (jobscheduler#508): `CrunRuntime::open` removes every lease whose sidecar (`<scratch>/oci-labels/*.json`) names this agent id: kills what runs in the lease cgroup, deletes the container, the cgroup and the directories, then the sidecar. It leaves another agent's and malformed sidecars alone and reports them; a lease it cannot remove keeps its sidecar for the next start. The swept runs are lost, not adopted.
- *Taint and owed checks [F]* (`lifecycle/mod.rs`): a marker under `--state-root` taints the host; an `owed-*` record means a job's checks did not finish, and a restart or SIGTERM inside that window taints the next start. A tainted agent refuses every start (`host-tainted`) and nothing clears it: "the host is reimaged".
- *Locks [F] (jobscheduler#493 and #516, merged as fcc025a1f and 587f72c69)*: agents take the image store's lock shared; the start-time stage sweep runs only if `LOCK_EX|LOCK_NB` succeeds; #516 adds a per-scratch-root claim, so a second `crun` agent on the same roots is refused.
- *The server's view [F]*: the hello carries `agent_version` (`js-agent-wire/src/hello.rs`); `GET /v1/hosts` lists hosts with it (`js-lease-server/src/hosts.rs`); kbf already has a typed client (`kbf-lease-client`). A second hello for a live host id is a 409 `host-live`, retried with backoff.
- *Cordon [F]*: `js-sched` has `Cordon`, `Drain(deadline)` and `Uncordon` as operator actions on a worker; a drain never kills a lease and pauses at its deadline (`js-sched/src/cordon.rs`, `js-server-core/src/core.rs`); the rows persist (`js-store/src/cordon.rs`). There was no HTTP route for them in the lease server or `js-cli` when this was written; the own-host route is built (3.6) and persists in the job registry and agents state, not `js-store`.
- *`js-agent --version` [F]*: clap prints the package version. The line `runtimes: docker crun` landed with jobscheduler#516 **[F]** (587f72c69); the runtime in the hello is a pending addition to the hello (`contract.rs`) **[new]**.

**Cordon: a prerequisite, not a choice.** The hook cordons and uncordons through the own-host route of the lease server (`POST /v1/hosts/{id}:cordon`, `:uncordon`, `GET /v1/hosts/{id}`, for the host in the credential the hook presents) **[new at the time of writing; built in jobscheduler#545, see 3.6]**; without it a busy host never reaches zero leases (migration step 9 `needs` it, 8; Question 17). Per 3.6 the cordon is a renewable lease, and the hook records it (see `cordon_placed`) where every step can find it. The agent's SIGTERM `draining` heartbeat is not a substitute: it is sent only at the stop.

**The hook record [D].** Every step decides from it (3.2), not from the order it was called in. It lives under `/var/lib/js-agent-update` (see the declaration) and holds: the target and previous release; `cordon_placed` and the cordon's current expiry; `stop_begun` (written and fsynced **before** `cutover` signals the unit, so a `cutover` killed or crashed at any later point leaves it set); `link_moved` and `start_issued` (each written and fsynced **before** the act it names; a rerun checks the real state, see below); and `verify_ok` (written by the first successful `verify`). `stop_begun` is what tells `rollback` that the agent was stopped and that its runs are gone: with it set, a failed or killed `cutover`, and every `rollback` after it, reports `"reversible": false`. With it unset (a `cutover` that failed before the signal) `rollback` has nothing to repair beyond the cordon and reports `true`. `rollback` adds its own sub-step marks, each written (and fsynced) **before** the act it names, except where marked: `rb_drained` (the bounded wait of the table saw no lease), `rb_stop_begun` (before the SIGTERM), `rb_link_restored` (before the rename), `rb_start_issued` (before the start), `rb_hello_ok` (after the previous version's hello was seen). `rb_drained` and `rb_hello_ok` record what was observed, so they follow it; every mark that names an act precedes it.

**The record directory is not the service's [D].** `/var/lib/js-agent-update` is `root:root`, mode `0700`, and not in the agent's or the job user's read or write paths; no job can write it, so a compromised job cannot steer a `rollback` that runs as root. The agent itself runs as root on `js-agent-crun.service` (it launches crun as the job user), so the record does not protect against a compromised agent, which holds root already; the hook opens the agent's state root read-only, and `StateRoot::open`'s owner-equals-euid check holds because both are root. This is 3.4.1 for a hook that runs as root: the declaration names the directory as `state_dir`, and the load rules refuse it inside any path the agent or the job user can write. Every step takes an exclusive `flock` on it for the whole step (`LOCK_EX|LOCK_NB`; a second copy refuses with exit `1`, having changed nothing, as 3.5 says); the updater also stops the old transient unit of a resumed step by its deterministic name and waits for it before starting the step again (3.5), and the lock is the backstop for a step that outlives its unit. Steps therefore never run concurrently on resume. **Every value read from the record is validated against the declaration before it is used:** a release path must lie under the declared `<release dir>`; the unit name must equal the declared `units` entry; the previous and target versions must match the update order; the cordon expiry must be a number no later than `cordon_max_secs` after the first placement; the schema must be known. A record that fails validation is not acted on: the step exits `1` and changes nothing.

**The steps.**

| step | what it does | exit codes |
|---|---|---|
| `prepare <artifact>` | Refuse (exit `1`, nothing changed) if the staged release is not an agent of this service, if its unit's flags or cgroup layout (`supervisor`, `actions`) differ from the running one's **[new]**, or if `<staged> --version` does not report the runtimes the declaration requires (`runtimes: docker crun`, jobscheduler#516). Refuse with `76` if the host is tainted or an `owed-*` record exists (no version can repair it, and the old agent would refuse its next start). Write the hook record (intent), cordon through the own-host route, and wait up to `drain_wait` for `GET /v1/hosts/{id}` to show no lease. | `0`; `75` if the bound passes with a lease still running: the hook lifts the cordon it placed, nothing is stopped, `retry_after_secs` is the service's backoff (the updater then runs `rollback`, which finds nothing left to lift); `76`; `1` (the updater runs `rollback`, which lifts a cordon placed) |
| `cutover` | Record `stop_begun`, stop the unit (SIGTERM; the agent's own drain, at most `drain_wait + stop_grace`, inside `TimeoutStopSec`; only then does `KillMode=mixed` kill what is left), link the staged release, start the unit and wait for it to be active. **The irreversible stop is here:** the JSON line says `"reversible": false`, on failure as well as on success, and so does every later `rollback`. It does not repair before it exits `1`: the updater runs `rollback`, also after a timeout or a kill. Each of the three acts is a no-op when already done, so a rerun after a crash goes forward from whatever the unit and the link show. | `0`; `1` |
| `verify` | All of: a hello after the start carrying the staged `agent_version` and `runtime=crun`; the sweep ran clean (no foreign or malformed sidecar, no lease kept; `SweepReport` is not reported outside the log today **[new]**); no taint and no `owed-*` record; the host `ready` in `GET /v1/hosts/{id}` for `bake_polls` consecutive polls. May be run again and again. Classed below. | `0`; `1` with `class`; `76` on a taint or an `owed-*` record |
| `rollback` | Run after a failed, timed-out, killed or deferred `prepare` or `cutover` and after a `verify` that failed or passed its deadline. **A repair, not a restore:** runs stopped at the cutover are not brought back, which is why `"reversible": false` once `stop_begun` is set. It decides by entry state, described under the table (**Rollback by entry state**); it ends by waiting for the previous version's hello, then uncordons only if `cordon_placed`, and deletes the hook record (no `cleanup` follows a rollback). | `0`; `76` if an `owed-*` record or a taint appears at any point; `1` (with `"reversible": false` once `stop_begun` is set, which after the commit is `Failed` with phase `after_commit`, not a halt: 3.2, 3.8) |
| `cleanup` | Run only after `verify` succeeded; refuses (exit `1`, changes nothing) if the record lacks `verify_ok`. Uncordon, **only if this update placed the cordon** (`cordon_placed`); delete the hook record. A cordon that was there before is left. | `0` |

**Rollback by entry state [D].** `rollback` first reads the unit (`systemctl show`), the release link and the record, and takes the first row that matches. The record decides which sub-steps were done; the unit and the link are checked against it, and a mismatch is trusted in favour of what the system shows (a sub-step whose effect is already visible is skipped).

| entry state | what `rollback` does |
|---|---|
| (c) `stop_begun` unset: the agent was never signalled (a `prepare` or early `cutover` failure) | Nothing to repair. Uncordon if `cordon_placed`, delete the record, exit `0` with `"reversible": true`. |
| the unit is `deactivating` (a `cutover` killed during its stop) | Wait for it to become inactive, at most `TimeoutStopSec` (3900 s); then (a). |
| (a) the unit is stopped, inactive or failed (a failed or killed `cutover`) | Relink the previous release (`rb_link_restored`), start the unit (`rb_start_issued`), wait for the hello of the **previous** version with `runtime=crun` (`rb_hello_ok`). |
| (b) the unit is active and the link is at the staged release (a failed `verify` or a passed `verify_deadline_secs`; the new agent runs) | The cordon is still held (`cleanup` has not run), so the new agent should hold no lease, and the hook checks that instead of assuming it: (1) refuse to touch the agent if a taint or an `owed-*` record exists: exit `76`. (2) **Bounded drain:** wait up to `drain_wait` for `GET /v1/hosts/{id}` to show no lease, renewing the cordon at each poll, then record `rb_drained`. (3) Record `rb_stop_begun` (fsynced), then stop the unit (SIGTERM; the agent's own drain applies, at most `drain_wait + stop_grace`, inside `TimeoutStopSec`; then `KillMode=mixed`). (4) Relink the previous release, start, and wait for the previous version's hello with `runtime=crun`. |
| the unit is active and the link is already at the previous release (a resumed rollback past (4)'s relink, or an old agent that systemd restarted) | Skip to the hello wait. |

If an `owed-*` record or a taint appears at any point (before the stop, during the drain, after the stop, or when the previous agent does not say hello and the state root is checked), `rollback` stops where it is and exits `76`; a tainted agent refuses every start, the old release included, and nothing is gained by trying (3.8). Because the hello carries the runtime only from jobscheduler#516 on, a previous release whose hello lacks it is checked by version alone **[V]**. The hello wait ends in exit `1` if the previous version does not join within the bound.

**A lease after the bound passes [D].** If the drain of step (2) ends with a lease still on the host (which the cordon should make impossible), `rollback` does **not** stop the agent. It exits `1` with `"reversible": false`, `detail` naming the lease, and leaves the cordon to expire in `cordon_lease_secs` (it stops renewing). This differs from `prepare`'s `75` on purpose: after the commit nothing is deferred and re-ordered, the update is already past `cutover`, and a failed rollback is `Failed` with phase `after_commit` (3.2), which blocks the host's slot and pages for a human. It differs from a stop-and-rerun on purpose too: (1) the SIGTERM would land on a job of unknown phase, and one inside its owed-checks window taints the host for good, which is `76` territory and strictly worse than an agent that is running a version that failed `verify`; (2) the agent's own `--drain-wait` would start a second wait of up to `drain_wait` after the hook's own, so the bound would be double; (3) a lease under a cordon means the cordon failed, which is a fault to see, not to repair around; (4) the host keeps serving: a new agent that failed `verify` is wrong, but it is not stopped. A later `rollback` (an operator's rerun, or the next update order) starts again from `rb_drained` unset. It is not `76`, because a retry once the lease ends can succeed; `76` is for what no retry can repair.

**Marks are written before their acts [D].** Each mark (`stop_begun`, `link_moved`, `start_issued`, and the `rb_*` marks that name an act) is written and synced **before** the act it names, never after. On a rerun a mark means the act *may* have happened, so the step checks the real state (the link's target, the unit's state) and does or skips the act from that; a mark is never taken as proof the act is done. Writing it after would let a kill between the act and the mark repeat an act the record does not know about.

**The release link [D].** The path of the link the agent's unit runs from is the service's own value, carried in the declaration's `[hook.params]` as `release_link` (an absolute path inside the hook's `write_paths`), not a reserved `updater.*` key: the updater owns where releases are staged (`updater.staged_release`), not where a service's unit looks for its binary. `cutover` refuses with `bad_params` without it. The link must sit **inside a declared `write_paths` directory**, never be one: the swap creates a new link beside it and renames it over the old one, which writes the link's parent, and under `ProtectSystem=strict` a parent that is not itself declared is read-only (the declaration's `<release link dir>` is that directory).

**A first install is irreversible [D].** With no `updater.previous_release` there is nothing to relink and no previous unit to stop, so a first install writes no `stop_begun`: `cutover` reports `"reversible": false` from its first act (writing `link_moved`), and a later failure is `Failed(after_commit)`: an honest report, since no rollback could restore a previous state.

**Idempotent on resume [D].** Each sub-step above is recorded and is a no-op when its effect is already visible: `rb_link_restored` is a rename to a target the link already has; `rb_start_issued` is skipped if the unit is active; the SIGTERM is not sent twice for the same `rb_stop_begun` unless the unit is active again (systemd restarted it after it crashed mid-drain, in which case the stop is repeated once, with no second drain). A `rollback` killed anywhere, including by its own timeout, is run again by the updater (3.2, 3.5) and continues from the record; a rollback that is resumed never repeats the bounded drain once `rb_drained` is set.

**Where the old commit point went.** The old text committed at the SIGTERM and had `prepare` abortable until then; the new contract has the same abort window (it ends when `cutover` is entered, not when the signal is sent) and `rollback` after `cutover` is the old `restore_previous`. The old `plan`, `stage`, `abort` and `recover` verbs are gone: `plan` and `stage` are `prepare` and the updater's fetch (3.1 step 2), `abort` is `rollback` after a pre-commit failure, and `recover` is the step record (3.5).

**A halt runs nothing further** (3.2), so a `76` leaves the cordon in place; the cordon is a renewable lease (3.6) and expires in `cordon_lease_secs`, which 3.2 states is harmless for a halt (a tainted agent refuses to start, so no work is lost to it).

**Classifying `verify` (3.8).** Only `release` counts toward rollback of the fleet.
- `environment`: the lease server is unreachable (no hello or host listing can be read). Reported and alerted; it never rolls a healthy release back.
- `release`: a hello with the wrong `agent_version` or runtime; an unclean sweep.
- *`halt` (exit `76`), not a class:* a taint or an `owed-*` record. Page, no retry, **no automatic rollback**, nothing clears it: a tainted agent refuses every start, the old release included. A human decides the repair.

**Why a passed drain bound is `Deferred` and not followed by the stop.** (1) The agent has its own `--drain-wait`; stopping it after the hook's wait would start a second wait of up to `drain_wait`, so the host would drain for twice the stated bound with `TimeoutStopSec` as the only real limit. (2) Whatever the agent does not finish is stopped and rerun from the lease server's rerun budget; an update should not spend a user's budget, and a host whose jobs have none left cannot be updated this way at all. (3) A SIGTERM inside a job's owed-checks window taints the next start, and nothing clears a taint; the hook cannot know the window is closed and must not guess. A deferred update is a refused update, not a killed run and not a bad release: the cordon keeps new leases away, the wait ends in the normal case, and the coordinator re-orders it after `retry_after` (3.8; Question 9).

**Crash cases.** Step resume and the dead-man are the updater's (3.5); the hook is idempotent by the table above. What is js-agent's: an *agent crash mid-drain or a host reboot* is restarted by systemd (`Restart=always`); the new process sweeps the previous run's leases (lost and rerun) and starts clean. A crash inside a job's cleanup window leaves an `owed-*` record, so the start is tainted: the next `verify` (or `prepare`) exits `76`, and nothing clears it **[F]**. *The hook killed during the wait in `prepare`* has changed only the cordon, which the rerun finds in the hook record.

**The declaration** (`/etc/updater.d/js-agent.toml`, 2.4). The hook manages a root-owned unit and no unit-scoped polkit rule is assumed **[V]** (3.4), so `user = "root"`, with every other restriction kept. The first install of this declaration is `Deferred` as `rights_change` until approved, once per host (`updater approve`) or by a fleet approval file (3.3); the first hook-bearing release is itself installed through the interim workflow (3.3, 7). Paths below are those of the package **[V]**.


`verify_deadline_secs` is a top-level key of the declaration (placed before the tables above, since a key after a table header belongs to that table). The cordon lease and cap are the hook's own values in `[hook.params]`; the updater does not read them.

Derivations (each margin is 300 s, Question 16; `drain_wait` 3600 s, stop grace 120 s and `TimeoutStopSec` 3900 s are the unit's values, 3900 = 3600 + 120 + a 180 s margin):
- `prepare` 3900 = `drain_wait` 3600 + 300. The version check, the cordon calls and the unit comparison take seconds.
- `cutover` 4320 = stop 3900 (the unit's own limit) + start to active 120 + 300. The link is a rename.
- `verify` 615 = hello wait 300 + `bake_polls` 3 x 5 s poll + 300.
- `rollback` 8220 = bounded drain 3600 (`drain_wait`, entry (b) only) + stop 3900 (the unit's own limit; the new agent normally stops in seconds, but the limit is the honest bound) + start to active 120 + hello wait 300 (the same as `verify`'s) + 300 margin = 8220. The relink is a rename and the checks take seconds. Entry (a) needs only the start, the hello wait and, after a killed `cutover`, up to 3900 for the unit to finish stopping: 3900 + 120 + 300 + 300 = 4620, inside the same bound. The old value 4320 had no drain and no hello wait.
- `cleanup` 120: an HTTP call and a file delete. It runs only after `verify` succeeded; `rollback` also ends with an uncordon, so it is bounded as above.
- `verify_deadline_secs` 9000 >= `verify` + `rollback` = 615 + 8220 = 8835 (the rule of 2.4), with 165 s of slack; it was 5000 against 4935. Per 3.2 it runs from the success of `cutover`, so the stop is inside `cutover`'s own bound and not in this one. If the deadline instead passes before `verify` has succeeded, the updater runs `rollback` at once, and its own bound (8220) governs.
- `cordon_max_secs` (`[hook.params]`) 17355 = `prepare` 3900 + `cutover` 4320 + `verify` 615 + `rollback` 8220 + 300: every step including a rollback with its drain (it was 13500). The lease expires in 300 s without renewals, so a dead updater costs minutes; the cap only bounds a live one that stalls. The hook renews from a thread while it waits inside a step, since `prepare`, `cutover` and `rollback` each run for up to an hour or more. (The `cordon_max_secs = 13500` in the example of 2.4 is that example's, not this declaration's.)
- The unit's `TimeoutStopSec` (3900) must stay above `drain_wait + stop_grace` (3720): `prepare` refuses a staged unit whose flags differ from these or whose timeout is lower **[new]**.

**Open points.** (a) *The keeper* (jobscheduler#507, in review): until it lands, a stop that reaches `TimeoutStopSec` or a cgroup kill is the only way a container leaves; the hook never kills the agent first. (b) *Lease hand-off:* none, by design; a job that cannot rerun must not be on a host that is updated, since an agent that dies on its own still reruns it. (c) *Cgroup layout across versions:* `supervisor` and `actions` are names two versions must agree on; a release that changes them cannot be swept by the old one, so `prepare` compares and refuses a change **[new]**.

**Where rev 4.1 still does not fit js-agent.** One point, stated so it is not read as a gap: *`verify_deadline_secs` runs from the success of `cutover`*, so the up-to-one-hour stop inside `cutover` is guarded by `cutover`'s own bound and not by the dead-man's deadline. Acceptable (a crash reruns `cutover`, and a `cutover` that passes its bound is killed and followed by `rollback`). The earlier misfits are answered by the generic text: a failed or killed `cutover` runs `rollback` (3.2); a `halt` runs nothing and the cordon expires (3.2, 3.6); `health` is optional (2.1) and the registration client is step 4a of 8; the first hook-bearing release goes through the interim workflow (3.3, 7); the hook's values are in `[hook.params]` (2.4); `user = "root"` is approved once (3.3).

**New work [new].** (1) The `update-hook` subcommand of `js-agent` (jobscheduler), with the steps above; **it must pass the conformance suite (9) in jobscheduler's CI**. (2) The own-host cordon, uncordon and GET route with a requester-set, renewable expiry on the lease server (Question 17; built in jobscheduler#545, 3.6). (3) The runtime in the hello (`contract.rs`), after jobscheduler#516. (4) The sweep result reported outside the log. (5) The registration client: the agent links the tiny crate of migration step 4a (name and version, no `health`) and registers on start. (6) `prepare`'s comparison of the staged unit's flags and cgroup layout. (7) The declaration above in the package.

### 4.3 kbf-daemon: the kbf hook (today's behaviour)

The kbf daemon becomes a hook like the others: `kbf update-hook <step>` does what `agent/update.rs:89-250` does today, split at the five steps, with no change in behaviour. | step | what it does (today's code) |
|---|---|
| `prepare <artifact>` | the host health precondition (`health.refusal`); the node's cordon state before the update (a node already out of placement is never undrained); drain the node at the frontend (cordon, wait until it holds no lease, however long that takes unless `--drain-deadline-secs` is set, in which case a deadline that passes exits `75` with the node left drained and nothing installed over running leases, `agent/update.rs:253`); the cordon mark is kept on disk (`--cordon-dir`) |

## 5. The generic coordinator

### 5.1 Desired version per service; host sets; who should run a service

The coordinator already stores one desired state per service (`desired.rs:239`) and defines services as data (`services.rs`). Today a host belongs to a service only if its own heartbeat lists it and the service's definition has the host's role (`service.rs:200-207`). That is **self-announced membership**: a host that lost its registration disappears from the service's denominator, and convergence can read `converged` while a host has no copy of the service at all (`converge.rs` counts `at_desired` over hosts that announced). Proposal: the service definition holds a **host-set selector** (certificate roles and labels) and the coordinator decides from it who *should* run the service. A selected host that has not reported the service is `missing`, and `converged` fails while any selected, live host is `missing` or `absent` (2.2). A service that no selected host announces is `in_progress`, not converged.

Four rules make this safe to roll out. **An exit:** an operator can mark a host `excluded` for a service, with a reason, audited; an excluded host does not count, and the convergence JSON shows the counts of `missing`, `excluded`, `unmanaged` and `deferred` hosts, so CI sees why a service is not converged. **No deadlock with old agents:** a host whose agent has not advertised the new heartbeat is `unmanaged` for services that have a selector, not `missing`; it does not count until it is upgraded, and the rollout order is coordinator, then agents, then definitions with selectors (a definition whose selector matches such a host is accepted and logged). **Where labels come from:** labels are kept coordinator-side in a host table keyed by node id, set by the operator or carried by the enrollment record; they are never taken from a heartbeat, so a host cannot select itself into or out of a service. **Node ids across systems:** see 2.4.

### 5.2 One host at a time

Per host, already true: `decide.rs:105` orders nothing to a host that has any service updating or an order outstanding (`fleet.rs:179-189`). This is the only serialisation across services this design keeps (Question 1).

**Slots stay per (service, role).** Rev 1 proposed slots shared across services so at most one host of a role is ever down for any service. That couples unrelated services: a tierstore update on one storage host would block a kbf update on another storage host, and `min_up` means different things for different services (kbf: blobs stay readable; tierstore: cache nodes). Slots remain per service (`decide.rs:100-102`), with an optional **named pool** in a definition for two services that really do share a capacity. Two further rules, because a per-host queue has a head-of-line problem (a kbf node drain waits for leases however long it takes, and a js-agent drain up to an hour, so a security fix for another service on that host waits behind them): each definition has a `priority`, which is the order of the reply loop (today it is kbf first and then the agent's announcement order, `service.rs:219`, an accident), and a desired state may carry `urgent`, which makes a host that is not yet updating take that service's order first; it never interrupts an update in progress and never overrides `after`; a service in its `Deferred` backoff on a host is not re-offered first by `urgent`. Three more rules close the holes this opens. **A named pool by default where capacity is shared:** the shipped definitions of tierstore and kbf on `storage` join one named pool, because tierstore's storage node is the blob data path and a failed tierstore update on one host takes capacity that kbf's own `min_up` does not see; the coordinator tests carry that cross-service case. **`priority` ages:** after a service has been ordered N times on a host without progress, the reply loop skips it for the next lower service for `skip_secs` (an in-memory counter beside the orders), so a flapping high-priority service cannot starve the rest. **`urgent` is restricted:** it can be set only by the operator token or by an allow-list entry with `may_urgent = true`, and every use is audited; a service's own CI token cannot set it.

### 5.3 Canary, health gate, rollback; how health is learned

- **Canary.** None in the coordinator today. A one-host canary can be modelled as a separate service with `min_up = 0`, a workaround (without it a lone host is never ordered, `decide.rs:116-120`). Proposal: a first-class `canary` in the service definition: a count or a host selector, ordered first; the rest wait for it.
- **Health gate.** The coordinator never probes: the agent reports `Health` and `UpdateResult` (`wire.rs:29-52`), and a failed update shows as `last_update.outcome == Failed` for the desired version, which keeps the host's slot and makes the service `blocked` (`converge.rs:1-14`). Proposal: keep that, and add the gate as a rule on the *reports*: after a host (or the canary) updates, it must report `healthy` and the desired version for `bake` consecutive heartbeats (a config count) before the next host or the rest of the set is ordered. The coordinator has no network path to a host's loopback and should not get one; the hook's `verify` runs the real checks and the updater reports the result.
- **Rollback.** Today a human or CI sets an older version. Proposal: the coordinator remembers `last_good` per service (the last version for which the set converged and passed the gate) and, when `Failed` outcomes with a phase of `after_commit` or `gate_release` reach the definition's `rollback_after_failed` (3.8) and its definition says `rollback = "automatic"`, sets desired to `last_good` and marks the failed version `bad` (not ordered again until another version is set). CI can still set a version by hand, which clears the mark. The hosts roll back through the same hooks as any update; a host past its hook's commit point (the success of `cutover`, 3.2) is rolled back by the hook's own `rollback`, or, for the fleet, by an update to the older version through the same hooks. A `Deferred` host, a failure before the commit and a post-commit wait that only says the service is slow (4.1.6) never trigger it.
- **Compatibility and order of rollout.** A new agent to an old coordinator degrades quietly: a `services` list the coordinator cannot read is dropped and the host is treated as kbf-only (`wire.rs:175-196`), so a new service would look unmanaged. The coordinator is rolled first. The agent learns what the coordinator supports from `features` in the reply, sent only to an agent that announced `agent_features` (3.8); it refuses to run non-kbf hooks, and does not use `Deferred`, against a coordinator that has not advertised them.

`decide.rs` is generic: it branches on no service name (`decide.rs:79-121`; `decide()` at `:49-54` is a kbf wrapper). The rest is not.

## 6. Where the code lives, and what was considered

**The updater** is generic code in kbf: the crates exist (`kbf-updater`, `kbf-host-install`, `kbf-installer`), their tests pin today's behaviour, and the release pipeline already signs and attests them (`crates/kbf-installer/src/attest.rs:1-17`, a list of accepted signers at `:136-137`). It names no product; a lint checks that its public items and its tests name no service.

**Hooks** live with their services, in their repositories, shipped in the service's release; ours are subcommands of the service's binary. The updater depends on no service; a service depends on no updater crate except one **dev-dependency**, the conformance suite (9): a crate with no kbf product dependency, which a service uses in its own CI to prove that its hook satisfies the contract. The contract is a document and a golden test in the updater's repository.

**The coordinator** is generic code in kbf (5), with a lint of the same kind.

**Alternatives considered.** The previous shape (rev 3) was a library of per-service strategies compiled into the updater, driving a closed set of root verbs: each verb was generic, each strategy was a Rust implementation of a trait, and a service's cutover logic therefore lived in the updater and shipped with the updater, not with the version it cut over to. Two things were wrong with that: the updater had to know every service and to be released whenever a service's cutover changed; and a service's cutover logic could not be tested with the service. **Hooks were chosen** because the cutover logic then ships with the version that needs it, is tested in that service's CI, and the updater stays generic. The cost is that a hook is code that runs as root with declared rights, which is why the declaration, the verified artifact and the rights of 3.3 and 3.4 are the security core of the design. For the tierstore hand-over itself, socket activation and `SO_REUSEPORT` with `tcp_migrate_req` were weighed and port forwarding is a given (4.1.7).

## 7. The interim per-service deploy workflow

Until the pieces above exist, a service that is not `kbf` is rolled by an interim per-service deploy workflow (kept in kbf, off unless a repository variable is set, in its own concurrency group). What it does now: after a release is published, it sets that release as the desired version of the service with the CI token (an allow-list entry that names only that service, `docs/design/updates.md`, section 5.1), polls the convergence of that service (`GET /v1/convergence?service=S`, `docs/design/updates.md`, section 3), runs a check against the hosts, and on a failed check sets the desired version back to the version recorded before the roll. A stall or a cancelled job is "incomplete", not a failure of the release, because the coordinator goes on rolling by itself once the version is set.

How it maps onto the generic pieces later:

| the workflow does | later done by |
|---|---|
| sets desired, polls convergence | unchanged; the workflow becomes "set desired and read the result" |
| runs a check on the hosts | the hook's `verify` and the coordinator's health gate (5.3) |
| rolls back by setting the recorded version | the coordinator's `last_good` and automatic rollback (5.3) |
| a one-host canary service with `min_up = 0` | the first-class canary (5.3) |
| restart timeout, active wait and confirm window as per-service config of the helper | the same values, in the declaration (2.4) |
| records the attempt | the coordinator's `bad` mark |

Nothing in the workflow is thrown away without its replacement being in place first; it is kept, renamed the first-install path, after section 8: it installs each service's first hook-bearing release.

## 9. Tests

The rules for all of them: **no test asserts on or depends on elapsed time**; sequences are driven by handshakes (a count of completed requests, an exit status, a start line, an answer, a file that appears), and hang guards live in `.config/nextest.toml`. **Red proofs come first**: each test is written, seen to fail against the wrong behaviour, and only then is the behaviour written.

**The conformance suite.** A crate that a service uses as a **dev-dependency** and that has no kbf product dependency. It runs the service's real hook binary against a fake service and checks the contract: (1) each of the five steps run **twice in a row** leaves the same observable state as once; (2) **crash-resume at every step boundary**: the harness kills the hook (and, in the updater's own tests, the updater) at the start, in the middle and at the end of each step, runs the step again, and checks the final state is the one an uninterrupted run reaches; (3) the exit codes and the last-line JSON are well formed for success, failure, `75` and `76`; (4) `rollback` after `cutover` returns the fake service to its earlier state, or says `"reversible": false`; (5) `cleanup` after `rollback` and after success leaves nothing behind. A hook must pass it in its service's CI; the updater's own repository runs it against the kbf hook.

**Rights.** In a root job, a test hook declared with a narrow set of rights **tries to exceed it, and must fail**: open a file outside its paths, write where the filesystem is read-only, use `CAP_NET_ADMIN` without it (an `nft` call fails), start or stop a unit not in `units`, read an environment variable not listed, open an address family not listed, run past its timeout (it is killed), gain privilege through `setuid` or `NoNewPrivileges` bypass. Each is a separate test with a red proof (the same hook with the rights widened succeeds).

**Hook state.** A state file planted in the service-writable area (the service's data directory, the old `state.json` location) must not change what the hook does; a record directory writable by the service account is refused at load; two copies of one step (resume while the old transient unit lives) never run at once.

**Trust.** A declaration not owned by root, or group- or world-writable, or in a writable directory, is refused; a hook in an artifact whose digest changed after verification never runs, even when a step is resumed; a declaration that widens rights is `Deferred` until approved; a name mapped to a shared uid, two declarations claiming one unit, a bad file beside a good one (only the bad service is refused).

**The step record.** Kill the updater at every boundary of a full update (before the record, after the record and before the step, mid-step, after the step and before `done`), and check that resume reaches the same end state; a step record from another boot id is treated as running; a record with a newer `schema` is read-only; a `verify` that does not succeed by its deadline runs `rollback` even when the unprivileged part is dead.

**Outcomes.** Exit `75` reports `Deferred`, holds no slot, leaves the service not `blocked`, is not re-ordered before `retry_after`, and never triggers automatic rollback; exit `76` and a failed `rollback` halt the service fleet-wide until cleared with the operator token and survive a new desired version; a `Failed` after commit of class `release` triggers rollback once `rollback_after_failed` is reached, one of class `environment` does not; an old coordinator given the new fields reads them; the pairings of 3.8.

**Coordinator over fake hosts.** The shape of `decide_tests.rs` with several services: per-service slots, per-host serialisation, a named pool, `priority` with ageing, `urgent` restricted to the operator token and not overriding `after`, canary, `bake`, `last_good` rollback, the `bad` mark, a selected host missing the service, `excluded`, `unmanaged`, a coordinator restart mid-roll. The kbf-only golden is unchanged.

**The tierstore hand-over test** and its nftables CI plan belong to the tierstore hook and are the owner's (8): a root network namespace through `cargo xtask sudo-test` (the repository already uses it on hosted Linux runners, `.github/workflows/host-install-linux.yml:47-51`; unprivileged user namespaces are not relied on, `crates/kbf-task/src/network.rs:36-56`, `docs/platform-properties.md:464-465`), a probe that asserts the nft features and the conntrack sysctls and can fail, deterministic scenario tests sequenced by handshakes, a hammering stress test with no retry. The generic updater's contribution to it is only the step record and the rights.

## 10. Questions

Each with a recommendation. The shape (generic updater, hooks in the service's binary, declarations in root-owned files) is decided and is not a question. The js-agent section refers to these numbers (9, 16 and 17 match); the tierstore deep dive keeps its own list of questions, and where it means this list it writes "(host-updates.md Question N)". The owners also keep their own questions for the maintainers (the tierstore deep dive, section 11; the misfit list in 4.2).

1. **Serialisation.** Per host only, per host plus slots shared across services, or global. *Recommend per host (`decide.rs:105`, already true) and slots per (service, role), with an opt-in named pool, tierstore and kbf sharing one on `storage`.*
2. **Who owns automatic rollback.** *Recommend the coordinator (`last_good`, a `bad` mark), limited to post-commit and release-gate failures, never `Deferred` or `halt`.*
3. **A declaration that widens rights.** *Recommend it is `Deferred` until an operator approves that exact declaration (`updater approve`, or a fleet approval file); equal or narrower is installed automatically (3.3). A `user = "root"` declaration is approved once per host or once per fleet.*
4. **How a hook controls units.** A polkit rule generated from the declaration, or `user = "root"` with every other restriction. *Recommend polkit first (scope verified for start and stop, section 11; a hook never masks, 3.4), with root-and-restrictions as the approved fallback, which the kbf and js-agent hooks use today.*
5. **Exit codes, the JSON line and what runs next.** `0` ok, `1` failure, `75` deferred, `76` halt, a last-line JSON, `rollback` after any failed `prepare` or `cutover`, `cleanup` only after `verify` (the table in 3.2). *Recommend as written; the alternative of running `cleanup` after a failure needs every hook to guard against committing in it.*
6. **Private listeners** (tierstore). *Recommend wildcard plus guard with redirect, not loopback plus `route_localnet`.*
7. **Canary and bake as first-class definition fields.** *Recommend yes.*
8. **Install a declared service that never registered.** *Recommend off by default (`install_when_absent = false`).*
9. **The defer backoff.** *Recommend an initial wait of minutes, a factor of 2 and a cap of an hour for js-agent.*
10. **An operator-set `excluded` state for an ineligible host.** *Recommend yes.*
11. **`halt` and who clears it.** *Recommend yes, cleared only with the operator token, audited.*
12. **The declaration comes with the release** and is installed by the updater's trusted step before `prepare`; the first hook-bearing release of a service goes through the interim workflow. *Recommend yes, with the package manager winning where it owns the file.*
13. **The settle** (tierstore). *Recommend about 70 s from the stop of v-current, from the last SYN retransmit of a default client.*
14. **One drain or two** (tierstore). *Recommend replacing the 503 drain unless a deployment relies on it.*
15. **First conversion of a host that listens on 9300** (tierstore). *Recommend a planned restart; a flow not tracked before is reset, one already tracked is not.*
16. **js-agent bounds with no default.** *Recommend active wait 120 s, health bound 300 s, bake 3 polls, cordon lease 300 s renewed at every step, margin 300 s; the confirm window and the cordon cap follow by rule.*
17. **The js-agent cordon route and a renewable cordon lease on the lease server.** *Settled, as built in jobscheduler#545 [F] (merged as 65dcc94eb; 3.6):* own-host cordon, uncordon and GET for the host in the credential, a requester-set lease (default 300 s, 3600 s per request) that a repeat extends, no server-side total cap (the hook's `cordon_max_secs` is the cap), and no placer identity (the hook uses `already_cordoned` to lift only its own cordon).
18. **The registration client.** A tiny crate with no kbf product dependency, linked by services; a synthetic registration from the declaration only as the fallback for a service that cannot link it. *Recommend yes (migration step 4a).*
19. **Hook parameters.** An opaque `[hook.params]` table passed as `--params <file>`, or named fields in the declaration for each service's values. *Recommend the table: the updater stays generic and a service's values (cordon lease and cap, the promotion bound) live in its own declaration.*

## 11. What is unverified

Everything marked [V] or "unverified" in this document, in one place: the oldest supported kernel for NAT in an `inet` chain (a decision, not a fact); that the nft syntax of 4.1.1 loads, that the conntrack sysctls are writable in a root namespace of a hosted runner, and that `nft` exists on the image (the probe decides); that early drop evicts unreplied, non-assured conntrack entries first; that jobscheduler#545 lands with the persistence and expiry 3.6 describes (another repository). **Probes assigned to the root job of step 3 (8), each a test that can fail, so the design stops early if the hosted image refuses one:** (1) a non-root hook account holding `CAP_NET_ADMIN` as an ambient capability under `NoNewPrivileges=yes`, `RestrictNamespaces=yes` and `ProtectKernelTunables=yes` can run `nft` in the host network namespace; (2) `systemctl mask --runtime` followed by `stop` on an active templated instance, driven through polkit, which needs the manage-unit-files action as well as manage-units; (3) `systemd-run --wait --collect --pipe` as a non-root `User=` preserves the exit code and the last stdout line; (4) exec of a binary through a link in a group-readable directory (3.4.1); (5) `/proc/locks` is readable by an unprivileged hook, for naming a lock holder; (6) the js-agent hook's claim that root with no capabilities writes only where it owns, and keeps systemd's authority by uid (4.2). **Probe results** (the root job of migration step 3, on the hosted image; all six ran): (1) holds; (2) a rule for `manage-units` holds an account to the listed units for start and stop, but `mask` needs `manage-unit-files`, which implies `manage-units` for every unit, so hooks never mask (3.4); (3), (4), (5) and (6) hold. Also: `ReadOnlyPaths=` confines nothing under `ProtectSystem=strict` (3.4.1; documented, not probed), and `RestrictAddressFamilies=none` is refused by `systemd-run`, so an empty family list is passed as an empty value, which refuses every family.
