# kbf-installer: contract

Status: design of record for the parallel PRs; on-prem only for now (section 13 lists what is deferred). Marks: **(built)** exists on `feature/pull-updates`; **(to build)** does not. Orders, the order spool, the fetch child, generation and the verification steps are agreed with `pull-updates.md` (#1024), which is their authority (section 12); settings, CLI, units and layout names are decided here, and #1021 (distribution), #966 and #1024 are edited to match (section 11).

## 1. Purpose
`kbf-installer` is THE package and the one root tool for setup and updates of kbf. It is the only writer of root-owned release files. It never updates itself; only the package manager does.
1. **kbf** is the runtime only: `kbf --mode=frontend|storage|daemon|storage-and-daemon|all-in-one` (or `mode = "..."` in `/etc/kbf/kbf.toml`; a flag overrides the file), with `--config`, `--check` and `--instance` as flags. There are no positional arguments and no `node` mode. The old subcommand forms stay as aliases until the test farm has moved, then are removed. kbf never installs, fetches or restarts anything. It writes an order record into the installer's `orders/` directory (section 4) and reports status. kbf.toml has no update or installer keys. Enrollment runs inside the start of the `storage`, `daemon` and `storage-and-daemon` modes; the enrollment token limits which roles a host may hold. There is no `kbf enroll`, `kbf ca` or `kbf token` command: the frontend creates its CA on first start into an empty `--ca-dir`, and tokens are operator-API routes.
2. **kbf-installer** pulls the kbf release itself (an unprivileged fetch child from the one configured source; nothing is root-owned before it verifies), installs, verifies, activates, confirms and reverts releases. It takes its orders from the kbf-owned `orders/` directory, keeps its state under the root-owned `/var/lib/kbf-installer`, and reads its settings from `/etc/kbf/installer.toml`.
3. **The package** ships `kbf-installer`, the unit files (disabled) and the trust files. It ships no kbf runtime release; `setup` installs the first one. It has no package `Depends:` on Envoy: on frontend and all-in-one hosts `setup` and `check` test the installed Envoy against the tested range (section 5.1).

Updates are triggered externally (section 6): nothing in kbf or in the installer decides to update. Not goals: self-update, cloud update providers, fetching or pinning Envoy, an installer network listener, root logic in kbf.

## 2. CLI
One binary (**to build**; today a library plus `kbf-helper`). Mutating verbs are a dry run without `--apply` (**built**). Flags: `--json`, `--apply`; `--root DIR` exists only in builds with the `test-sandbox` feature. Exit codes: 0 ok; 1 failed; 2 usage or missing prerequisite; 3 refused (verification, policy); 4 busy; 5 needs operator. Every verb but `status` and `check` needs root.

| Verb | What it does |
|---|---|
| `setup` | First install. `--mode` (the kbf mode this host runs), `--release-source url\|frontend`, `--release-url`, `--min-generation`, `--commit`, `--no-start`. `--token-file` (the enrollment token; not for `all-in-one`, which does not enroll). Fetches and verifies the release through the same fetch child and checks as an update, writes `installer.toml` (the only writer), **writes `kbf.toml`** (mode and frontend URL) **and places the token** from `--token-file` (0600 root:kbf), creates users and directories. On a frontend or all-in-one host it first checks the installed Envoy against the tested range and refuses with one line and the fix (`envoy_range`). `setup --mode=frontend`, run as root, also creates the **first operator token** once, writes it to a root-only file and prints that file's path, never the secret; it creates none once any operator token exists (the only token path that does not go through the operator API). Idempotent. |
| `status` | Current, previous, staged, pending confirm, last refusal. `--json` equals `status.json` (section 4). |
| `run` | Run by `kbf-installer.service`, no listening socket. Each pass: finish an owed restart, revert an expired swap, sweep scratch, act once on each record in `orders/` in (epoch, id) order, write status. No release polling. |
| `update --commit SHA --frontend` | The frontend host's own update (section 6), run as root by whatever external trigger the operator uses. Runs inline under the lock (exit 4 while a `run` pass holds it); no control socket. |
| `confirm`/`revert ID` | Operator override of a pending swap, naming the activation id; inline under the lock. Exit 5 if none pending. |
| `rollback` | `current` to `previous`, no window. Operator only; the only verb allowed below the release floor. |
| `gc` | Keeps current, previous, one more. State-aware (S22). |
| `boot-check` | Counts starts of a release on trial; reverts when the budget is spent (**built** logic). |
| `quiesce` | For maintainer scripts: takes the lock, exit 5 if a swap is pending (S25). |
| `check` | Validates installer config, trust files, path chain and, on a frontend host, that the installed Envoy is inside the tested range (section 5.1). Lists every problem. |

`stage`, `activate`, `fetch-child` are internal.

## 3. Files, ownership, one source per setting
Three roots, never nested: kbf's own state `/var/lib/kbf` (user `kbf`, systemd StateDirectory, untouched by the installer); the installer tree `/var/lib/kbf-installer` (root:root 0755, not kbf's StateDirectory; everything the root side reads as authority lives here); package files. Only `orders/` in the installer tree is writable by `kbf`.

Package-owned (root:root, no group/other write, changed by package upgrade only):
- `/usr/bin/kbf-installer`, `/usr/lib/systemd/system/kbf-*.service`.
- `/usr/share/kbf-installer/trust/`: pinned `gh`, `trusted_root.jsonl` (with `valid_until`), `installer.conf` (signer workflow, OIDC issuer, repo, allowed source refs, `deny` commit list, and the tested Envoy version range of section 5.1). Replaces `/usr/local/libexec/kbf-deploy`. Allowed source refs live **only** here; `installer.toml` may narrow them, never widen (set intersection).

Installer-owned (root:root):
- `/var/lib/kbf-installer/releases/<sha>/`: `kbf` (the one component on every platform, macOS included), `units/`, and a `VERIFIED` marker written into the directory before it is renamed into place. Files 0755/0644; no setuid, setgid or file capabilities.
- `/var/lib/kbf-installer/releases/current`, `releases/previous`: relative links to `<sha>`. Frontend instances use `slots/<instance>` links (section 6).
- `/var/lib/kbf-installer/state.json` (0600, schema 2) and `state.json.bak`; it supersedes the schema 1 `helper.json` of #1024. `status.json` (0644, section 4). `work/<sha>.partial/` (0755, extraction; `dl/` inside it 0700 holds the tarball), swept at every start. `orders/` (`kbf:kbf` 0700). Lock `/run/kbf-installer/lock`.
- Layout constants live in `layout.rs`, one place. macOS: root-owned `/usr/local/kbf-installer` tree (not a user-owned Homebrew prefix), `/var/db/kbf-installer` for state.

`state.json` schema 2 (types fixed by the golden fixture, section 9 P1; `deny_unknown_fields`): `schema`, `current`, `previous` (confirmed releases only), `staged`, `pending_confirm {activation "<epoch>-<order_id>", commit, previous, deadline_wall, deadline_mono_s, starts_left}`, `floor {epoch, order_id, generation}`, `serving_instance` (frontend), `last_acked_order_id`, `unacked` (copy of the order being acted on, with root's first-seen time of each record in `orders/`). `floor` replaces the built, unused `order_floor`. Schema 1 to 2 migration (including the string activation id) belongs to P3.

Config:
- `/etc/kbf/kbf.toml`: kbf's runtime config, root:kbf 0640 (#966). The installer reads only its existence and its `mode` key (to know whether this is a frontend host).
- `/etc/kbf/installer.toml` (root:root 0644, TOML, unknown keys refused): `release_source` (`url`|`frontend`), `release_url`, `source_refs` (narrowing only), `confirm_window_s` (default 900, bounds 120-1800), `confirm_window_max_s`, `min_generation`, `min_protocol` (operator floors), `fetch_timeout_s` (900, bounds 60-3600), `max_component_bytes` (512 MiB, at most 1 GiB), `min_activation_interval_s` (60), and for the `frontend` source `node_cert`, `node_key` (paths of the certificate and key that enrollment, inside the start of the node modes, writes under kbf's state; the installer opens them `O_NOFOLLOW` at each fetch and lends them to the child, section 5). A `storage-and-daemon` host holds two role pairs: `setup` points `node_cert` and `node_key` at the daemon pair if present, else the storage pair. An `all-in-one` host does not enroll (no remote roles), so it has no pair and uses the `url` source. A host's first release therefore comes from the `url` source or a release `setup` was given; it can switch to the `frontend` source once enrolled. Source is read only from this file, never from an order, offer, environment or flag outside `setup`. This supersedes `[update]` in kbf.toml of #1024.

Users: `kbf` (runtime). `kbf-signer` (frontend and all-in-one hosts only): owns the key that signs certificates and grants, so the frontend process cannot read it; the signer binary ships as a release component and the frontend reaches it over a local socket, with `kbf-signer.service` (section 7). Until that is built, the frontend uses the in-process file signer (#966). `kbf-fetch` (`_kbf-fetch` on macOS): dedicated, no home, `nologin`, no groups, owns no file; it runs the download and the `--version --json` probe, never anything with credentials. There is no `kbf-verify` user.

## 4. Order handover
Channel decides authority, not a body field. There is no order socket, no control socket and no installer listener.
- **Wire orders** reach the installer only as files in `/var/lib/kbf-installer/orders/` (`kbf:kbf` 0700 under the root 0755 tree, so `kbf` traverses to it). `kbf-update` writes one record per order, to a temporary name starting with `.` and renames it into place; the installer ignores dot names. The installer opens `orders/` with `openat` relative to a descriptor it holds and `O_NOFOLLOW`, takes an entry only if `fstat` says a regular file with one link, reads it **once into memory** (at most 1 MiB) and parses from that copy, never re-reading a path; it then removes the entry by name through the same descriptor. At most 64 records are held. A record is expired and removed when older than the confirm-window maximum (1800 s) **measured from root's first-seen time** (kept in memory and in `state.json`), never the file's mtime, so a stuck or hostile writer cannot grow the directory or replay a stale order after a restart. A larger, unparsable, symlinked or non-regular entry is refused and removed. A record is a locator and a set of claims, not trust.
- **Operator orders** (`update --frontend`, `confirm`, `revert`, `rollback`) are CLI runs as root (section 2); `kbf` cannot run them. `update --frontend` is the local fallback of the `frontend_update` record below; both run the same code. A `frontend_update` record is accepted only on a host whose `kbf.toml` mode is `frontend` or `all-in-one`, and only from `orders/`; it is subject to the same ordering, floors and refusals as `activate`.
- **Record**: `{ "order_id": u64, "epoch": u64, "generation": u64, "verb": "activate"|"confirm"|"revert"|"frontend_update", "commit": "<40 hex>", "window_s": u32 }`; for `activate` also the components (from the offer the node holds) for the host's own platform (`name`, `sha256`, `size`, `attestation`, each at most 256 KiB of bundle) and the **expected facts** `platform`, `protocol`, `min_protocol`, `state_schema`, `profile` from the frontend's preflight. Unknown and duplicate keys refused. Nothing in a record is a path, URL, command or unit; unit names come from a code table (S2). The activation id is `<epoch>-<order_id>`. A node holding no offer for the commit writes no record and reports `refused` ("no offer for this commit"). A `frontend_update` record carries none of the components or expected facts (the root half fetches by commit and probes; see section 6).
- **Ordering**: (epoch, order_id), each once (**built**): older epoch and replays dropped, a jump above 1000 beyond the floor refused, a parse failure never advances the floor. **Also** (epoch, generation) lexicographically: within an epoch the generation must be at or above the highest acted on and at most 1000 above it per order; generation 0 refuses `activate`. A rollback is the old release ordered again with a higher generation. This stops a replay, not a forgery by a compromised `kbf`; against that the defence is the operator floor (`min_generation`, `min_protocol` in `installer.toml`), and the intended end state, a frontend-signed grant verified before any fetch, is not designed here.
- **Refused before any fetch** (reason in `status.json`): replay or older, commit not 40 lowercase hex, component set not exactly what the platform needs, size over `max_component_bytes`, expected facts missing (fail closed), a pending trial, below the floor, or a live lease. The installer observes leases itself (Linux: the cgroup of the action unit; macOS: the launchd job and processes by lease uid); the record's claim is never used.
- **Unacknowledged orders**: the record is removed after it is read, but the order is acknowledged only after the flip, so the installer keeps its own copy in `state.json` and reruns it from the start (nothing was flipped, so repeating is safe) unless it has expired.
- **`window_s`** is an input, clamped to `[120, confirm_window_max_s]`; on Linux the window starts at the first start (`boot-check`), so `window_s` is advisory there; on macOS it arms at activation.
- **Status**: `/var/lib/kbf-installer/status.json` (root-owned 0644, atomic rename; in the persistent tree, so it survives reboot), schema 2: **built** fields `installed_commit`, `previous_commit`, `staged_commit`, `state`, `refusal`, `acked_order_id`, `staged{...}`, plus the probe's reported facts, days left on the trust root and "unverified: rollback refused" flags. `state` words: `idle`, `fetching`, `staged`, `activated_unconfirmed`, `confirmed`, `reverted`, `refused`, each 1:1 with `UpdateStatus.State`. `helper_present` means installer present. `kbf-installer.service` starts before the runtime units (`Before=`); `/run/kbf-installer` (tmpfiles.d) holds only the lock.
- A swap pending refuses `activate` (`pending`, exit 4): one confirm window at a time, and `previous` is only ever a confirmed release. A confirm is accepted only if it names the pending activation, the unit is active, `/proc/<MainPID>/exe` is in `releases/<current>`, and the first boot-check has run.
- **macOS**: `kbf` runs as root there, so a compromise of `kbf` is a compromise of root; the separation of this section holds on Linux only. The fetch child and the probe still run unprivileged.

## 5. Fetch and verify
**Release source** (from `installer.toml`, never from an order): `frontend` (default; `ReleaseService.Fetch` by sha256 over mutual TLS, server authenticated by the pinned CA and the frontend name checked against the certificate SAN) or `url` (an HTTPS file server with the store layout `files/<sha256>`; system roots are the transport anchor only, bytes are trusted by verification, not TLS). `setup` refuses non-https, user information, query or fragment. **The child follows no redirect at all**; any 3xx is a failed fetch. No other source is contacted; a compromised frontend can only serve bytes the verification refuses.

**Assets**: tarballs `<name>-<40hex>-<platform>.tar.gz` (**built**, platforms `linux-x86_64`, `linux-arm64`, `darwin-arm64`), each attested by the release workflow as its own subject. The attestation bundle travels in the order record, from the offer the frontend published; it is self-authenticating, so the frontend is a courier, not a trust anchor. Hosts never fetch `SHA256SUMS` (advisory only) and never use `gh attestation download`. There is no release manifest: the facts a release declares come from `kbf --version --json` and are checked against the record (step 5).

**Fetch child** (`kbf-installer fetch-child`, **to build**; the same binary, one child per component, also used by `setup`): the root parent sets `setgroups(0)`, `setgid`, `setuid` to `kbf-fetch` (ids read back), `no_new_privs`, `chdir /`, an empty environment, closes every descriptor but 0 (`/dev/null`), 1 (byte pipe), 2 (log pipe) and 4 (lent identity), `RLIMIT_FSIZE` 0 (it cannot create a file), `RLIMIT_CORE` 0, `RLIMIT_NOFILE` 16, `RLIMIT_AS` 1 GiB, small `RLIMIT_NPROC`; Linux `PR_SET_PDEATHSIG`; macOS kills the process group when the pipe closes. Seccomp and `sandbox_init` are later hardening, not required. **Bytes pass through the pipe**: the child writes the tarball to stdout; the parent hashes while reading and writes a file it created in root-owned `work/<sha>.partial/dl/`, so the child has no object to swap or link. Stderr is read up to 4 KiB and never parsed, the rest drained; the parent uses `poll` and non-blocking reads. Caps: at most `size` bytes (one more kills the child, fewer is a failed fetch), connect 30 s, 60 s without a byte, `fetch_timeout_s` per component, no ranges or resume. Free space under the installer tree must cover the tarball, its extraction (1 GiB or ten times the declared size if smaller) and the release it replaces, computed before anything is opened. A short read, timeout or unreachable source is `refused` with that reason and is not retried; the frontend holds the run and a person re-issues it.
**Identity**: for the `frontend` source the parent lends the node certificate and key named in `installer.toml` (on a two-role host the daemon pair if present, else the storage pair; `ReleaseService.Fetch` admits any enrolled role) over descriptor 4 (Linux anonymous memory file; macOS socketpair; never disk). **A compromised child can steal the node key**: an accepted v1 residual (seven-day certificate). The follow-up is a fetch-scoped client certificate (a distinct extended key usage accepted only for `Fetch`), which replaces P15's proxy idea.

**Every root step is bounded**: wall-clock limit, process group killed on expiry, output read up to 4 KiB and parsed strictly; `gh` runs with an empty environment and empty `HOME`. Limits: 120 s `gh`, 120 s extraction, 10 s probe.

**Verification order**, by the root parent, on files it opened itself (`O_NOFOLLOW`, `fstat` regular and owned); nothing is unpacked or run before step 4:
0. Trust files and every path component of installer, `gh`, trust dir are root-owned, not links, not group/other writable (`openat2` walk). Trust `valid_until` not passed (exit 5), with days left in `status.json`.
1. **Count**: exactly `size` bytes arrived, within `max_component_bytes`.
2. **Digest**: the SHA-256 computed while reading equals the record's `sha256` **and** the attestation bundle's subject digest (the record's digest is only a locator).
3. **Attestation**, offline: pinned `gh` and `trusted_root.jsonl`, `--repo`, `--signer-workflow`, `--cert-oidc-issuer`, `--source-ref` (allowed refs), `--predicate-type`, `--deny-self-hosted-runners` unless decision 6 says otherwise, and `--source-digest` equal to the order commit (**built** `attest.rs` flags). Failure ends the order; nothing from the child is read further.
4. **Shape**: gzip and tar with exactly one regular file named `<name>` (no link, device, directory, absolute path or `..`), at most 1 GiB, extracted by the parent into `work/<sha>.partial/` as root, mode 0755. Binary kind and CPU checked; macOS quarantine refused and `codesign --verify --strict`.
5. **The binary names itself before the flip**: `<name> --version --json` run as `kbf-fetch` (empty environment, no credentials, no network that is enforced in v1) reports the order commit (12 hex prefix) and `protocol`, `min_protocol`, `state_schema`, `profile`, `platform` that must equal the record's expected facts, satisfy the operator floor, and be supported by this installer (else `installer_too_old`). Mismatch refuses before anything is renamed.
6. **Install**: write `VERIFIED` into the directory, rename to `releases/<sha>`, fsync the parent, then `staged` in `state.json`. A `releases/<sha>` without `VERIFIED` and not referenced by `current`, `previous` or `pending_confirm` is removed; a referenced one stays and is flagged "unverified: rollback to it refused". "Already installed" means `VERIFIED` exists, never skips verification of a new fetch, and a rollback to it skips steps 1-4 but reruns 5. Directories made by the test-farm switch never carry the marker.

### 5.1 Envoy is an installed prerequisite
The frontend's update path needs an Envoy in front of it (section 6). Envoy is not part of a kbf release and the installer never fetches, pins, installs or upgrades it. It is **not** a package `Depends:`: one `.deb` serves every host and a dependency cannot apply per host, and there is no separate frontend package. Host preparation installs it, on frontend and all-in-one hosts only. The range is the one the farm has tested, kept in the package-owned `installer.conf`; `setup --mode=frontend|all-in-one` and `check` refuse a host whose Envoy is missing or outside it, with one clear line and the fix. The installer renders kbf's Envoy configuration for the frontend's ports and instances and asks the installed Envoy to reload it; the Envoy service itself is its own package's. Changing Envoy across versions is not designed here (section 13).

**Refusals** (exit 3, stable `refusal` word): `trust_chain`, `hash`, `attestation`, `commit_or_ref`, `facts`, `installer_too_old`, `platform`, `size`, `disk`, `fetch`, `replay`, `generation`, `floor`, `pending`, `lease`, `denied`, `envoy_range` and `frontend_busy` (frontend update only: a second `frontend_update` order while one is in flight). Lock contention is exit 4, not a refusal.

## 6. Update sequences
**Who triggers.** An update is always triggered from outside kbf: an external system calls the frontend's control API (`POST /v1/update/desired` of #1024 6.3) to set the desired release, and calls `POST /v1/update/frontend {commit}` for the frontend's own update (below). For our own farm that external system is its deployment pipeline; the later UI button calls the same two routes. kbf shows no update button and polls nothing in this version (section 13).

**Node update.** With a desired release set, the frontend rolls the storage and daemon nodes through the drain system, one storage node at a time (P14 builds on the API):
1. Drain, then `UpdateOrder{ACTIVATE, commit, generation}`; `kbf-update` writes the record (section 4) and does nothing else.
2. Installer fetches and verifies (section 5), then writes `pending_confirm`, flips `previous` then `current` (state first), then restarts the node units named in its code table.
3. Linux: window starts at the first start (`boot-check`), 3 start attempts; macOS armed at activation, `expire` triggers.
4. New kbf reports `ACTIVATED_UNCONFIRMED`; the frontend sends `CONFIRM`. A compromised new release can self-confirm; accepted residual (section 10).
5. No confirm by the deadline (monotonic plus wall), start budget spent, or `REVERT`: revert state first, then links, then restart; report `REVERTED`.
Crash at any step: `reconcile` makes links match `state.json` on next start (**built**). Fetch failure leaves `current` untouched and reports `refused`.

**Frontend update**: superseded by `docs/design/frontend-proxy.md` (FP). On a frontend or all-in-one host the unprivileged `kbf-proxy` (shipped in this package) owns the swap; the root half only stages and confirms. What this document keeps:
- **Route**: `POST /v1/update/frontend {commit, request_id, ...}` is served by the proxy, not by `kbf` (FP section 4). One update at a time; a second is refused (`409`).
- **Orders (three, all from `orders/`, subject to section 4 ordering and floors)**: `frontend_update` is a locator, `{order_id, epoch, generation, verb, commit, window_s}`, with no components and no expected facts; the root half fetches the commit from `release_source`, takes the attestation from the source, verifies (section 5), probes `--version --json`, and **stages without flipping**, publishing the probe facts under `staged{}` in `status.json`. `confirm` (naming the staged commit) flips `previous` then `current`, state first; it does not check a MainPID because the proxy's children are not units. `revert` drops the staged release. The proxy gates compatibility on the staged facts before it starts anything.
- **No slots.** `slots/<instance>`, `kbf-frontend@%i` and the frontend `pending_confirm` are not used; children run `releases/<sha>/kbf` and are started by the proxy. After a reboot the proxy starts `installed_commit` from `status.json`.
- **gc** also keeps any release directory a live process's `/proc/<pid>/exe` resolves into, so the proxy needs no pin.
- **Operator token.** On frontend and all-in-one hosts `setup` creates `/etc/kbf/operator.token` (root:kbf 0640, never overwritten); `installer.toml` key `operator_token_file` names it. The proxy uses it for the update API until GitHub OIDC (#1088) covers remote triggers.
- `kbf-installer update --commit SHA --frontend` (root) stays as the local fallback and writes the same orders. Node `activate` records never touch the proxy or frontend children, on an all-in-one host too.
- `kbf frontend handover`, the Envoy handover and the writer baton are removed with FP units U7c and U3b.

## 7. Units and gating
Plain files in `packaging/linux/units/`, installed disabled, never enabled by package scripts: `kbf-installer.service`, one unit per mode `kbf` offers (`frontend` as `kbf-frontend@.service`, `storage`, `daemon`, `storage-and-daemon`, `all-in-one`; there is no `node` mode; P11 lists them from `kbf --help`). There is no Envoy unit: Envoy's service is its package's (section 5.1). `kbf-signer.service` (frontend and all-in-one hosts only, `User=kbf-signer`, runs the signer release component, local socket for the frontend, gated like the mode units) is installed disabled with the rest. Paths are literal; there are no `@...@` substitutions. The `check-units` rules (`handover`, `state-store`, `stop`, `credential`, `storage`) move with the units (P11).
```ini
[Unit]
ConditionPathExists=/etc/kbf/kbf.toml
[Service]
ExecStartPre=+/usr/bin/kbf-installer boot-check
ExecStartPre=/var/lib/kbf-installer/releases/current/kbf --mode=<mode> --check
ExecStart=/var/lib/kbf-installer/releases/current/kbf --mode=<mode> --config /etc/kbf/kbf.toml
RestartPreventExitStatus=2
```
`--check` is a flag of every mode, prints every missing prerequisite and exits 2 (**to build**, P12; #1020 runs the same checks at every start). It is `ExecStartPre`, not `ExecCondition`, because `ExecCondition` skips silently on exit 1-254. `boot-check` runs as root (`+`); lock contention waits and neither counts as a start nor fails the unit. There is no enrollment pre-start: enrollment runs inside the start of the `storage`, `daemon` and `storage-and-daemon` modes, so a host without a valid token fails its start with one line, and the token decides which of those roles the host may hold.
`kbf-installer.service` (no socket unit): `Type=simple`, `Restart=on-failure` with exit 4 treated as success, `ConditionPathExists=/etc/kbf/installer.toml`, `ExecStartPre=/usr/bin/kbf-installer check`, hardening (`NoNewPrivileges`, `ProtectSystem=strict`, `ReadWritePaths=/var/lib/kbf-installer /run/kbf-installer`, `PrivateTmp`, trimmed capabilities); P11 lints the `systemd-analyze security` score. Frontend template rules from the handover design apply (`Type=notify`, finite `TimeoutStartSec`, `RuntimeDirectoryPreserve=yes`, no `Conflicts=`).
macOS: launchd plists in `packaging/macos/`; nodes only, via cask or `.pkg` (a formula cannot place a root LaunchDaemon, #966). `kbf-installer` there is root-owned; a user-owned prefix is refused by `check`.

## 8. Compatibility and migration
- Wire: the frozen messages stay, plus the one additive change of #1024 section 5, made together with its tests: `UpdateOrder.generation = 6` and `UpdateOffer` `protocol = 5`, `min_protocol = 6`, `state_schema = 7`, `profile = 8` (older peers ignore them; zeros are refused fail closed). `update_order = 9`, `update_status = 7` unchanged.
- Offers stay on the wire and nodes consume them: the node builds the order record's components, attestation and expected facts from the offer it holds for the commit. `ReleaseService.Fetch`'s caller is the installer's fetch child, not `kbf`. ## 10. Security rules
Threats: A compromised `kbf`; B compromised fetch child or release host; C local user; D old or malicious signed release. Root is out of scope.
- S1. Authority comes from the channel: only `orders/` carries wire orders (section 4). S2. Wire orders act on a fixed code table of node and daemon units; unit and instance names never come from order content.
- S3. Release monotonicity: (epoch, generation) rule, operator floors, trust-file `deny` list; only `rollback` goes lower. S4. `source_refs` narrows only; no PR or feature-branch refs in the default.
- S5. One pass: hash while reading the pipe; the child can create no file. S6. The probe runs on the file that is renamed, extracted by root. S7. Every artifact is bound to the order commit (`--source-digest`). S8. Names and versions are validated, never free-form. S9. `SHA256SUMS` is advisory; trust is the attestation, and the record's digest is only a locator.
- S10. Spawn hygiene, caps, network rules, dedicated uids, download directory outside the root tree (section 5). S11. The node identity is lent over a descriptor and a compromised child can steal it (accepted v1 residual; follow-up P15).
- S12. `window_s` clamped. S13. One activation at a time, minimum interval, `previous` only confirmed. S14. Strict record parsing: duplicate keys refused, ids and generation bounded, dot names ignored, one read into memory.
- S15. `--root` absent from release builds; environment variables ignored; `gh`, `systemctl`, `launchctl` run by absolute path with an empty environment, `GH_NO_UPDATE_NOTIFIER=1`. S16. Trust files expire; the trust root cannot self-update, so revocation ships as a package. S17. The package signing key is the root of trust; packages are signed before any public channel (decision 7).
- S18. Envoy is outside the attested set: it is a host prerequisite whose version `check` compares to a tested range. It carries traffic, never authority; a bad Envoy can drop or delay builds, not forge an order or a release.
- S19. Stage, fsync, rename, fsync parent, then state. S20. A directory is not proof (section 5 step 7). S21. Missing or corrupt `state.json`: use `.bak`, else write nothing and exit 5; never treat as empty. S22. `gc` never removes current, previous, staged, pending, or a release a process executes from; it takes the lock. S23. Links via `current.new` rename; `state.json` is the source of truth.
- S24. Confirm deadlines use monotonic plus wall time. S25. `run` re-execs between orders if its binary is replaced; maintainer scripts call `quiesce`.
- S26. Frontend revert order per section 6. S27. A `frontend_update` record arrives only in `orders/` on a frontend host (or from the root CLI); it is a locator and claims like any record, verified before any use, and one at a time. S28. Leases are observed by the installer, never taken from a record.
- Residuals (accepted): a compromised `kbf` can drop, delay or burn order ids (and on macOS is root), and a bad new release can self-confirm; a compromised release pipeline producing valid attestations from an allowed ref defeats the design (mitigate with protected refs and S4).

## 14. State database schema (frontend and all-in-one hosts)
Postgres is a runtime dependency of these two modes and the installer owns its schema. kbf creates and alters nothing; it only checks the version at its own start.
- **Where.** `database = "postgres:///kbf?host=/run/postgresql"` in `installer.toml`. A URL with a password is refused (the file is world-readable); no message quotes the URL. The role and the database exist before `setup` runs (creating them is not part of this unit).
- **Migrations** are SQL files embedded in the binary (`crates/kbf-state/src/postgres/migrations/NNNN_name.sql`), numbered from 1 without a gap, each applied in its own transaction together with its `schema_version` row, under an advisory lock. The first line says `-- kbf-migration: expand` or `contract`.
- **`setup --mode=frontend|all-in-one`** creates the schema on a fresh database, or brings an older one forward; a dry run without `--apply`. Idempotent.
- **Updates.** Before the helper moves the links for an `activate` order, it applies the embedded migrations up to the `state_schema` the staged release reports (`kbf --version --json`, now the Postgres schema version). A refusal (the installer embeds fewer migrations than the release needs, or the next one is a contract step) stops the swap and is reported in `status.json`. An older release ordered again asks for nothing; kbf's own start check covers it.
- **Expand only.** An `expand` migration is linted: no `DROP`, `RENAME`, `TRUNCATE`, `DELETE`, column type change, `SET NOT NULL`, or `NOT NULL` column without a default. Any migration is refused if it uses `EXECUTE` or controls transactions. A `contract` step ships in a release after the one that stopped using what it removes, and no update applies one. Nothing runs a contract step yet; the verb that will is a later unit.
- **kbf's start check.** kbf supports versions `MIN_SUPPORTED..=latest embedded`. A schema above that range is accepted while every row above it is `expand` (so a release reverted after its successor migrated starts again); a `contract` row above it, a version below the minimum, or no schema is refused with one line. Only the first connection of a store is judged.
- **No migration of old state.** A database that holds tables without a `schema_version` table (a store made before schemas were versioned) fails migration 1 with a line saying so; the farm starts fresh.
